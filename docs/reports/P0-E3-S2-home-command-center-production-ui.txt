15. HOME ARCHITECTURE
--------------------------------------------------------------------------------
`app/(app)/home/page.tsx` is a server component. It fetches, in one
`Promise.all`: `listCurrencies()`, `listAssetTypes()`,
`getFinancialPositionSummary()` — plus `getCurrentProfile()` (already
`cache()`-deduped against the layout's own call) beforehand for the
greeting. Recent Activity is fetched separately, wrapped in try/catch, so
its failure degrades gracefully without taking down the rest of the page
(§41). Every section component receives already-fetched data as props
and performs zero I/O and zero arithmetic — presentational formatting
(`formatCurrencyAmount`, percentage-bar widths already computed
server-side, date formatting) only.

16. AUTHENTICATED-USER DYNAMIC BEHAVIOR
--------------------------------------------------------------------------------
Greeting uses `profile.preferred_name || profile.first_name || null`
(neutral greeting when both are absent) and a time-of-day derived from
`profile.timezone` via `Intl.DateTimeFormat` (never the server's local
time, never hardcoded). Every other section reads directly from
`getFinancialPositionSummary(supabase)`, which is itself scoped to
`auth.uid()` at every underlying RLS-protected read — there is no branch
anywhere in Home's source that checks a specific user id, name, or
persona. Verified explicitly with two structurally different fixture
users in `supabase/tests/home/run.ts`.

17. USER-ISOLATION BEHAVIOR

JPY reporting currency, JPY activity) — asserted distinct profile names,
distinct reporting currencies, zero cross-contamination in

ADDENDUM — ONBOARDING RUNTIME FIX (post-completion, before review)
================================================================================

BUG. `components/onboarding/OnboardingForm.tsx` threw "Maximum update
depth exceeded" and warned "the result of getServerSnapshot should be
cached" in the browser. Root cause: `useSupportedTimezones()` called
`useSyncExternalStore` with a `getSnapshot` of `() =>
Intl.supportedValuesOf("timeZone")` — this allocates a brand-new array on
every invocation. `useSyncExternalStore` requires `getSnapshot` to return
a referentially stable value (via `Object.is`) when nothing has actually
changed; since it never did, React treated every render as "the store
changed," re-rendering forever until it hit its own built-in safety
limit and threw. This was never a case of "useSyncExternalStore is the
wrong tool" — `Intl.supportedValuesOf`/`Intl.DateTimeFormat().
resolvedOptions()` are genuinely browser-only, unavailable during SSR,
and never change during the page's lifetime, which is exactly the shape
useSyncExternalStore is for. The defect was purely the unstable
snapshot.

FIX. `getSupportedTimezonesSnapshot()`/`getDetectedTimezoneSnapshot()`
now compute their value AT MOST ONCE (a module-level cache, populated
lazily on first client call) and return that SAME array/string reference
on every subsequent call — satisfying `useSyncExternalStore`'s stability
contract correctly instead of working around it, which is exactly what
the React warning itself says to do ("should be cached"). `getServerSnapshot`
stays the original fixed empty fallback, so the server-rendered and
first client-rendered HTML remain identical (no hydration mismatch).
`Intl.supportedValuesOf` absence, and any exception either call might
throw, safely fall back to the empty list/string — the form's existing
"inject the user's own detected/saved zone as a selectable option even
if it's not in the full list" logic still lets onboarding complete in
that case, so no second hardcoded timezone registry was introduced and
Nigeria/Lagos is never hardcoded (the detected zone is read from the
real runtime's `Intl` data, whatever it is).

An initial attempt used `useState` + a one-time `useEffect` (the more
commonly-cited alternative to useSyncExternalStore for this exact
"browser-only value unavailable during SSR" case) — this repository's
`react-hooks/set-state-in-effect` ESLint rule rejects ANY direct
`setState` call inside a bare effect, so that approach was replaced with
the cached-snapshot fix above, which needs no effect at all.

REFACTOR (no behavior change). The two hooks and their cached-snapshot
helpers were extracted from `OnboardingForm.tsx` into a new, JSX-free
module, `components/onboarding/useTimezoneOptions.ts`. This was done
specifically so the exact logic that was buggy could be exercised in a
real `react-dom/client` render without needing a JSX/TSX build pipeline
in a standalone verification script (see below) — `OnboardingForm.tsx`
now imports both hooks from it, otherwise unchanged.

ADDENDUM 9 — FINAL MOBILE TEXT-WRAP FIX
================================================================================

Home's visual direction is approved. This is a single, isolated
responsive-defect fix, not a design change.

DEFECT: on manual mobile testing, the Liquid Position card's explanatory
sentence ("Actual cash across your reserves — not receivables, not
estimates.") was being ellipsized (`truncate`) because it shared one
flex row with the reserve-count pill (`ReserveContext`), and the row
didn't have enough width for both at typical mobile widths.

FIX (`components/home/PositionSection.tsx`): the description and the
pill no longer share a row at all. The container changed from `flex
items-center justify-between gap-3` (one row, description truncated via
`truncate`) to `flex flex-col gap-1.5` (two rows): the description is
now a plain wrapping `<span>` (the `truncate` class removed — it wraps
across as many lines as it needs, at its existing `text-xs` size,
unchanged), and the reserve-count pill sits on its own row beneath it,
inside a `flex justify-end` wrapper that keeps it right-aligned (matching
its original visual position) regardless of how many lines the sentence
above wraps to. `ReserveContext`'s own span also had `whitespace-nowrap`
removed and `max-w-full` added, so even an unusually long multi-currency
pill (e.g. three or four currencies each contributing "N reserves
(CODE)") can wrap internally rather than ever forcing horizontal
overflow.

An earlier draft of this fix attempted a single `flex flex-wrap` row
with the description as a `flex-1 min-w-0` item, intending the pill to
drop to its own line only when space was tight. On reflection before
finalizing, this was rejected: with `flex-basis: 0` and `min-width: 0`,
the description item can always shrink to accommodate the pill on the
same line — CSS flex-wrap only wraps items to a new line when even
their minimum sizes don't fit, and an explicit `min-w-0` removes any
such minimum. That approach would have squeezed the sentence into a
very narrow column while keeping the pill inline, rather than reliably
moving the pill beneath it — not a fix for the reported defect. The
two-row structure implemented instead has no such conditional behavior
to get wrong: the description always gets the card's full inner width
to wrap within, and the pill is always on its own line.

STRUCTURAL VERIFICATION AT 320/360/393/430px (reasoned against the
literal CSS values now in source — no browser render available in this
environment, unchanged limitation from every prior addendum):
- Page gutter: `PageContainer`'s `px-4` (16px each side), unchanged.
- Card padding: Liquid Position's `p-4` (16px each side), unchanged.
- At 320px: available inner width for the description = 320 − 16×2
  (gutter) − 16×2 (card padding) − 14px (icon) − 6px (icon gap) ≈ 222px.
  At the existing 12px body-copy size, the ~57-character sentence wraps
  to roughly 2-3 lines within that width — no truncation, no overflow,
  since it's a plain wrapping text node with no `truncate`/`nowrap`
  applied anywhere in its path.
- At 360/393/430px: the same inner width grows (≈262/295/332px
  respectively), so the sentence wraps to fewer lines, never more —
  monotonically improving, no width in the required range is worse than
  320px.
- The reserve-count pill, on its own row in all four widths, needs only
  as much width as its own short text (e.g. "2 reserves (NGN)",
  typically well under 150px) — comfortably within even the narrowest
  (320px) available width, and `max-w-full` guarantees it can never
