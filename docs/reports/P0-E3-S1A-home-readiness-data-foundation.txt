9. MONEY PERIOD-SUMMARY ARCHITECTURE
--------------------------------------------------------------------------------
Two functions: resolve_period_bounds(p_start, p_end) resolves an explicit
range or, when omitted, the current calendar month in the caller's
profile timezone — the single source of "what period does This Month
mean," called both directly (so a zero-activity period still has known,
real bounds) and internally by money_period_summary(p_start, p_end),
which does the actual per-currency aggregation. Classification is
entirely by financial_events.cash_flow_class (income/other_inflow/
expense/other_outflow/transfer/opening_balance) — never by
hand-enumerating event_type — so a future event type needs no change here
as long as its cash_flow_class is set correctly (this directly covers the
brief's "future asset-sale proceeds"/"future external purchase" hints).
lib/domain/money/repository.ts's getMoneyPeriodSummary(client, start?,
end?) calls both functions in parallel and returns one
MoneyPeriodSummary{periodStart, periodEnd, currencies: [...]}.

10. MONTH/TIMEZONE BOUNDARY MODEL
--------------------------------------------------------------------------------
Identical pattern to obligation_summary()/upcoming_obligations()
(P0-E2-S6): coalesce(profiles.timezone, 'UTC'), never the database
server's own timezone. Verified explicitly with a real UTC+14 case
(Pacific/Kiritimati): an event at 2026-01-31T23:30:00Z is still January
31 in UTC but 2026-02-01 13:30 local under Pacific/Kiritimati — the SAME
event was proven to resolve into the January period under one timezone
and the February period under the other, by switching the profile's
timezone between two calls with fixed explicit period bounds.

11. CASH-IN/OUT SEMANTICS
--------------------------------------------------------------------------------
cashIn = sum of income/other_inflow-classified movements (always
positive by construction). cashOut = sum of the negation of expense/
other_outflow-classified movements (always positive). Both exclude
opening_balance and transfer/fx_transfer entirely. Verified: an fx
transfer between the user's own HKD and AED buckets contributes to
neither leg's cashIn/cashOut, only to transferIn/transferOut, on BOTH
currencies independently.

12. INCOME/EXPENSE SEMANTICS
--------------------------------------------------------------------------------
earnedIncome = income-classified only (a strict subset of cashIn).
expense = expense-classified only (a strict subset of cashOut). Verified
explicitly: receivable recovery and loan proceeds both contribute to
cashIn but earnedIncome stays exactly 0; debt principal repayment
contributes to cashOut but expense stays unaffected by it, while debt
interest and fees contribute to both cashOut and expense.

13. TRANSFER/OPENING-BALANCE TREATMENT
--------------------------------------------------------------------------------
transferIn/transferOut are exposed as their own fields, summing the
positive/negated-negative transfer-classified movements respectively —
never folded into cashIn/cashOut. opening_balance is excluded from every
field (cashIn, cashOut, earnedIncome, expense, transferIn, transferOut) —
verified explicitly with an opening-balance event that never appears in
cashIn despite occurring in the same query period as a real salary
deposit.

14. REPORTING-FX ARCHITECTURE
--------------------------------------------------------------------------------
record_manual_reporting_rate(p_base_currency, p_quote_currency, p_rate,
p_rate_as_of default now()) inserts one append-only row into the EXISTING
public.fx_rates table with source='manual', event_id=null.
reporting_fx_rates(p_reporting_currency) returns the caller's own latest
manual row per (base_currency, quote_currency) pair touching the
reporting currency, in either direction — filtering source='manual'
explicitly. Direct/inverse resolution and the inversion arithmetic itself
happen entirely in TypeScript (lib/domain/currency/reporting-rates.ts's
resolveReportingRates(), using decimal.js), never in SQL.

15. EXISTING fx_rates REUSE/NEW-MODEL DECISION
--------------------------------------------------------------------------------
Inspected first, as required. public.fx_rates (P0-E2-S2) already has
exactly the right shape and its own original comment already anticipated
this use ("source=manual rows are standalone user notes"). No schema
change was made. The one place reuse would have been WRONG — treating a
transaction_actual row (the rate actually applied to a past fx_transfer)
as a current reporting rate — is explicitly prevented by
reporting_fx_rates()'s source='manual' filter, never by conflating the
two concepts into one query. No second FX subsystem was created.

16. MANUAL-RATE HISTORY
--------------------------------------------------------------------------------
Append-only: record_manual_reporting_rate() only ever inserts; no
update/delete path exists for a manual rate. Verified explicitly: an
older EUR->BRL rate (6.00) remains readable via listManualReportingRates()
after a newer one (6.20) is recorded, and reporting_fx_rates() resolves
to the latest applicable one (ORDER BY rate_as_of DESC, created_at DESC).

17. DIRECT/INVERSE-RATE STRATEGY
--------------------------------------------------------------------------------
A direct rate (stored as currency -> reporting currency) always wins over
an inverse rate (stored as reporting currency -> currency) for the same
currency when both exist, since the direct entry is literally what the
user recorded to express that currency in the reporting currency.
Inversion uses decimal.js exclusively (new Decimal(1).dividedBy(rate)) —
verified with an exact non-terminating-decimal case (1/1.90). No
triangulation/multi-hop routing exists or was added.

18. FINANCIAL POSITION REPORTING INTEGRATION
--------------------------------------------------------------------------------
getFinancialPositionSummary() resolves the caller's own rates into a
plain Map<string,string> and passes it to the UNCHANGED, REUSED
convertFinancialPositionToReportingCurrency() (P0-E3-S1) — zero new
combination arithmetic was written. reportingPosition is a genuine
three-state field: null (no reporting currency configured at all —
distinct from a missing rate), {status:"not_calculated", missingRates}
(reporting currency known, a rate is missing), {status:"calculated", ...}
(every required rate resolved). Verified end-to-end at the summary level
with an isolated fixture (User B: EUR cash position, USD reporting
currency, one recorded EUR->USD rate) producing an exact calculated
result, and separately with User A's NOK position (deliberately left
unrated) producing an explicit not_calculated result with NOK listed in
missingRates.

19. FX TRANSPARENCY
--------------------------------------------------------------------------------
reportingRateContext exposes, per currency: the resolved (possibly
inverted) rate, isInverse, storedBaseCurrency/storedQuoteCurrency (as the
user actually recorded them), storedRate (pre-inversion), rateAsOf, and
source (always "manual" this phase, never live/market/official).
reportingPosition itself continues to expose reportingCurrency,
currenciesRequiringConversion, ratesUsed, and asOf (all P0-E3-S1,
unchanged).

20. ASSET QUICK-SALE COVERAGE MODEL
--------------------------------------------------------------------------------
asset_quicksale_coverage() reads asset_summary() (the same canonical
source financial_position_by_currency() already uses for
assetQuickSalePotential), filtered to non-archived assets, grouped by
currency: activeAssetCount, quickSaleEstimateCount, quickSaleSum (null
when zero estimated, exact sum otherwise), coverageStatus
(not_set/partial/complete). Verified through a full not_set -> partial ->
complete -> (new unestimated asset) partial -> (archived) complete
progression on one currency, with exact sums asserted at every step via
decimal.js-computed expected values.

21. RECEIVABLE RECOVERABILITY COVERAGE MODEL
--------------------------------------------------------------------------------
receivable_recoverability_coverage() mirrors §20 exactly, reading
receivable_summary(): activeReceivableCount, recoverabilityEstimateCount,
recoverableSum, coverageStatus. Verified through the identical
not_set -> partial -> complete -> archived-exclusion progression on a
dedicated currency.

22. PARTIAL/NOT-SET/COMPLETE SEMANTICS
--------------------------------------------------------------------------------
not_set: zero recorded estimates among active items (including the
appropriate empty state of zero rows at all for a currency with zero
items — verified: a currency with literally no assets produces no row in
asset_quicksale_coverage() at all, never a fabricated 0/not_set row).
partial: some but not all active items estimated. complete: every active
item estimated. Archived items are excluded from both the numerator and
denominator — verified explicitly that archiving the one unestimated item
in a partial set restores complete status, proving exclusion rather than
mere non-counting-toward-the-sum.

23. FINANCIAL POSITION SUMMARY CHANGES

FinancialPositionSummary gained five fields: reportingPosition,

One real migration bug was found during local testing (not present in
the final applied schema): money_period_summary()'s original
`coalesce(sum(...), 0)::text` lost NUMERIC's declared 6-decimal scale

CHF's 2-decimal precision; two rate-string equality checks not accounting

the test file itself.

33. ASSUMPTIONS
--------------------------------------------------------------------------------
- "This Month" / period summary intentionally does not expose category or
  source-level breakdowns — the brief explicitly allows this only "if
  inexpensive and useful," and deferring it avoids scope creep; a future
  breakdown, if needed, would be its own canonical function, not folded
  into this one.
- The manual reporting-rate UI records rates only in the currency ->
  reporting-currency direction (quote fixed to the user's own reporting
  currency) — the domain layer supports resolving an inverse-stored rate,
  but the restrained UI this phase doesn't need to expose recording one
  in that direction, since every rate this phase's UI records is already
  in the direction Financial Position actually needs.
- reportingRateContext returns ALL resolved rates (both those actually
  used and, when reportingPosition is not_calculated, whatever partial
  context exists) rather than being empty whenever the position isn't
  fully calculated — this was judged more transparent ("show what we do
  know") than hiding partial context behind a not_calculated status.
