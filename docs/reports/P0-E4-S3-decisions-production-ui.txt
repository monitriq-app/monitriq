P0-E4-S3 — DECISIONS PRODUCTION UI + CANONICAL EVALUATION EXPERIENCE
================================================================

1. PHASE
P0-E4-S3 — Decisions Production UI + Canonical Evaluation Experience.

2. STATUS
COMPLETE. Decisions is usable end-to-end for all 10 canonical decision
types against the existing, unmodified domain layer built in P0-E2-S7.
No schema or migration change was made this phase (none was needed — a
gap audit found the full calculation/RLS layer already implemented and
tested). A small number of reference elements were deliberately NOT
reproduced because building them would have required either inventing a
calculation the domain doesn't support, or reintroducing an
invented-suggestion pattern the brief explicitly prohibits — see §8 and
§51 for the complete list and rationale for each.

3. OBJECTIVE
Replace the "foundation-level" Decisions screens (`app/(app)/decisions/
page.tsx` and `app/(app)/decisions/[decisionId]/page.tsx`, both
self-documented as "not the final design") with a production UI matching
the approved reference's composition, while strictly preserving: (a) a
Decision as a plan/simulation that never executes a transaction, (b) no
ranking/recommendation/score anywhere, (c) facts vs. assumptions vs.
derived values kept visually distinct, (d) multi-currency truthfulness,
(e) full tenant isolation, (f) the plain-language discipline established
in P0-E4-S2/S2A.

8. DOMAIN GAPS FOUND
Two real gaps, both handled per the brief's own "if a calculation is
incomplete, do not fake it" instruction — see §51 for the full list of
every reference element this affected:
(a) No canonical Stress Test capability exists (no RPC computes a
"repairs overrun +25%" or "sale price 10% discount" hypothetical) — the
reference's toggle pair was OMITTED rather than built as a new
frontend-only forecasting formula, per the brief's explicit "do not
build an entirely new forecasting engine in this UI phase."
(b) No canonical "incremental return on additional capital" comparison
metric exists between two scenarios — the reference's synthesized
"Mathematical Trade-Off" paragraph (e.g. "11.1%... unmodeled until a
time assumption is provided") was OMITTED; Scenario Comparison instead
shows each scenario's own already-canonical derived figures side by
side with no synthesized verdict.
Neither gap required a schema change to work around, and neither
affects any OTHER capability — the rest of the domain (facts,
assumptions, derived values, rule statuses, choice recording) is fully
implemented and canonical, so this is NOT a "PARTIAL — DECISIONS DOMAIN
GAP" phase.

9. DOMAIN CHANGES INTRODUCED
None. No migration was created or modified. No RPC, table, or RLS policy
was touched. Every read/write in the new UI goes through the exact same,
already-tested repository functions from P0-E2-S7.

10. DECISION MENTAL MODEL
"What happens to my money if I do this?" — never "what should I do?" —
implemented literally: every screen shows facts and calculated
consequences; nothing ranks, scores, or labels a scenario "better."
Choice recording (Proceed/Wait/Decline/Keep Reviewing) records the
user's own conclusion; Monatriq never suggests which one to pick.

11. DECISIONS OVERVIEW
`components/decisions/DecisionsWorkspace.tsx`'s Active tab shows: how
many decisions are active (real count, in the tab label), the user's own
real Decision rows (name, type icon, type label, linked asset/liability
name if any, scenario count, current choice chip, a "Review Decision"
action), and a calm empty state when there are none. Nothing here is
generated — `decisions` is `getDecisionSummaries()`'s real output,
passed down from the server component.

12. EMPTY STATE
Implemented exactly per the brief's own copy: "Nothing under review" /
"Start a decision when you want to compare a purchase, investment,
repair, sale or major expense." with a single "Test a Decision" action —
no fake scenarios, no fake savings opportunities, no AI suggestions.

13. NEW DECISION FLOW
"Test a Decision" (the reference's own exact wording, used per the
brief's explicit allowance to prefer "the exact approved reference
wording if it differs" from "Evaluate a Decision") opens the Test New
tab's type grid ("What are you considering?"). Tapping a type opens
`CreateDecisionSheet` — name, optional linked asset/liability (filtered
to real capability-eligible candidates, see §14), currency, and the
type's primary assumption field(s), with secondary/advanced fields
(additional costs, loan terms, expected value, repair target value)
behind the shared `MoreDetails` "More details" disclosure. Submitting
creates the Decision AND its first Scenario in one guided step (two real
RPC calls — `create_decision` then `create_decision_scenario` — chosen
over the old foundation UI's two separately-navigated forms because a
Decision with zero scenarios has nothing to evaluate yet), then hands
off directly into `DecisionReviewSheet` for the same decision.

14. DECISION TYPES
All 10 canonical `decision_type_code` values render as their own tile
(Buy an Asset, Sell an Asset, Repair/Improve an Asset, Invest in a
Business, Large Personal Purchase, Use Savings, Take a Loan/Debt, Pay
Down Debt, Start a New Venture, Other) — a deliberate deviation from the
reference's 9-tile grid, which merges Take Debt and Pay Down Debt into
one "Take or Pay Debt" tile. They are kept separate here because they
are two distinct `decision_type_code` values with different scenario
semantics (new borrowing vs. paying down existing debt) — merging them
in the UI would create ambiguity about which canonical code a tap
should write, and the brief's own "NEW DECISION" section lists all 10
as separate items. Asset-link eligibility is real, not assumed: Sell
Asset only offers assets where `assetCapabilities(type).supportsSale`
is true; Repair/Improve only offers assets where `assetCapabilities
(type).supportsCapitalImprovement` is true (so a Financial Investment
cannot be given a Repair decision, per the brief's explicit example) —
both reuse the exact same capability flags Assets' own UI already
relies on, not a second classification.

15. PROGRESSIVE DISCLOSURE
`lib/domain/decisions/presentation.ts` (new) is the single source for
which of `decision_scenarios`' ~18 columns are relevant to a given type,
and what to call them — the Decisions equivalent of Assets'
`assetDisplayConfig()`/`assetCreationConfig()` pattern. A Repair/Improve
scenario asks for "Planned Repair / Improvement Cost" and (behind "More
details") a target value after repair; it never asks for loan interest,
business ownership, or a property deposit. Both `CreateDecisionSheet`
and `DecisionReviewSheet` read from this one config — no duplicated
per-type field-visibility logic exists in two places (the old
foundation UI's `CreateScenarioForm.tsx` had its own local
`OUTFLOW_TYPES`/`INFLOW_TYPES`/`VALUE_ASSUMPTION_TYPES` arrays with no
counterpart on the read side; that duplication is resolved by this
file, and the open question BUILD_STATE.md's prior report flagged about
centralizing this is now closed).

16. FACTS
`DecisionReviewSheet`'s "Tracked Fact" category shows only real,
currently-true figures read live by `evaluate_decision_scenario()`:
linked asset's cost basis and current value, linked liability's
outstanding principal, and the relevant cash account's current balance
— never copied, never user-editable, never present when nothing is
actually linked.

17. ASSUMPTIONS
The "Your Assumption" category echoes back exactly what the user typed
into the scenario — cash required, proceeds, costs, expected value,
loan terms — never auto-filled from a fact (the domain's own test suite
already proves, e.g., that a Sell Asset scenario never silently copies
the linked asset's target/quick-sale value into the sale-price
assumption; the UI does nothing that could defeat that guarantee, since
it only ever calls `createDecisionScenario()` with exactly what the
user typed).

18. DERIVED VALUES
"What This Changes" shows only fields the evaluation actually returned
non-null: net cash effect (labeled "Cash Required" or the type's own
net-proceeds label depending on sign), cash after, Safe to Deploy
before/after, the type's profit/loss label (Sell Asset only — see §21
of the brief and §20 below), expected final amount invested (Repair
only), and remaining debt (Pay Down Debt / Take Debt). A missing
derived value never renders as a blank or zero — it's simply omitted
from the list, and the standard `fmt()` helper prints "Not calculated"
for any null the code path does still choose to show.

19. CURRENT POSITION
`components/decisions/DecisionPositionCard.tsx` — Cash Position,
Protected Cash, Safe to Deploy, Upcoming Obligations, in the reference's
exact 2x2 grid composition. Reuses `getFinancialPositionSummary()`
directly — the SAME function Home's `PositionSection` calls — so this is
not a second calculation; it is the identical canonical read, invoked
from a second server component. Multi-currency-safe: each cell renders
one line per native currency the user actually has (never blended),
matching Home's own `NativeAmountList`/`SafeToDeployList` pattern rather
than assuming a single reporting currency the way the reference's
"Base Currency: NGN" chip implicitly does (that chip was NOT
reproduced — see §51).

20. WHAT THIS CHANGES
See §18. Sale-specific language is exact per the brief: "Possible Sale
Price," "Selling Costs," "Money You'd Receive After Costs," "What You
Have Invested" (fact), "Estimated Profit / Loss" (derived, explicitly
"Estimated" because the sale hasn't happened) — all sourced from
`presentation.ts`'s `sell_asset` entry. Repair scenarios intentionally
never show a profit/loss label (`showsProfitLoss: false` for
`repair_improve_asset`) — per the brief, a repair is not a sale, so its
derived figure is "Expected Final Amount Invested"
(`basisAfterCapitalizedImprovement`), never "profit."

21. SAFE TO DEPLOY
Reused verbatim from `getSafeToDeployByCurrency()`/
`getFinancialPositionSummary()`'s `nativePositions[].safeToDeploy`/
`safeToDeployStatus` — never recalculated. Supporting copy is the exact
P0-E4-S2A sentence: "Money you can use after protected savings and
commitments." "Not configured"/"Not calculated" render honestly when
`safeToDeployStatus !== 'calculated'` rather than a fabricated number.
No "liquidity buffer" or "capital deployment" language appears anywhere
in the new UI (verified — see §56).

22. RULES
`DecisionReviewSheet`'s Rules section shows exactly the 3 real
rule-relationship fields `evaluate_decision_scenario()` returns —
Minimum Cash Floor, Protected Goal, Protected Obligation — using the
neutral vocabulary (`Aligned`/`Attention`/`Conflict`/`Not configured`/
`Insufficient information`), never Pass/Fail. The reference's separate
"Financial Constitution" TAB shows only the one real, user-configurable
`RuleType` that exists today (`minimum_cash_floor`, via
`getFinancialRuleSummaries()`), per real currency, with real "Not
configured"/threshold-value states, plus a link to the existing `/rules`
screen to configure it — see §8 and §51 for why the reference's other 3
static rule cards ("Vehicle Concentration Limit," "Minimum Expected
Margin," "Protected Goals" as a separately-configurable rule) were not
reproduced: no canonical `rule_type` exists for any of them.

23. GOALS IMPACT
Surfaced exactly as the domain computes it — `protectedGoalStatus` in
each decision's Rules section (see §22), and `protectedGoalCash`/
`protectedCommitments` in the Decision Position card's Protected Cash
cell. No new "this would use $X protected for [goal]" sentence was
added, because `evaluate_decision_scenario()` returns a STATUS
(aligned/attention/conflict/etc.), not the specific dollar amount at
risk for a specific goal — inventing that sentence would require either
a new domain calculation or guessing at which goal is implicated, both
out of scope this phase (documented as an open question, §61).

24. COMMITMENTS IMPACT
Same treatment as Goals — `protectedObligationStatus` per scenario, and
the Decision Position card's "Upcoming Obligations" cell (count + the
nearest one's name), read straight from `getFinancialPositionSummary
().upcomingObligations` — no hypothetical/invented obligation is ever
shown.

25. CONCENTRATION
No canonical concentration-analysis capability exists in this domain
(no denominator — "% of asset value" vs. "% of deployed capital" — is
computed anywhere). Per the brief's own explicit instruction ("If no
reliable denominator exists: do not display a concentration
percentage"), no concentration figure appears anywhere in this phase's
UI. The reference's own vehicle-concentration figures were not
reproduced for this reason (see §8, §22, §51).

26. SCENARIOS
A Decision may have one or many scenarios, all user-created via the
real "+ Add another scenario" affordance inside `DecisionReviewSheet`
(reusing `createDecisionScenario()`, driven by the same
`decisionTypePresentation()` field set as the initial creation sheet).
Nothing auto-generates a "Best Case"/"Worst Case" — scenario names are
entirely user-typed.

27. SCENARIO COMPARISON
When a decision has 2+ scenarios, `DecisionReviewSheet` shows each
scenario's own real derived figures (net cash effect, profit/loss where
relevant, Safe to Deploy after) side by side, with the explicit note
"Shown side by side for comparison only — Monatriq does not rank or
recommend a scenario." No score, no highlighted "winner," no synthesized
verdict (see §8b for what was intentionally omitted here).

28. STRESS TEST
Omitted entirely — see §8a. Building one would have required inventing
a new frontend-only forecasting formula, explicitly forbidden by the
brief ("do not build an entirely new forecasting engine in this UI
phase").

29. USER CHOICE
`DecisionReviewSheet`'s "Your Decision" panel offers exactly Proceed /
Wait / Decline / Keep Reviewing (the brief's allowed vocabulary,
verbatim) plus an optional note, calling `recordDecisionChoice()` —
the same append-only RPC the domain audit already proved has zero
financial side effects, including for Proceed.

30. CHOICE VS TRANSACTION SEPARATION
No code path in this phase's UI calls `record_asset_sale()`,
`recordMoneyReceived`/`recordMoneySpent`/`recordTransfer`,
`createAsset`, `createLiability`, `recordDebtPayment`, or any other
real-transaction mutation. Every write from the Decisions screen is one
of exactly 4 RPCs: `create_decision`, `create_decision_scenario`,
`record_decision_choice`, `save_decision_scenario_evaluation` — all of
which are already proven, by the domain's own 70-assertion test suite,
to touch nothing outside the 5 Decisions tables.

31. DECISION JOURNAL/HISTORY
The Journal tab lists every decision that has a recorded choice
(`currentChoice !== null`), sorted by `currentChoiceAt` descending,
using data already present on `DecisionSummary` — no new RPC needed.
Tapping a row reopens the same `DecisionReviewSheet`, which itself shows
the full per-decision choice history via `getDecisionChoiceHistory()`
(every past choice, its date, and its note — append-only, nothing
overwritten).

32. HOME INTEGRATION
Unchanged in behavior. `components/home/YourMovesSection.tsx` still
reads `DecisionSummary` rows from the exact same
`getFinancialPositionSummary()` Home always has. The ONLY change to this
file is import-level: its own local icon-mapping switch statement was
extracted to the new shared `components/decisions/DecisionTypeIcon.tsx`
(byte-identical case list) so Home and the full Decisions screen render
the same type icon for the same type — not a second copy of the mapping.
No visual, layout, or data change to Home.

33. MONEY INTEGRATION
None of this phase's writes touch Money (`financial_events`/
`cash_movements`) — confirmed both by the domain's own test suite and by
this phase's UI never calling a Money mutation function (§30). The
Decision Position card reads Money's cash totals only via the shared
Financial Position summary, exactly as Home already does.

34. ASSETS INTEGRATION
Read-only: `getAssetSummaries()` supplies the candidate list for linking
an asset to a decision, filtered through `assetCapabilities()` (§14).
No asset is created, valued, or archived from this screen.

35. ASSET SALE SEPARATION
Explicitly and structurally enforced: no file in `components/decisions/`
imports `recordAssetSale` from `lib/domain/assets/repository.ts`, and
none of the 4 RPCs this phase's UI calls can reach `asset_dispositions`.
A Sell Asset decision's "Estimated Profit / Loss" is computed by
`evaluate_decision_scenario()` from the linked asset's live cost basis
and the user's own hypothetical sale-price assumption — a completely
separate code path and separate formula from `record_asset_sale()`'s
real, realised "Profit / Loss on Sale." Recording "Proceed" on a Sell
Asset decision does not execute a sale; the real sale, when it happens,
is recorded separately from Assets' own Sell Asset action (unchanged,
untouched this phase).

36. DEBT INTEGRATION
Read-only: `getLiabilitySummaries()` supplies the candidate list for
Pay Down Debt's required liability link. Take Debt intentionally has NO
liability link (the debt doesn't exist yet — see `presentation.ts`).
Loan proceeds are never treated as income (the derived label for
`netImmediateCashDelta` on a `take_debt` scenario is "Cash Received,"
never "Income" — matching the brief's explicit prohibition).

37. MULTI-CURRENCY
Every currency-bearing figure in this phase's UI is rendered per its own
native `currencyCode` via `formatCurrencyAmount()` — never summed or
blended across currencies. The Decision Position card explicitly lists
one line per currency rather than assuming a single reporting figure
(§19). A scenario's own currency is fixed at creation (matching the
domain's own constraint) and every bucket picker is filtered to
`currency_code` match. No new FX conversion path was introduced; the
existing `convertScenarioNetDeltaToReportingCurrency()` aggregate helper
was not wired into this pass's UI (a scenario's own native currency is
always shown, so no rate lookup was needed to satisfy this phase's
requirements) — flagged as a reasonable future enhancement, not a gap
(§61).

1. BROWSER-QA ISSUE
Manual browser QA on P0-E4-S3/S3A found the calculations themselves
correct but not comprehensible: a user reviewing a Decision could see a
number like "Cash after: NGN 350,100" but had no way to see it came
from "NGN 850,100 (tracked) minus NGN 500,000 (their own payment
assumption)." A flat "Insufficient information" message (already
partly addressed in S3A for the general case) still didn't distinguish
WHICH specific thing was missing when several different figures on the
same scenario were each blocked for a different reason. And a real,
pre-existing Pay Down Debt decision with no linked liability (created
before this phase's own required-link rule existed) surfaced in QA as
"Develop Land / Pay Down Debt" — an understandable user-chosen title,
but with no visible connection to which debt, if any, it was about.

2. ROOT CAUSE
Not a calculation bug — every underlying figure from `evaluate_decision_
scenario()` was already correct (confirmed by re-running the unmodified
70-assertion baseline with zero changes needed). The gap was entirely
presentational: the UI displayed RESULTS without displaying the
PROVENANCE of those results, and displayed absence-of-data as one
generic phrase regardless of which specific canonical fact was missing.
Separately, Pay Down Debt's evaluation formula has always been built
around a linked liability (`hypothetical_liability_outstanding_after`
reads `v_decision.linked_liability_id` directly, per the migration) —
but nothing in the UI ever required selecting one before creating a new
Pay Down Debt decision, so a user could create one that could never
produce a debt figure without realizing why.

3. CALCULATION TRANSPARENCY PATTERN
New pure function, `buildDecisionCalculationExplanation(presentation,
evaluation, minimumCashFloor)` in `lib/domain/decisions/presentation
.ts`. Given an already-fetched `DecisionScenarioEvaluation`, it returns
up to four `CalculationExplanationBlock`s (`cash`, `debt`, `profitLoss`,
`safeToDeploy`), each either `calculated: true` (with explanatory
`terms` plus a `result` copied VERBATIM from the matching canonical
evaluation field) or `calculated: false` (with a specific `reason` and,
only when a real destination exists, an `actionLabel`/`actionHref`).
Rendered inside Decision Review as a new "How this was calculated"
section, using the existing shared `MoreDetails` disclosure component
(collapsed by default — "Collapsed by default is acceptable," per
instruction), positioned after "What This Changes" and before "Not Yet
Calculated" — explaining the figures that DID calculate before
explaining the ones that didn't, a natural reading order. This function
is presentation-only: it is called with data the caller (`Decision
ReviewSheet`) already fetched from `evaluateDecisionScenario()`/
`getFinancialRuleSummaries()`; it performs zero Supabase/RPC calls of
its own and computes zero new financial facts — see §17 for the
explicit "no second engine" verification.

4. PROVENANCE LABELS
Exactly the three restrained labels specified: "Tracked," "Your
assumption," "Calculated" (`TERM_KIND_LABELS`, `ExplanationTermKind =
"tracked" | "assumption" | "calculated"`). Rendered as a small uppercase
chip in front of each term's own label (e.g. "TRACKED  Cash before"),
matching the visual weight of the existing `CategoryBlock`'s own
"Tracked Fact"/"Your Assumption" chips elsewhere in the same sheet, so
the new section reads as the same product rather than a bolted-on
addition. No database field name (`bucket_balance_after`,
`net_immediate_cash_delta`, etc.) is ever shown to the user.

5. CASH EXPLANATION
For any type with cash relevance (a `cashRequired`/`grossProceeds`
field, or Pay Down Debt's payment split): Tracked "Cash before"
(`bucketBalanceBefore`) → the type-appropriate middle term — an
outflow's own assumption amount with a "−" sign, an inflow's `net
Proceeds` (gross minus costs, itself already canonical — never
gross-alone) with a "+" sign, or Pay Down Debt's `totalCashRequired`
labeled "Calculated · Total payment" with a "−" sign — → the canonical
result, "Cash after" (`bucketBalanceAfter`), always copied verbatim.
Not-calculated reasons are specific: "Choose the cash account this
decision would use." (no bucket linked) vs. "Add an amount to
calculate this." (no amount entered) — never a generic fallback unless
neither specific code is present in `missingInformation`.

6. SAFE TO DEPLOY EXPLANATION — DELIBERATELY CONSERVATIVE
This is the one area where the brief's own worked example (`Cash after
/ Minimum cash to keep / Protected commitments / MAX(...) / Safe to
Deploy after`) was NOT implemented literally, and the reasoning is
important: `safe_to_deploy_by_currency()`/`evaluate_hypothetical_bucket_
liquidity()` compute Safe to Deploy from LIQUID CASH ACROSS EVERY
BUCKET the user holds in that currency — but `DecisionScenarioEvaluation`
only exposes ONE bucket's `bucketBalanceBefore`/`bucketBalanceAfter`.
Showing "Cash after (this one bucket) − Minimum cash to keep = Safe to
Deploy after" would silently substitute a bucket-scoped number for the
real currency-scoped number the engine actually used internally — which
is not an explanation of the real formula, it is a DIFFERENT, WRONG
formula that happens to share some terms with it. Per the CRITICAL
ARCHITECTURE RULE's explicit "do not fork Safe to Deploy... into a
frontend formula," this block therefore shows NO equation at all: only
the canonical `currencySafeToDeployAfter` RESULT, plus the user's own
real, static, non-hypothetical configured minimum (from
`getFinancialRuleSummaries()`, newly threaded into `DecisionReviewSheet`
as a `ruleSummaries` prop) as read-only CONTEXT — never as an
arithmetic input, never combined into a displayed "=". "Protected
commitments" (the brief's own `Z`) was deliberately left out of
`context` too, for the same reason plus one more: it is only exposed
for CURRENT state (`SafeToDeployResult.protectedCommitments`, a
different type from a different function), not the hypothetical-after
state this block is about — showing it next to an "after" result would
misleadingly imply it were also hypothetical-after when it is not. This
is a scoped, deliberate, documented omission — not a missed
requirement — and is called out explicitly per the brief's own "if
genuinely lacking information, identify the exact missing domain
output, do not fabricate it" instruction: the missing domain output is
a currency-wide "hypothetical liquid cash after" figure that
`evaluate_decision_scenario()` does not currently return.

7. DEBT EXPLANATION
Rendered for any type that shows a liability link at all (Pay Down
Debt) OR that happens to have one linked (covers legacy/edge cases):
Tracked "Current debt" (`linkedLiabilityOutstandingPrincipal`) → Your
assumption "Principal payment" (`debtPrincipalPayment`, "−") → the
canonical result, "Remaining debt" (`hypotheticalLiabilityOutstanding
After`), copied verbatim — proven by a new test that deliberately sets

missing-information code the migration itself adds specifically for
`pay_down_debt`), confirmed against the actual SQL rather than assumed.
