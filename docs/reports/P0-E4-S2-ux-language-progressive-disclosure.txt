P0-E4-S2 — UX LANGUAGE + PROGRESSIVE DISCLOSURE SIMPLIFICATION
================================================================

1. PHASE
P0-E4-S2 — UX Language + Progressive Disclosure Simplification.

2. STATUS
COMPLETE.

3. OBJECTIVE
Make Monatriq understandable to a normal person answering "How much
money do I have? Where is my money? What am I invested in? What do I
own? What am I owed? What am I working toward? What changed recently?"
without requiring accounting/investment terminology knowledge — without
removing financial truth, weakening accounting semantics, flattening
distinct concepts, or touching schema/migrations/RLS/financial
calculations. Simple language first; advanced financial detail on
demand, via progressive disclosure, never deleted.

4. GIT PREFLIGHT
`git status` at the start of this phase showed the full P0-E4-S1 Asset
Sale/Disposal working tree still uncommitted, exactly as the prior
phase left it (migration, repository/types changes, SellAssetSheet,
SoldAssetsSection, architecture/security doc updates) — none of it was
deleted or rewritten this phase. One unexpected, unrelated diff was
found: `package.json`/`package-lock.json` already modified with a newly
added `"supabase": "^2.117.0"` devDependency (~222 additive
package-lock.json lines), predating this phase's own work. Per this
phase's explicit "if unexpected unrelated changes exist: STOP and
report" instruction, the user was asked via AskUserQuestion how to
proceed and explicitly chose "Leave it as-is, proceed with P0-E4-S2."
That diff was left untouched for the remainder of this phase and is not
attributed to P0-E4-S2's own changes (see §33, Git status).

5. LANGUAGE AUDIT
Searched runtime UI copy (components/, app/) for "cost basis", "capital
allocation", "tracked non-cash", "realised gain", "net proceeds",
"gross proceeds", "disposition", "liquidity buffer", "financial
investment", and related domain terms. Each occurrence was classified:
domain/internal-only (left as-is: `capabilities.ts` internals, database
column names, architecture docs, test names), advanced-detail
(acceptable behind "More details": Gross Proceeds, Cost Basis label
variants, Capital Returned), or default-consumer-UI (simplified: card
labels, form labels, section headings, empty-state copy, help text).
No mechanical find-and-replace was used — every occurrence was read in
its component/context before deciding which of the three buckets it
belonged to, per the brief's explicit instruction.

6. MENTAL-MODEL CHANGES
No architecture or schema change. The five-category user mental model
(Money, Investments, Things I Own, Money Owed to You, Goals) is
expressed purely through copy and section framing on top of the
existing Assets/Money/Receivables/Goals domains, which keep their
existing table/domain names. Money and Investments remain genuinely
separate domains (cash buckets vs. the `assets` table) — this phase did
not and could not merge them; it only made the existing separation read
correctly to a user (Savings/checking/wallet copy lives in Money, never
suggested as something to add via Assets).

21. CENTRALIZED PRESENTATION CONFIGURATION
`lib/domain/assets/capabilities.ts` now exposes three functions with a
clear boundary: `assetCapabilities(assetType)` — what a type CAN do
(supportsVehicleStatus, supportsCapitalImprovement, supportsSale);
`assetCreationConfig(assetType)` — form-question labels for Add Asset;
`assetDisplayConfig(assetType)` — compact card/field labels for display,
plus `showGainLoss`/`emphasizeQuickSale` presentation-priority flags.
This is the single source every display component reads from
(AssetCard, AssetActionSheet, SellAssetSheet, SoldAssetsSection) — no
per-component duplicate label map exists. `showGainLoss`/
`emphasizeQuickSale` are presentation-priority flags only; they gate
which metrics render where, they never gate what data exists or is
computed.

22. MULTI-CURRENCY REVIEW
No change to currency handling. Every renamed label still renders
per-currency, per-asset — no new cross-currency aggregation or fake
single total was introduced anywhere in this phase's changes.
"Liquid Position" → "Cash Position" (not "Available Cash") was a
deliberate truthfulness decision: `liquidCash` includes protected/
goal-allocated amounts, so calling it "Available" would misrepresent
already-earmarked money as spendable — this is documented directly in
`PositionSection.tsx`'s doc comment.

`h-9` (36px) — consistent with the existing disclosure buttons it was
modeled on. Focus is not force-moved into/out of the revealed content,
matching the existing `ManageCashSection` precedent.

================================================================
FINAL UX SIMPLIFICATION CORRECTIONS (P0-E4-S2A)
================================================================

Manual report review after P0-E4-S2 found four items that had been
requested during that phase but were not actually applied to the code
or accurately reflected in documentation. This is a targeted correction
pass on top of the phase above, not a redo of it — nothing else in
P0-E4-S2's scope was touched. All four corrections are presentation-
only or documentation-only; no schema, migration, RLS, or financial-
calculation change.

1. MORE DETAILS TOUCH TARGET
Problem: §20/§23 above describe `components/ui/MoreDetails.tsx`'s
disclosure trigger as `h-9` (36px), below the 48px minimum touch target
for reliable mobile tap accuracy, while §23's accessibility review did
not flag this gap.
Fix: the button's visible box stays exactly as compact as before (still
`h-9`, still reads as a small text-style control) but now carries a
`relative` position and a `::before` pseudo-element with
`before:-inset-y-1.5 before:inset-x-0 before:content-['']`, extending
the button's actual hit-testable area 6px above and 6px below its
visible edges — 36px + 6px + 6px = 48px effective height. The
pseudo-element carries no visible styling (no background, no border),
so nothing about the control's appearance changed. `aria-expanded` and
native `<button>` keyboard activation (Tab to focus, Enter/Space to
toggle) were already correct in P0-E4-S2 and are unaffected by this
change. This is the one shared MoreDetails component every "More
details" control in the app uses (AddAssetSheet, AssetCard,
SellAssetSheet), so the fix applies everywhere at once — no
per-instance patching was needed or done.

2. INVESTMENT GAIN / LOSS LABEL
Problem: `components/assets/AssetCard.tsx` labeled the computed
current-value-minus-basis figure on Financial Investment and Business
Interest cards as "Gain / Loss" — a label that reads as interchangeable
with Asset Sale's "Profit / Loss on Sale," even though the two are
financially distinct (one is an unrealized, still-fluctuating estimate;
the other is a realised, cash-settled outcome from an actual sale).
Fix: relabeled to "Unrealized Gain / Loss" in `AssetCard.tsx` (both the
rendered label and the surrounding doc comment). The calculation itself
— `display.showGainLoss && basis && currentValue ? currentValue.
minus(basis) : null`, using Decimal.js, shown only when both source
values genuinely exist — is byte-for-byte unchanged. Asset Sale's
`SellAssetSheet.tsx`/`SoldAssetsSection.tsx` already used "Profit /
Loss on Sale" / "Profit / Loss" from the original P0-E4-S2 pass and
required no change; the two labels are now unambiguous, and neither
value is ever conflated with the other in code (they come from
different tables — `asset_summary()`'s valuation columns vs.
`asset_dispositions`' `GENERATED` columns).

3. VEHICLE DEFAULT DISCLOSURE
Problem: `lib/domain/assets/capabilities.ts`'s `assetDisplayConfig
("vehicle")` had `emphasizeQuickSale: true`, keeping Quick-Sale
Estimate in AssetCard's primary grid by default. This assumed every
Vehicle is resale-oriented — exactly the kind of unstated assumption
the rest of P0-E4-S2 was written to eliminate, and one the phase's own
Vehicle-simplification section (see original §13 above) explicitly
warned against without first confirming the model could support it. It
cannot: `assetCapabilities()` has no personal-use/business-use/
resale-intent classification field for Vehicle, only
`supportsVehicleStatus` (an operational lifecycle) and `supportsSale`
(a generic capability every non-inventory type has).
Fix: `DISPLAY_CONFIG.vehicle` in `capabilities.ts` now has
`emphasizeQuickSale: false`, matching Property/Equipment/Collectible/
Other — Vehicle's default `AssetCard` shows only What You Paid and
Current / As-Is Value in its primary grid, same as every other
non-investment type. `targetLabel` was also corrected from generic
"Target" to "Target Sale Price" (matching the vehicle-specific wording
`assetCreationConfig()` already used at creation time, and matching
this correction's own instruction). On `AssetCard.tsx`, the vehicle
status badge that previously rendered unconditionally at the top of
the card (for any asset with `supportsVehicleStatus`) was removed from
that default position and is now rendered as a "Vehicle Status" entry
inside the card's "More details" section alongside Quick-Sale Estimate
