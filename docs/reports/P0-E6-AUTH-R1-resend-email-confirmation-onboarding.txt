2. ROOT CAUSE
-------------
PKCE flow + default email template. The browser client starts signup in PKCE mode and stores a one-time "code verifier" cookie in THAT browser. The default template link goes to Supabase's own verify endpoint, which redirects back with `?code=`. The callback can only exchange the code if the verifier cookie is present. Users usually open the confirmation email in a different context than the one that signed up (mail app / in-app browser / another device / the installed PWA, whose cookie jar is separate from Safari/Chrome). There the verifier is missing, exchangeCodeForSession fails, and the user is bounced to /login (or, if the redirect URL is not allowlisted in Supabase, to the site root with Sign In / Create account). Result: confirmed at Supabase but no Monitriq session, so "back at Sign Up / Sign In".
Contributing defects: no resend, raw provider errors, login ignoring the callback error, and an unvalidated `next` in the callback (open-redirect: `next=@evil.example` produced https://<origin>@evil.example).

3. CONFIRMATION ARCHITECTURE
----------------------------
  Signup -> Supabase Auth generates the token and hands the email to its SMTP provider (Resend, once configured) -> email link {{ .SiteURL }}/auth/confirm?token_hash=...&type=email -> Monitriq server route app/auth/confirm/route.ts.
  Resend only delivers mail. Supabase Auth remains the token authority. No second token system, no Resend API call from the app, no Resend key in the repo.
  The route (server client, cookie session):
    1. reads token_hash + type; missing token or unsupported type -> /link-invalid?reason=missing
    2. supabase.auth.verifyOtp({ type, token_hash }); error -> /link-invalid?reason=expired|invalid (Supabase reports expired and already-used identically as otp_expired)
    3. supabase.auth.getUser() to confirm the session really exists in this cookie context; none -> /link-invalid
    4. reads the EXISTING profile through getProfile() (RLS, anon key); never creates/updates it
    5. redirects (Cache-Control: no-store)
  Accepted types: email, signup (confirmation) and recovery (so the reset email can be moved to the same pattern later). Anything else is rejected.
  Works from any browser: it does not depend on a code-verifier cookie. (Tokens generated for PKCE signups are prefixed `pkce_`; verifyOtp accepts them — verified in the browser test.)
  Existing /auth/callback is kept for the PKCE recovery link; no duplicate system was created. Its `next` is now validated.

4. SESSION ESTABLISHMENT
------------------------
verifyOtp runs on the SSR server client, so the Set-Cookie session is written to the same redirect response. Browser test: link opened in a brand-new browser context with no prior cookies arrived at /onboarding authenticated; refresh stayed on /onboarding; the cookie is the normal Supabase SSR auth cookie (SameSite=Lax, Path=/), no cookie setting weakened. Before this, the same route confirmed getUser() sees the user.

5. ONBOARDING REDIRECT BEHAVIOUR
--------------------------------
onboarding_completed = false -> /onboarding (always; any `next` is ignored so first-run users cannot skip setup).
Browser-verified: after confirmation -> /onboarding "Set up your workspace"; authenticated incomplete user visiting /home is sent to /onboarding; unauthenticated /onboarding -> /login; completing onboarding -> /home.

6. ALREADY-ONBOARDED BEHAVIOUR
------------------------------
onboarding_completed = true -> approved `next` if given, else /home. Authenticated + onboarded visiting /onboarding -> /home (existing guard, verified). Sign out -> sign in -> /home (verified). Recovery links -> /update-password (verified for an onboarded account). A confirmed user is never sent to /login, /signup or /auth unless verification failed (unit-tested).

7. OPEN-REDIRECT SECURITY
-------------------------
lib/auth/redirects.ts safeNextPath(): only approved internal app paths (home, money, budget, goals, assets, liabilities, receivables, decisions, financial-position, rules, spending-check, onboarding, update-password); query/fragment dropped; rejects https://, //, ///, backslash, @host, javascript:, encoded control characters, ../ and unlisted paths. Applied in /auth/confirm and /auth/callback. Tested with 15+ hostile inputs; browser test with next=https://evil.example stays on-site.

11. RESEND SMTP REQUIREMENTS (configured IN SUPABASE, never in the repo)
------------------------------------------------------------------------
  Provider Resend; host smtp.resend.com; port 465; username `resend`; password = a Resend API key (sending access) entered only in the Supabase dashboard; sender name Monitriq; sender email = an address on a domain verified in Resend (SPF + DKIM, ideally DMARC).
  No NEXT_PUBLIC_RESEND_* variable exists; no Resend key or service-role key is in app code, email, URLs or logs (tested).
  TRACKING: disable Click Tracking and Open Tracking for the sending domain in Resend (Domains > the domain > Configuration). Click tracking rewrites links through a tracking host, which breaks or delays token_hash links and lets Resend's redirect service see them; open tracking injects an image that can trigger scanners. Authentication mail must be sent untracked.
