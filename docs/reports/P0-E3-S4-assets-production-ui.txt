P0-E3-S4 — Assets: Production UI + Asset Workflow Completion.

built against the approved reference, and verified against real

progressive-disclosure Add Asset, a generic + subtype-aware detail

can be safely added within this phase.

alongside Assets, with `recordRecovery()` and `updateReceivable()`

14. ASSETS OVERVIEW
`TrackedAssetsSummaryCard` shows tracked non-cash asset totals grouped by
category and currency (Decimal.js summation, never native float),
sourced from `asset_value_by_type()`. Cash is never included — Money
owns cash, and the headline is scoped to non-cash tracked assets only,
avoiding the double-count risk the brief called out. Only categories
with a real present asset render.

15. ASSET CATEGORY COMPOSITION
`CapitalAllocationCard` renders one segmented bar PER CURRENCY (never
blended across currencies) using real current-value composition from
`asset_value_by_type()`. Category color is identity-stable via a fixed
`COLOR_BY_TYPE` map keyed by asset_type code (not sort/array position),
matching the established Home/Money precedent. Colors carry no good/bad/
risk semantics — purely categorical.

16. NEEDS ATTENTION
`NeedsAttentionSection` surfaces exactly two real, factual signals: (a)
assets with `estimatedCurrentValue === null` (missing valuation), and
(b) receivables with `lastFollowUpAt === null` (no follow-up ever
logged). No "urgent"/"risk"/"sell now" language anywhere. Empty when
neither condition is true for any record.

17. POTENTIAL LIQUIDITY
`PotentialLiquiditySection` only includes assets where `quickSaleEstimate
!== null` — the user's own conservative quick-sale figure, never target
value, never latest current-value estimate. Assets without a quick-sale
figure are simply absent from this section rather than defaulting to
another value.

18. GENERIC ASSET DETAIL
`AssetCard` is the shared foundation used for every asset type: Cost
Basis, Current Value (Est.), Quick-Sale Value, Target Value are rendered
as four visually distinct fields (never merged/derived from one
another), plus a status chip (`assetStatusLabel()`, "Status not set"
fallback) and a "Manage" trigger opening `AssetActionSheet`. Notes,
valuation history entry points, and timestamps are exposed via the same
canonical `asset_summary()` fields already returned.

19. VEHICLE DETAIL
No vehicle-specific screen/fields were added beyond what the generic
foundation + `status_code` already provide — the domain has no vehicle-
only columns (classification, remaining-repair-as-a-field, etc. do not
exist as first-class columns; "remaining repair" is derivable only via
basis-event history, not a stored field). Vehicles render through the
same `AssetCard`/`AssetActionSheet` foundation as every other type,
correctly avoiding inventing vehicle information the user never entered.

20. VEHICLE STATUS
`assets.status_code` (new column, §9) with 6 real, user-set values:
Awaiting Repair, Repairing, Ready to List, Listed, Offer Received, Under
Negotiation. Unset renders "Status not set." Status is a plain dropdown
in `AssetActionSheet` calling `updateAsset({statusCode})` — nothing in
the read or write path infers status from valuation/repair data ("Insight
!= status" preserved by construction, not by convention).

21. VEHICLE REPAIR HANDLING
`AssetActionSheet`'s "Record a repair / improvement cost" form calls
`recordBasisEvent({basisEventType: 'capital_improvement'})` — a real,
already-canonical append-only basis-history row. This increases cost
basis but deliberately does NOT create a `financial_events`/
`cash_movements` row and does not touch Money, per the brief's explicit
instruction not to auto-capitalize every repair as a combined cash+basis
event (no such atomic canonical operation exists). If the user paid from
a tracked cash bucket, that is recorded separately as real Money Spent
via Quick Add — documented in-component via a code comment.

22. OFFERS
NOT implemented. No Offers table/model exists in the domain, and the
brief explicitly permits deferring this: "Do not create an offer system
solely because the screenshot has a decorative offer chip." No offer
chip, count, or fabricated state appears anywhere in the UI. See §31 for
the full audit reasoning.

23. PROPERTY/LAND
Rendered through the generic `AssetCard`/`AssetActionSheet` foundation —
type, cost basis, current estimate, quick-sale estimate, target value,
valuation history all real. No freehold/title/survey/mortgage/equity
field exists or is fabricated. Debt/Encumbrance is not rendered as a
distinct field this phase (no `asset_id` FK on `liabilities` — §8d); it
was not invented as "Debt: Not set" copy since no UI slot for it was
built, avoiding a half-implemented field. This is a disclosed omission,
not a silent gap (see §51).

24. RECEIVABLES
`ReceivablesSection` renders real Receivables cards (separate domain,
composed alongside Assets) — face amount, outstanding, recovered,
currency, status, last follow-up all sourced from `getReceivableSummaries
()`. Receivables never contribute to the Assets tracked-total headline or
liquidity figures as if they were cash.

25. RECOVERY INTEGRATION
`ReceivableActions.tsx` provides `LogFollowUpButton` (calls
`updateReceivable()` directly, setting `lastFollowUpAt`) and
`RecordRecoveryButton` (opens the global Quick Add sheet via
`useQuickAdd().open()` then `.goTo("received")`, routing to the existing
Money Received → Receivable Recovery flow built in P0-E3-S3). No
duplicate recovery form was built in Assets.

26. BUSINESS INTERESTS
Rendered through the generic foundation with an added disclosure line in
`AssetsBoard` for this category specifically: "A business interest's
invested amount is not automatically its market value. Business income
and spending are tracked in Money." No automatic market valuation is
computed; invested amount (cost basis) and market valuation (current
value estimate) remain the two distinct, separately-entered fields
already provided generically. Deliberate reference deviation: the
reference's own claim that business interests are "not included in
portfolio total" was NOT reproduced, since Monatriq's real
`asset_value_by_type()` DOES include valued business-interest assets —
reproducing the reference's claim verbatim would have been a misleading
financial statement.

27. VALUATION HISTORY
Every valuation update goes through the existing `recordValuation()` →
`asset_valuations` (append-only, timestamped, latest-per-type read via
DISTINCT ON) — prior estimates are never overwritten. Updating a value
from e.g. one figure to a higher one does NOT create a Money In entry;
this is enforced structurally, not by copy, since `recordValuation()` has
no code path that touches `financial_events`/`cash_movements` (verified
by the pre-existing test "Valuation creation does not create
financial_events or cash_movements").

28. QUICK-SALE VALUE
Always explicitly user-entered — via `recordValuation({valuationType:
'quick_sale_estimate'})` in `AssetActionSheet`, or at asset-creation time
in `AddAssetSheet`. Never derived as a percentage of target/current
value; when absent, sections requiring it (§17) simply omit the asset.

29. TARGET VALUE
Purely aspirational/planning — same `recordValuation()` mechanism,
`valuation_type = 'target_value'`. Confirmed (by existing pre-phase test
"Target value is never returned as the current estimated value") that it
never silently substitutes for current value, and by construction it
never enters `asset_value_by_type()`'s Net-Worth-facing totals (that
function only reads `estimated_current_value`).

30. ADD ASSET
`AddAssetSheet` implements 2-step progressive disclosure: step 1 (Asset
Type / Name / Currency — required), step 2 (Cost Basis / Current Value /
Quick-Sale Value / Target Value — all optional, contextually labeled via
`BASIS_LABEL`/`CURRENT_VALUE_LABEL` maps, e.g. "Capital Invested" for
Business Interest). No Vehicle-only fields are shown for non-vehicle
types, since no such fields exist in the domain to show. Creating an
asset never moves cash (`createAsset()` has no cash-bucket interaction —
see §33).

31. ASSET EDITING
Differentiated by mutation type, per the brief's explicit "do not treat
all changes as one generic UPDATE form": metadata (name — not exposed as
editable this phase, since no reference affordance requested it),
valuation update (`recordValuation`, new history row), financial event
(`recordBasisEvent`, new history row), status transition (`updateAsset
({statusCode})`, plain column update), archive toggle (`updateAsset
({isArchived})`). All four are distinct forms/buttons inside
`AssetActionSheet`, not one combined form.

32. ARCHIVE/DELETE BEHAVIOR
Archive only — `AssetActionSheet`'s "Archive Asset"/"Unarchive Asset"
button toggles `is_archived` via the existing `updateAsset()` mutation
(pre-existing capability, not new this phase). No hard-delete UI was
built, per the brief's explicit "do not hard-delete financially
meaningful assets merely because the reference has a trash icon."

33. ASSET ACTIVITY/TIMELINE
Not built as a separate dedicated timeline view this phase. The
reference's activity/timeline treatment was not reproduced as its own
section; valuation and basis-event history remain queryable/real via the
existing append-only tables but no new UI surface was added to render
them as a combined chronological feed. Disclosed omission (§52) — adding
this safely was judged lower priority than the core Overview build
within this phase's scope, and no existing read function currently
returns a combined, ordered valuation+basis-event stream.

34. ASSET SALE/DISPOSAL AUDIT
Re-confirmed: zero sale/disposal mutation exists anywhere in Assets, and
none was added by P0-E3-S3. A safe implementation requires: atomicity
(single transaction spanning asset lifecycle + cash movement + basis
history), ownership verification of both the asset and destination cash
bucket via `auth.uid()`, currency-compatibility checking, correct
separation of capital-returned vs. realised gain/loss (computed in SQL,
never in JSX), selling-cost handling, idempotency/double-sale prevention,
audit-preserving history, and a full adversarial RLS test suite (cross-
user asset, cross-user bucket, double-sale, currency mismatch). This is a
materially separate scope of domain + security work from the Overview UI
build completed this phase. Per the brief's own explicit instruction —
"If safely completing this requires significant architecture redesign:
STOP and report: ASSET SALE DOMAIN GAP rather than inventing unsafe
accounting" — this phase reports exactly that gap rather than
implementing a partial/unsafe version.

ADDENDUM — ADD-ASSET TYPE SELECTOR — FUNCTIONAL HORIZONTAL SCROLL FIX
================================================================

Manual browser QA disproved the previous pass's assumption that
`overflow-x-auto` + a hidden scrollbar was sufficient — the selector did
not reliably let the user reach every asset type. This pass replaces
that structure with a real scroll-owner/track separation and adds
desktop-discoverable controls. Scope stayed exactly where the brief drew
it: only the Choose Asset Type interaction changed. Assets Overview,
Capital Allocation, AssetCard, Manage, the Add Asset data model,
mutations, asset types themselves, RLS, schema, Money, Financial
Position, and Asset Sale/Disposal were not touched.

ROOT CAUSE: the previous structure was a single flex row
(`-mx-4 flex gap-1.5 overflow-x-auto px-4`) with `shrink-0` on each chip
but no `min-w-0` on the scrolling element itself. Without `min-w-0`, a
flex item that is also an auto-sizing scroll container does not reliably
concede layout space to its content the same way across all rendering
paths — in some cases the browser can end up sizing the scroll container
to (or constraining it near) its content's shrink-to-fit width rather
than the space actually available, which changes how much genuinely
becomes reachable via scroll versus how much silently sits outside the
scrollable range. There was also no verified, owned mechanism ensuring
the selected chip — or any off-screen chip — could actually be scrolled
to; the row relied entirely on default browser scroll behavior with no
explicit scroll-into-view guarantee and no visible affordance for
pointer (non-touch) users once the scrollbar was hidden.

SCROLL VIEWPORT STRUCTURE (new `components/assets/AssetTypeSelector.tsx`,
the scroll-owning element): `relative min-w-0 overflow-x-auto
overflow-y-hidden no-scrollbar overscroll-x-contain touch-pan-x`. The
explicit `min-w-0` is the actual fix — it lets this element shrink to
the space its flex-row parent (the prev/next-button layout, see below)
actually gives it, which is what makes the wider inner track truly
overflow and become scrollable rather than silently expanding its
ancestor. `overscroll-x-contain` stops horizontal scroll from chaining
into the sheet's own vertical scroll or the page behind it;
`touch-pan-x` declares the element's intended touch gesture explicitly
rather than relying on default touch-action inference.

INNER TRACK STRUCTURE: `flex w-max min-w-full gap-1.5 px-4`, nested one
level inside the scroll viewport. `w-max` lets the track grow to its
natural content width; `min-w-full` keeps it at least as wide as the
viewport when there are few chips (so short rows don't look
truncated/off-balance). Because sizing responsibility is split between
viewport (owns scrolling, allowed to shrink) and track (owns content
width, allowed to grow), the track can genuinely exceed the viewport's
width, which is what makes the remaining chips actually scrollable
instead of invisibly compressed.

CHIP SHRINK BEHAVIOR: every chip keeps `shrink-0 whitespace-nowrap` (as
before) plus its exact prior visual dimensions (`px-3.5 py-1.5
text-[13px]`, category icon, active/inactive coloring) — chip appearance
and the asset-type data itself are unchanged. Chips are rendered
directly from the same `assetTypes` prop with no slicing or filtering,
so every canonical type the database returns (Vehicle, Property,
Business Interest, Financial Investment, Equipment, Inventory,
Collectible, Other — the application's actual 8 asset-type rows; "Money
You're Owed"/Receivables is, as established throughout this phase, a
separate domain with its own flow, not an `asset_type` option, and was
correctly not added here) is guaranteed reachable by construction — the
component never limits which items can scroll into range.

DESKTOP OVERFLOW CONTROLS: two small (`h-7 w-7`) circular buttons —
"Previous asset types" / "More asset types" (exact `aria-label`s) — render
only when `canScrollLeft`/`canScrollRight` are true, computed from the
viewport's real `scrollLeft`/`scrollWidth`/`clientWidth` (not assumed),
recalculated on scroll and on window resize. Each click scrolls by 70%
of the viewport's visible width via `scrollBy({..., behavior:
"smooth"})` — never changes `assetType`, only scroll position. They sit
outside the scroll viewport in a plain flex row (prev-button |
viewport | next-button), not absolutely positioned over the chips, so
they never obscure content. A restrained, token-based edge fade
(`bg-gradient-to-r/l from-surface-raised to-transparent`, `w-4`, no
glow) renders on whichever side still has offscreen content, using the
same `canScrollLeft`/`canScrollRight` state — never on a side with
nothing left to reveal.

SELECTED-CHIP SCROLL: a `useEffect` keyed on the selected `value` reads
the matching chip via `[data-asset-type="<code>"]` inside the viewport
and calls `element.scrollIntoView({ behavior: "smooth", block:
"nearest", inline: "nearest" })` — `block: "nearest"` specifically
avoids scrolling the sheet/page vertically, only the horizontal chip row
moves.

ACCESSIBILITY: every chip remains a real `<button>` (native Tab focus,
Enter/Space activation). The two new scroll controls are real `<button>`
elements with explicit `aria-label`s, independently focusable and
keyboard-activatable, and are omitted from the DOM entirely (not just
visually hidden) when there is nothing in that direction to scroll to,
so Tab order never lands on a dead control.

POINTER/TOUCH/TRACKPAD: touch swipe and trackpad horizontal gesture are
native `overflow-x-auto` behavior, preserved by this structure (nothing
here disables or intercepts them); the two visible buttons cover mouse
