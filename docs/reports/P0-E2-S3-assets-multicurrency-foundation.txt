6. CURRENCY REGISTRY CHANGES
---------------------------------
Expanded from 26 to 158 currencies
(supabase/migrations/20260922220526_expand_currency_registry.sql).
Method, fully reproducible and documented in the migration file's header
and docs/architecture/MULTI_CURRENCY_MODEL.md §3:
  1. Intl.supportedValuesOf('currency') (Node v24.14.0, ICU 78.2, Unicode
     17.0) — ICU's own list of currently-active, formattable currency
     codes. Already excludes precious-metal codes (XAU/XAG/XPD/XPT) and
     the "no currency"/testing placeholders (XXX/XTS).
  2. Two further exclusions: XDR (IMF Special Drawing Rights — a reserve/
     accounting unit, not spendable personal-finance currency) and XSU
     (Sucre — an ALBA regional clearing unit, same reasoning). Genuine
     regional fiat currencies that happen to use an "X" prefix (XAF, XCD,
     XCG, XOF, XPF) were kept — real, actively used money.
  3. Two superseded/historical exclusions, both with real replacements
     already in the list: SLL ("Sierra Leonean Leone (1964-2022)",
     replaced by SLE) and ZWL ("Zimbabwean Dollar (2009-2024)", replaced
     by ZWG).
  4. For each remaining code: Intl.DisplayNames for the display name,
     Intl.NumberFormat's formatted currency part for the symbol (falls
     back to the code itself when ICU has no distinct 'en'-locale symbol
     — expected, since symbol is presentation-only, never identity), and
     that formatter's maximumFractionDigits for decimal_exponent.
Result: 158 rows, verified duplicate-free before writing the migration.
The INSERT uses ON CONFLICT (code) DO UPDATE, so it is idempotent and the
original 26 rows now carry the exact same ICU-sourced metadata as the
other 132 — one consistent source for all 158, not "26 hand-typed + 132
generated." Crypto was never in scope — ISO 4217/ICU's currency list
never included it, so nothing had to be filtered out for that reason
specifically.

11. ASSET SCHEMA
--------------------
public.asset_types (code PK, display_name, created_at) — seeded: vehicle,
  property, business_interest, financial_investment, equipment,
  inventory, collectible, other. RLS enabled, permissive SELECT-only
  policy (public reference data, same pattern as currencies/money
  categories).
public.assets (id, user_id, asset_type FK, name, description, currency_code
  FK, acquired_at, is_archived, created_at, updated_at) — no stored
  balance/value column. currency_code immutable once basis/valuation
  history exists (enforce_asset_currency_immutable(), same mechanism as
  cash_buckets).
public.asset_basis_events (id, asset_id FK, user_id, basis_event_type
  CHECK in (initial_basis, capital_improvement, basis_reduction), amount
  numeric(20,6) signed, currency_code FK, occurred_at, description,
  created_at) — append-only; current basis = sum(amount).
public.asset_valuations (id, asset_id FK, user_id, valuation_type CHECK
  in (estimated_current_value, quick_sale_estimate, target_value), value
  numeric(20,6) positive, currency_code FK, valued_at, source, note,
  created_at) — append-only; latest row per (asset_id, valuation_type) is
  current.
Full column-level detail and every constraint/trigger/comment is in the
migration file, the canonical source.

12. ASSET TYPE STRATEGY
----------------------------
A controlled-vocabulary reference table (asset_types), not a bare
CHECK-only enum scattered through the schema and not an arbitrary
client-supplied string — same pattern already proven by
money_received_categories/money_spending_categories. Extending the
supported type list later is a migration that inserts a row, not a
schema change. Deliberately generic: no vehicle-specific, property-
specific, or any single-subtype columns anywhere. Receivables are
explicitly not forced into this list this phase — they get their own
dedicated domain shortly, per the brief.

13. COST-BASIS STRATEGY
----------------------------
Chosen: (B) an append-only basis-event history table
(asset_basis_events), not (A) a mutable field on assets or a bare
overwrite-in-place column. Signed amounts, same convention as
cash_movements: initial_basis/capital_improvement positive,
basis_reduction negative (enforced by a trigger, not client discipline).
Current basis is always sum(amount) per asset
(asset_current_basis()), never a stored/overwritten column. This shape is
deliberately the same one that will later carry a real asset-purchase
workflow, capital improvements, vehicle-repair capitalization, and
partial disposal without requiring the table to be redesigned — each of
those becomes another basis_event_type value and another row, not a
schema migration for the core mechanism.

14. VALUATION-HISTORY STRATEGY
------------------------------------
Append-only (asset_valuations), three structurally distinct
valuation_type values (estimated_current_value, quick_sale_estimate,
target_value) — never collapsed into one "value" column. A correction is
a new row with a newer valued_at, never an edit to an existing row (no
UPDATE grant or policy exists on this table for anyone). Latest row per
(asset_id, valuation_type) is the authoritative current value for that
type.

15. CURRENT-VALUE READ MODEL
----------------------------------
asset_latest_valuations() (DISTINCT ON per asset_id+valuation_type,
ordered by valued_at desc, created_at desc) and the combined
asset_summary() (one row per asset with cost_basis,
estimated_current_value, quick_sale_estimate, target_value, and
latest_valued_at, via LEFT JOIN LATERAL per valuation type) are the sole
authoritative "what is this asset worth right now" calculations — SQL
functions, SECURITY INVOKER, never re-derived per screen. A known
Supabase type-generator limitation: these columns are generated as
non-nullable string even though Postgres genuinely returns NULL for an
asset with no basis/valuation of a given type; corrected in
lib/domain/assets/repository.ts's mapping layer (documented inline), so
the rest of the application sees the honest string | null shape.

16. QUICK-SALE MODEL
-------------------------
Optional, never fabricated, never auto-derived from target_value or
estimated_current_value. Absent a recorded quick_sale_estimate,
asset_summary() returns null for that field (mapped to "Not set" at the
UI layer) — tested explicitly (section 22). lib/domain/assets/
liquidity.ts's getPotentialLiquidity() uses it as the sole liquidity
evidence when present, returning {status: "not_calculated"} otherwise —
no invented haircut off any other value.

17. TARGET-VALUE MODEL
---------------------------
Aspirational figure, structurally separate from estimated_current_value
and never returned in its place — tested explicitly (section 22).
Excluded from asset_native_currency_totals() (section 18) and therefore
from the future Net Worth calculation that will consume it
(FINANCIAL_DOMAIN_MODEL.md §20).

18. MULTI-CURRENCY ASSET MODEL
------------------------------------
asset_native_currency_totals() sums only the latest
estimated_current_value per asset, grouped by currency_code, excluding
archived assets — never target_value, never quick_sale_estimate, never
across currencies (verified: separate NGN and USD totals in the same
test run, never merged into one figure). Reuses the exact
{currencyCode, amount}[] shape money_currency_totals() returns, so the
one shared convertToReportingCurrency() (lib/domain/currency/
conversion.ts, relocated this phase) accepts Assets' totals without any
translation — verified directly: calling it with Assets' totals and no
supplied rate returns {status: "not_calculated", missingRates: ["USD"]},
proving reuse rather than a parallel implementation.

19. EXACT-DECIMAL STRATEGY
-------------------------------
Identical discipline to Money, reused rather than reinvented:
numeric(20,6) for both asset_basis_events.amount and
asset_valuations.value (no REAL/DOUBLE PRECISION anywhere). A trigger
(prepare_asset_basis_event/prepare_asset_valuation) rejects any
amount/value with more fractional precision than its currency's
decimal_exponent allows — tested explicitly for JPY (0-decimal,
fractional valuation rejected). Read functions cast every amount to text
in their RETURNS TABLE shape, for the same PostgREST-numeric-as-JSON-
number reason documented for Money. decimal.js remains the one
arbitrary-precision library in the codebase — not reintroduced or
duplicated for Assets.

20. RLS POLICIES
---------------------
asset_types: SELECT-only, permissive, to authenticated.
assets: SELECT/INSERT/UPDATE scoped to auth.uid() = user_id; UPDATE grant
  columns (asset_type, name, description, currency_code, is_archived) —
  excludes user_id; no DELETE grant/policy.
asset_basis_events: SELECT/INSERT to authenticated; INSERT policy
  requires auth.uid() = user_id AND an EXISTS check that the referenced
  asset belongs to auth.uid(); no UPDATE, no DELETE.
asset_valuations: identical shape to asset_basis_events.
Nothing granted to anon anywhere in this domain.

21. CROSS-TENANT REFERENCE PROTECTIONS
--------------------------------------------
Same pattern proven in Money (docs/security/SECURITY_AND_RLS_
PRINCIPLES.md §13), reapplied and reconfirmed here: asset_basis_events'
and asset_valuations' INSERT policies check both the row's own user_id
AND an EXISTS(asset owned by auth.uid()) for the foreign reference — a
user cannot satisfy the first by claiming their own user_id while
pointing asset_id at someone else's asset. Additionally, record_asset_
valuation()/record_asset_basis_event() (section 27) independently
re-validate asset ownership in PL/pgSQL before ever attempting the
insert, so the protection exists at two independent layers (RPC-level
explicit check, and RLS-policy-level EXISTS check reached by either the
RPC or a hypothetical raw insert) — both were exercised directly by the
adversarial suite (section 22), not just one or the other.
