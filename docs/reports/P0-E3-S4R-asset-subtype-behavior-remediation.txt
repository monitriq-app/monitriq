P0-E3-S4R — GENERIC ASSET DOMAIN: SUBTYPE BEHAVIOR REMEDIATION
================================================================

STATUS: COMPLETE.

1. ROOT CAUSE
P0-E3-S4 added `assets.status_code` (the vehicle operational lifecycle:
awaiting_repair -> repairing -> ready_to_list -> listed ->
offer_received -> under_negotiation) directly onto the GENERIC `assets`
table. The column's CHECK constraint restricted its VALUE vocabulary
(`status_code is null or status_code in (...)`) but placed NO
restriction on which asset TYPE could hold a non-null value. The shared
`AssetActionSheet` then rendered the status selector and a "Record a
repair / improvement cost" form UNCONDITIONALLY for every asset — it
never branched on `asset.assetType` at all (confirmed by direct source
inspection before any change was made). `AssetCard` and
`PotentialLiquiditySection` likewise displayed the status chip for every
type. The repository's `updateAsset()` passed `patch.statusCode` straight
through to the database with no validation. Net effect, exactly as
manual QA found: a "Stocks" (financial_investment) asset could both
display and actually receive "Ready to List," "Repairing," etc. This was
not a cosmetic bug — the database itself would accept the mutation, so
the false state was persisted, not just rendered.

2. GENERIC VS. SUBTYPE BOUNDARY
Documented as a new architecture section, `docs/architecture/
FINANCIAL_DOMAIN_MODEL.md` §44. Generic asset data (name, type, currency,
description, cost basis, current/quick-sale/target valuation, valuation
history, archive state) is universal — the schema makes no per-type
distinction, so every type gets it from the same tables/RPCs. Subtype
capability is a real, canonical behavior that only applies to some
types, and per this remediation's own new standing rule, any such
capability must now be enforced at three independent layers that all
agree: database (CHECK constraint), repository (thrown domain error,
independent of what the database would do), and UI (a single centralized
capability read, never a scattered `if (asset.type === ...)`).

3. EXISTING VEHICLE LEAKAGE FOUND
- `AssetActionSheet`: the "Status" `<Select>` (vehicle lifecycle) and the
  "Record a repair / improvement cost" form both rendered for every
  asset type with zero conditional logic.
- `AssetCard`: the status chip rendered for every type (showing "Status
  not set" for non-vehicle types, which at least wasn't false, but
  implied a status COULD eventually be set — misleading by omission of
  the real constraint).
- `PotentialLiquiditySection`: same status-chip issue as `AssetCard`.
- Database: `assets.status_code`'s CHECK constrained values, not types —
  any asset type could structurally hold a vehicle status.
- Repository: `updateAsset()` had no validation logic for `statusCode`
  at all.
No other vehicle-specific leakage (garage language, offer language,
resale language) was found outside `AssetActionSheet`'s own status/repair
controls and the `ASSET_STATUS_OPTIONS` vocabulary itself, which is
correctly vehicle-only content, not leakage.

4. CAPABILITY MODEL INTRODUCED
New file `lib/domain/assets/capabilities.ts`, exporting
`AssetCapabilities` (typed interface) and `assetCapabilities(assetType)`
(pure function, one centralized source). Two real fields, matching only
capabilities that are actually canonically implemented today:
- `supportsVehicleStatus: boolean` — true only for `vehicle`.
- `supportsCapitalImprovement: boolean` +
  `capitalImprovementCopy: {title, description, submitLabel} | null` —
  true for every type except `financial_investment` (explicitly
  withheld — no canonical "contribution" operation exists yet), with
  subtype-appropriate wording (vehicle: "repair / improvement"; property:
  "capital improvement"; equipment: "additional capital cost";
  business_interest: "additional capital invested"; inventory/
  collectible/other: "additional cost").
`supportsReceivableRecovery`, `supportsInvestmentContribution`,
`supportsSale`, `supportsOffers`, `supportsIncomeTracking`, and
`supportsDebtLinkage` were deliberately NOT modeled — none has a real
canonical operation behind it today, and a capability flag that always
reads `false` would be dead code pretending to be a real boundary, per
the brief's own "do not create fake capability merely because it may
exist in the future."

5. DATABASE ENFORCEMENT
New migration `supabase/migrations/
20260930090000_restrict_asset_status_to_vehicle.sql`. Local Docker
(`supabase_db_Monatriq`) was queried directly before writing it (`select
asset_type, status_code, count(*) from assets where status_code is not
null group by asset_type, status_code`) and returned ZERO rows — no
existing invalid data to protect locally (local fixtures are cleaned up
by each test run's own teardown). The migration still includes an
unconditional, idempotent defensive cleanup UPDATE (clears `status_code`
only, never `asset_type`/name/currency/basis/valuation) ahead of the
constraint, so it remains safe to apply later to any environment —
including Monatriq Dev, NOT pushed this pass — without a separate manual
audit first. Adds a new table-level CHECK,
`assets_status_code_requires_vehicle`: `status_code is null or
asset_type = 'vehicle'`, additive alongside the original P0-E3-S4
column-level enum CHECK (Postgres allows multiple CHECK constraints on
one column; both must hold).

6. REPOSITORY ENFORCEMENT
`lib/domain/assets/repository.ts`'s `updateAsset()` signature changed
from `(client, assetId, patch)` to `(client, assetId, currentAssetType,
patch)` — `currentAssetType` is a required parameter, not optional,
specifically so the invariant can never be silently skipped. Before
building the update payload, it checks: if `patch.statusCode` is being
set to a non-null value and `assetCapabilities(currentAssetType).
supportsVehicleStatus` is false, it throws `Error('Asset type "..." does
not support the vehicle lifecycle status.')` — independent of whatever
the database would separately reject. Every real call site
(`AssetActionSheet`) already had the asset's own type in scope (it always
holds the full `AssetSummary` it's mutating), so this was a
zero-extra-fetch, signature-only change. All other call sites across the
codebase (both production and test) were found via grep and updated:
`components/assets/AssetActionSheet.tsx` (2 call sites),
`supabase/tests/assets/run.ts` (8 call sites, several new),
`supabase/tests/home-readiness/run.ts` (1 call site, an unrelated
archive-toggle test using a vehicle fixture).

7. ASSETACTIONSHEET COMPOSITION CHANGES
Rebuilt around `const capabilities = assetCapabilities(asset.assetType)`,
computed once per render. The Status `<Select>` block now renders only
`if (capabilities.supportsVehicleStatus)`. The capital-cost form now
renders only `if (capabilities.supportsCapitalImprovement &&
capabilities.capitalImprovementCopy)`, with its title/description/submit
label all read from `capabilities.capitalImprovementCopy` rather than
hardcoded vehicle text. The generic valuation-update form and the
archive toggle are unconditional, matching their status as genuinely
generic capabilities. Both `updateAsset()` call sites now pass
`asset.assetType` as the new required parameter.

8. VEHICLE BEHAVIOR
Unchanged in substance, verified explicitly: a vehicle asset can still
set and clear all 6 lifecycle statuses (tested individually — see §18),
and still gets the capital-cost form with its original "Record a repair
/ improvement cost" wording (`capabilities.capitalImprovementCopy.title
=== "Record a repair / improvement cost"`, asserted directly).

9. FINANCIAL INVESTMENT BEHAVIOR
`assetCapabilities("financial_investment")` returns
`supportsVehicleStatus: false`, `supportsCapitalImprovement: false`,
`capitalImprovementCopy: null` — verified by a dedicated test. In
`AssetActionSheet`, this means NEITHER the status selector NOR any
capital-cost form renders for a Financial Investment; it is left with
exactly: valuation update (current value / quick-sale / target — all
real, generic, already-canonical), and archive. No "Buy more," "Sell
shares," "Dividend," "Broker," "Ticker," "ROI," or "Market price" concept
was invented — none of those exist in the domain, and this remediation's
scope is removing false behavior, not building a brokerage system.

10. PROPERTY BEHAVIOR

copy title "Record a capital improvement" (verified to contain no

consistent with the P0-E3-S4 report's own prior finding on Property.

11. EQUIPMENT BEHAVIOR

12. BUSINESS INTEREST BEHAVIOR
