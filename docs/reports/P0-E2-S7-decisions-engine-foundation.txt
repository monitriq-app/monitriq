9. DECISION SCHEMA
------------------------------------------------------------------------
`decisions` (id, user_id, decision_type_code, name, description,
linked_asset_id, linked_liability_id, status, timestamps). `status`
(active/closed/archived) is lifecycle only; the user's actual conclusion
lives entirely separately in `decision_choices` — the two are never
collapsed into one field. `linked_asset_id`/`linked_liability_id`
identify the Decision's subject "where applicable," shared by every
scenario under it, cross-tenant-validated via both RLS policy EXISTS
checks and the create_decision() RPC's own explicit lookups. Neither
link is type-enforced by a CHECK constraint — deliberately, so "Other"
stays flexible and the link is a UI/product concern, not a database
invariant.

10. DECISION-TYPE STRATEGY
------------------------------------------------------------------------
`decision_types` is a public, extensible registry (buy_asset,
sell_asset, repair_improve_asset, business_investment,
large_personal_purchase, use_savings, take_debt, pay_down_debt,
start_new_venture, other) — purely descriptive labels, the same
"registry vs. math" decoupling already established for
goal_types/liability_types. The registry never drives calculation logic
directly; `evaluate_decision_scenario()` branches on `decision_type_code`
only for a small number of type-specific derived figures (projected
profit/loss for sell_asset, basis-after-improvement for
repair_improve_asset, hypothetical outstanding for pay_down_debt).

11. SCENARIO ARCHITECTURE
------------------------------------------------------------------------
`decision_scenarios` (one or more per Decision, user-named, one scenario
is a fully valid decision on its own) carries its own `currency_code`
(fixed at creation) and optional `source_bucket_id`/`destination_
bucket_id` (must match the scenario's currency exactly, trigger-
enforced, cross-tenant-validated). Scenario comparison is presented by
evaluating each scenario under one Decision independently and showing
them side by side — no SQL-level "compare" function, no ranking.

12. INPUT/ASSUMPTION ARCHITECTURE
------------------------------------------------------------------------
Neither of the two anti-patterns the phase brief warned against: not a
giant per-decision-type column explosion, not a JSONB/EAV bag of
authoritative numbers. `decision_scenarios` has a moderate set of
strongly-typed numeric(20,6) columns, each with ONE clear economic role
reused BY NAME across every decision type that needs it:
  cash_required           -- buy_asset (purchase price), repair_improve_
                              asset (repair cost), business_investment/
                              start_new_venture (investment amount),
                              large_personal_purchase/use_savings (amount)
  acquisition_costs       -- buy_asset only
  gross_proceeds/proceeds_costs -- sell_asset (sale price/selling costs),
                              take_debt (proposed principal/fees deducted)
  debt_principal_payment/debt_interest_payment/debt_fee_payment
                          -- pay_down_debt only, mirroring Liabilities'
                              own three-component vocabulary exactly
  interest_rate/term_months/monthly_payment_assumption/collateral_note
                          -- take_debt only, recorded not computed from
  expected_value_assumption      -- buy_asset, repair_improve_asset,
                                     business_investment, start_new_venture
  expected_future_sale_value/capitalization_classification
                          -- repair_improve_asset only
  sale_date_assumption    -- sell_asset only
  holding_period_months   -- generic timing assumption
`total_cash_required`/`net_proceeds` are DERIVED at evaluation time,
never stored — a scenario simply populates whichever columns apply;
unused columns stay null and contribute nothing. JSONB is used ONLY for
the immutable evaluation-snapshot audit trail, never as an authoritative
arithmetic source.

13. FACTS VS ASSUMPTIONS VS DERIVED VALUES
------------------------------------------------------------------------
Kept structurally distinct at both the SQL return shape and the
TypeScript type level, with explicit section comments in both. Facts
(linked_asset_cost_basis, linked_asset_latest_value, linked_liability_
outstanding_principal, source/destination_bucket_balance) are read LIVE
from asset_summary()/liability_outstanding_principal()/cash_movements on
every call — never copied into a scenario's own columns. Assumptions
(cash_required, gross_proceeds, expected_value_assumption, ...) are
echoed back exactly as entered — never auto-substituted; verified
explicitly that a sell-asset scenario with no gross_proceeds entered
reports net_proceeds=null rather than silently using the asset's
target_value or quick_sale_estimate. Derived values (total_cash_
required, net_proceeds, net_immediate_cash_delta, projected_gross_
profit_loss, hypothetical_liability_outstanding_after, basis_after_
capitalized_improvement, the whole Safe-to-Deploy before/after block)
are computed fresh every evaluation, never stored, and null (never a
fabricated zero) whenever a required input is missing.

14. CASH-IMPACT MODEL
------------------------------------------------------------------------
A scenario may describe an outflow, an inflow, or neither — never
assumed. `evaluate_decision_scenario()` determines ONE effective bucket
and signed delta per evaluation: source-bucket-only scenarios use a
negative delta (cash_required, possibly netted against proceeds if
source and destination are the same bucket); destination-bucket-only
scenarios use a positive delta (net_proceeds); a scenario naming both a
genuinely different source and destination bucket has its source
bucket's outflow evaluated as the primary concern, with the destination
bucket's own balance still shown as a fact (documented scope limitation,
see §39).

15. SAFE-TO-DEPLOY INTEGRATION
------------------------------------------------------------------------
The central architectural move this phase: P0-E2-S6A's evaluate_
proposed_cash_use() only ever modeled a SPEND (a positive amount,
subtracted). Decisions needed to model an INFLOW too, and the brief
explicitly forbade forking the formula. The fix: the shared rule-
relationship logic was extracted into a new sign-agnostic function,
evaluate_hypothetical_bucket_liquidity(bucket_id, delta), which accepts
any sign and internally calls safe_to_deploy_by_currency() twice (real
state, then with the delta applied) — exactly S6A's "one calculation
model" discipline, extended one layer up. evaluate_proposed_cash_use()
became a thin wrapper over it (negating a positive spend before
calling), with its public signature and return shape completely
unchanged — verified by the full, unmodified P0-E2-S6/S6A test suite
(155 assertions) continuing to pass against the refactor.
evaluate_decision_scenario() calls the same shared function directly for
every liquidity/rule-conflict figure it returns.

16. ASSET-DECISION BEHAVIOR
------------------------------------------------------------------------
Sell asset: facts from asset_summary() (cost basis, latest value, quick-
sale estimate, target value); net_proceeds and projected_gross_profit_
loss = net_proceeds - cost_basis are derived from the user's OWN gross_
proceeds/proceeds_costs assumptions, never auto-filled from target_value
or quick_sale_estimate (verified explicitly). The asset itself is never
archived, sold, or basis-adjusted by evaluating or saving a scenario
(verified explicitly, including a direct cost-basis re-check after
saving). Buy asset: no Asset row is ever created (verified explicitly).
Repair/improve asset: capitalization_classification is an explicit,
user-chosen field — Monatriq never decides automatically whether a
repair capitalizes; basis_after_capitalized_improvement is a projected
preview only, computed exclusively when classification='capital_
improvement', and the real asset basis is never mutated (verified
explicitly, including a paired 'expense'-classified scenario confirming
no projection is shown).

17. LIABILITY-DECISION BEHAVIOR
------------------------------------------------------------------------
Take debt: no Liability row is ever created by evaluating or saving a
take-debt scenario (verified explicitly); interest_rate/term_months/
monthly_payment_assumption are recorded assumptions only, no
amortization schedule is computed. Pay down debt: linked_liability_
outstanding_principal comes live from liability_outstanding_principal()
— the exact function Liabilities' own read models use; hypothetical_
liability_outstanding_after = outstanding - debt_principal_payment is a
pure projection; evaluating or saving a scenario never calls
record_debt_payment() or otherwise changes the liability's real
outstanding principal (verified explicitly: the liability's real balance
is re-read after saving and confirmed unchanged).

18. GENERIC/BUSINESS DECISION BEHAVIOR
------------------------------------------------------------------------
Business investment / start new venture: since no dedicated Businesses
domain exists yet, neither type fabricates a business valuation or
entity — only the proposed cash outflow and its liquidity/rule effects
are evaluated like any other outflow scenario, with expected_value_
assumption shown plainly as a user assumption, never claimed as a
resulting market value (verified explicitly: creating and evaluating a
business_investment scenario creates no new table row beyond the
scenario itself, and moves no real cash). Large personal purchase / use
savings: evaluated purely as a cash requirement against Safe to Deploy
and protected-fund rules, with zero moral framing. Other: a restrained
generic scenario using the same typed columns as every other type — not
an arbitrary untyped escape hatch.

19. MULTI-CURRENCY BEHAVIOR
------------------------------------------------------------------------
Each scenario's currency_code is fixed at creation; linked buckets must
match it exactly (trigger-enforced, same discipline as every prior
domain). Different scenarios under one Decision may be denominated in
different currencies and are evaluated entirely independently — never
blended. A reporting-currency conversion of one scenario's net
immediate cash delta (convertScenarioNetDeltaToReportingCurrency() in
lib/domain/decisions/aggregate.ts) requires an explicit rate, reusing
convertToReportingCurrency() — the same function Rules' own reporting
aggregation uses — and returns not_calculated when a rate is missing.
JPY (0-decimal) and KWD (3-decimal) precision are both enforced via the
same BEFORE INSERT/UPDATE trigger pattern established throughout.

20. SCENARIO-COMPARISON MODEL
------------------------------------------------------------------------
Multiple scenarios under one Decision are evaluated independently and
presented side by side by the application layer — there is no SQL-level
"compare" function and no ranking anywhere. Verified explicitly with two
structurally distinct repair-vs-sell scenarios: their factual cash
requirements differ (comparable), and neither evaluation result object
contains a rank/score/winner/recommendation/isBest/isRecommended field
at any layer — checked via `Object.keys()` on the actual returned
object, not merely by inspecting values.

21. EVALUATION-SNAPSHOT MODEL
------------------------------------------------------------------------
evaluate_decision_scenario() is a pure, un-persisted read. save_
decision_scenario_evaluation() calls that same read and freezes the
complete result (to_jsonb() of the record) into decision_scenario_
evaluations — append-only, no UPDATE/DELETE grant exists on the table at
all (verified: a direct update is rejected by grant absence, not merely
a policy). The snapshot preserves the facts/assumptions/derived
distinction and every rule-relationship field (verified by inspecting
the saved JSON's own keys).

22. RE-EVALUATION/HISTORY MODEL
------------------------------------------------------------------------
Re-evaluating and saving again APPENDS a new snapshot rather than
overwriting the prior one — verified explicitly: two saves on the same
scenario produce two distinct, both independently readable rows, with
the history function returning the most recent first. "Current
evaluation" is always the latest by evaluated_at — no is_current flag,
the same derive-don't-duplicate discipline every prior domain follows.

23. USER-CHOICE MODEL
------------------------------------------------------------------------
decision_choices is append-only: proceed/wait/decline/keep_reviewing,
current choice always the latest row by created_at. Recording a Wait
choice after an earlier Proceed preserves BOTH in history (verified
explicitly, with decision_summary() correctly reporting the latest as
current). Choice is deliberately separate from decisions.status
(lifecycle) — never overloaded into one field.

24. PROCEED-DOES-NOT-EXECUTE PROOF
------------------------------------------------------------------------
record_decision_choice() inserts exactly one row into decision_choices
and touches nothing else — there is no code path in it capable of
writing to another table. Verified explicitly across all four choices
(proceed, wait, decline, keep_reviewing): bucket balances, Asset
summaries, and Liability summaries are all confirmed byte-identical
before and after each choice is recorded, with the proceed case
additionally checked against all three simultaneously.

25. DECISION-JOURNAL MODEL
------------------------------------------------------------------------
decision_choices (§23) and decision_scenario_evaluations (§21-22)
together let the application reconstruct what was considered, what
assumptions were used, what each evaluation showed at the time, and how
the user's own conclusion evolved — without a second, duplicate
transaction system. An archived Decision remains fully readable,
including its complete choice history (verified explicitly). Actual-
outcome (expected vs. actual) comparison is an explicit, clean extension
point, not implemented this phase — no fake actual results exist
anywhere.

26. MISSING-INFORMATION BEHAVIOR
------------------------------------------------------------------------
evaluate_decision_scenario() tracks a missing_information text array
(no_bucket_linked, no_amount_specified, no_asset_linked, no_liability_
linked) built incrementally, never filling a genuinely missing value
with a fabricated 0. Verified explicitly: a scenario with no bucket and
no amount entered reports total_cash_required=null, net_proceeds=null,
both missing-information flags present, and overall_status=
'insufficient_information'.

27. EXACT-DECIMAL STRATEGY
------------------------------------------------------------------------
All scenario amount columns are numeric(20,6) (interest_rate is
numeric(7,4), the same plain-metadata treatment Liabilities established).
No real/double precision anywhere. decision_scenarios' BEFORE INSERT/
UPDATE trigger enforces every non-null amount's precision against the
scenario's currency decimal_exponent — a fractional JPY cash_required
and a 4-decimal KWD update were both tested explicitly and rejected; a
3-decimal KWD amount was tested and accepted. All read functions cast
monetary amounts to ::text. Exact-decimal correctness was verified with
non-round EUR inputs (6123.45/123.45) producing an exact 6000.00 net
proceeds and 1000.00 projected profit — no float drift.

28. RLS POLICIES
------------------------------------------------------------------------
Every new table (decision_types, decisions, decision_scenarios,
decision_choices, decision_scenario_evaluations) has RLS enabled
immediately, deny-by-default, no policy granting anonymous access. All
use auth.uid() = user_id ownership policies plus EXISTS-based cross-
tenant checks wherever a row references another table.

29. CROSS-DOMAIN REFERENCE PROTECTION
------------------------------------------------------------------------
decisions -> assets/liabilities (EXISTS check on both INSERT and UPDATE
policies, plus the create_decision() RPC's own explicit lookups).
decision_scenarios -> decisions/cash_buckets (EXISTS checks on both
source and destination bucket references simultaneously — the same
two-reference pattern established for goal_allocation_events).
decision_choices -> decisions (EXISTS check). decision_scenario_
evaluations -> decision_scenarios (EXISTS check). Every evaluation/
choice-recording RPC re-verifies ownership of every referenced row
inside the function body, never trusting RLS alone.

40. ASSUMPTIONS
------------------------------------------------------------------------
- linked_asset_id/linked_liability_id belong on decisions, not decision_
  scenarios — a deliberate, documented architectural choice (the subject
  of consideration is shared by every scenario under one Decision), not
  a literal reading of the brief's "scenario -> asset" reference-
  protection wording; cross-tenant protection is tested at the layer the
  reference actually exists (§29).
- A scenario naming two genuinely different buckets (source and
  destination) has only its source bucket's outflow modeled through the
  hypothetical Safe-to-Deploy chain this phase — a deliberate,
  documented scope limitation rather than an attempt to extend the
  shared formula to a second simultaneous override, since none of the
  ten canonical decision types require it.
- The remote "Monatriq Dev" project identity (confirmed in P0-E2-S3)
  remains valid and did not need re-confirmation this phase.
