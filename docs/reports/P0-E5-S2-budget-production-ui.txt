P0-E5-S2 — BUDGET PRODUCTION UI + QUICK ADD INTEGRATION
================================================================

PHASE
P0-E5-S2 — Budget production UI and Quick Add integration.

STATUS
COMPLETE, with two caveats: (1) the remote migration could not be confirmed (see MIGRATION STATUS); (2) one manual browser review is requested. Nothing committed or pushed.

OBJECTIVE
Let a non-financial user create a monthly budget, plan amounts per category, see spent / left / over, see unbudgeted spending and upcoming commitments, and update it easily. No new Budget engine.

VISUAL STRATEGY
No new design. Existing tokens, cards, bottom-sheet pattern (same wrapper as AddCommitmentSheet), MoreDetails disclosure, 48px targets, theme tokens (no Budget-specific theme). Progress rail is a plain bar with a text label ("65% used", "Over budget", "Planned zero"), so meaning never relies on color alone. No scores, gauges, advice.

QUICK ADD CHANGES
Modal heading "Quick Add", subtitle "What would you like to do?", centered modal preserved. Two groups: RECORD (Money Received, Money Spent, Move Money, Asset / Investment) and PLAN (Budget, Goal, Commitment). Compact 48px rows. Plan group is available even with no cash bucket (Record still shows the "add a cash bucket" note). Structure lives in components/quick-add/options.ts. Nav "+" aria-label is now "Quick Add". Also fixed a pre-existing invalid nesting (a link inside a button) for the Asset row.
- Budget -> /budget?quick=1: opens the current budget if one exists; otherwise the empty state with the Create sheet open. Never auto-creates.
- Goal -> /goals#add-goal (anchor added to the existing Add Goal section). The Goals screen is still the foundation-level UI; only the anchor was added.
- Commitment -> /rules?add=commitment: opens the existing AddCommitmentSheet (defaultAdding prop). No duplicate obligation flow.
- Asset -> /assets#add-asset (unchanged existing route).

BUDGET EMPTY STATE
"No budget for this month yet. Create a simple plan for what you want to spend." + Create Budget. No seeded amounts, no 50/30/20, no invented income.

CREATION FLOW
Sheet: Month (last month, this month, next six), Currency (all supported currencies; profile preferred currency preselected but changeable), optional Expected money in (planning only, labelled "not recorded income"). Duplicate month+currency gives a friendly message. After creating, the user lands on the new budget.

SUMMARY
Planned / Spent / Left (or "Over by") from budget_summary, with the month and currency shown. Before anything is planned: Planned "Not set yet", Left "—" (never a fake zero). Expected money in is shown as planning context only.

CATEGORY UX
One compact card per budgeted category: name, Left/Over by, rail, Planned, Spent, status text. Tap opens a sheet: Set / Change budget amount, Remove budget amount. Explicit zero is accepted and shown as "Planned zero"; removing returns the category to Not budgeted. Add category lists only canonical Money spending categories not yet allocated. Amount validation is a string check against the currency's decimal places; no Number/parseFloat.

UNBUDGETED SPENDING
Own section listing spending in categories with no allocation, with "Add to budget" per row. The budget is never changed automatically.

COMMITMENTS
From budget_upcoming_commitments (real obligations only): "Known payments still coming this month. They are not counted as spent." Calm empty state with an "Add commitment" link. Due dates use deterministic formatting (see OPEN ISSUES).

MULTI-CURRENCY
Each budget is one currency. Currency pills switch between same-month budgets; month arrows move between existing budgets. No cross-currency total anywhere. Verified with NGN and USD budgets.

MONEY INTEGRATION
Budget has no transaction entry. Money Spent, and voiding, change Budget on the next server render via the canonical read model (tested: spend 10,000 raises Spent by 10,000; void removes it). Budget Remaining is not labelled or styled as Available Cash or Safe to Deploy, and Safe to Deploy is omitted.

STATUS HANDLING
Closed: read-only banner + Reopen. Archived: hidden from default selection and navigation, reachable by id, banner + Restore. Close/Archive live under "Close or archive this budget" (MoreDetails).

HOME INTEGRATION
Compact "This Month's Budget" section (BudgetHomeCard): per current-month currency budget, Spent and Left/Over by, linking to it; or a simple "Plan this month's spending" link when none exist. Failure-isolated (Home still renders if Budget fails). No Home redesign.

1. QUICK ADD HORIZONTAL OVERFLOW
Measured before changing anything (headless Chrome, local scratch build): at every width (320-430) the hub's scroll container had scrollWidth exceeding clientWidth by exactly 4px (e.g. 258 vs 254 at 320), while no element box extended past the dialog and the page itself did not scroll. Root cause: the Close button used a `before:absolute before:-inset-1` pseudo-element to enlarge its hit area; that pseudo-element sits at the right edge of the hub's `overflow-y-auto` container (which makes overflow-x auto), so it overflowed it by 4px and produced the scrollbar. It was also the only target below 48px (40px).
Fix (structural, one file, components/quick-add/QuickAddProvider.tsx): the Close control is now a real 48x48 button (h-12 w-12, shrink-0) containing the 40px visible circle, so the hit area is genuine and nothing extends outside its container. The header row also got gap-2 and min-w-0 on the title block so text can wrap. overflow-x was NOT hidden.
Re-measured after the fix at 320, 360, 375, 393, 412, 430 in Light and Dark: scrollWidth == clientWidth at all 12 combinations (no horizontal scroll), no page-level overflow, no clipped text, minimum interactive height 48px, RECORD/PLAN grouping and centered modal unchanged. Screenshots reviewed at 320 (light) and 360 (dark): chevrons fully visible; longer descriptions wrap to two lines inside their rows (visible at 320 for Asset / Budget / Commitment).
Manual verification widths requested (320, 360, 393, 430): all covered, both themes, by scripted browser measurement plus screenshots. A human eyeball on a real device is still recommended.
