9. PROFILE SCHEMA
--------------------
public.profiles:
  id                    uuid PRIMARY KEY REFERENCES auth.users(id)
                        ON DELETE CASCADE
  first_name            text, nullable, 1-100 chars if present
  preferred_name        text, nullable, 1-100 chars if present
  preferred_currency    text, nullable, must match ^[A-Z]{3}$ if present
  timezone              text, nullable, must be a real IANA zone name if
                        present (validated via Postgres's own tz engine,
                        not a regex)
  onboarding_completed  boolean NOT NULL, GENERATED ALWAYS AS
                        (first_name IS NOT NULL AND preferred_currency IS
                        NOT NULL AND timezone IS NOT NULL) STORED
  created_at            timestamptz NOT NULL DEFAULT now()
  updated_at            timestamptz NOT NULL DEFAULT now(), trigger-
                        maintained

Deviation from the phase brief's suggested shape, deliberately and
documented in the migration file: no separate surrogate id + unique
user_id column. profiles.id IS auth.users.id. This is a genuine 1:1
extension table, so the identity IS the auth user's id — every RLS policy
collapses to `auth.uid() = id`, no join, no extra unique index needed.

preferred_currency and timezone are nullable with no default, deliberately
diverging from the brief's illustrative "NOT NULL" — see section 20
(assumptions) for why: a row is created at signup, before the user has
told us anything, and a default would mean fabricating one (explicitly
forbidden by docs/product/PRODUCT_DEFINITION.md and
docs/architecture/FINANCIAL_DOMAIN_MODEL.md).

10. PROFILE LIFECYCLE STRATEGY
-----------------------------------
Chosen: (B) a SECURITY DEFINER trigger (handle_new_user) on auth.users
AFTER INSERT, over (A) a server-side post-signup call and (C) a
client-callable initialization RPC.

Evaluated failure modes:
  (A) — a dropped client request between "auth user created" and "profile
        insert call" permanently orphans the user with no profile row,
        and every future read has to defensively handle that.
  (C) — same orphaned-user failure mode (still depends on the client
        actually calling it), and additionally needs its own INSERT
        policy on profiles — exactly the "insert a profile for another
        user" attack surface this design wants to close entirely.
  (B) — runs inside Supabase Auth's own transaction; cannot be skipped by
        a dropped client request. Idempotency: ON CONFLICT (id) DO
        NOTHING. Maintainability: one small, fully commented function; no
        dynamic SQL.

Why SECURITY DEFINER is necessary here and its blast radius: the trigger
fires as `supabase_auth_admin`, which has no grants on public.profiles —
without SECURITY DEFINER the insert fails for every signup. search_path is
pinned (`set search_path = pg_catalog, public`). The function performs
exactly one fixed-shape INSERT with no dynamic SQL and no client-supplied
values beyond NEW.id (the just-created auth user's own id, not
attacker-influenceable beyond signing up as themselves). EXECUTE is
revoked from public/anon/authenticated — nothing can invoke it directly;
it only ever fires via the trigger mechanism. Verified structurally: there
is no INSERT policy AND no INSERT grant to authenticated on profiles at
all, so "insert a profile for another user" and "insert a forged-id
profile" are not just policy-rejected, they are not a reachable code path
for any normal client at all. Confirmed by the isolation suite (section
13/14, tests 6 and 7).

11. RLS POLICIES
--------------------
RLS enabled immediately at table creation. Exactly two policies exist,
nothing broader:

  profiles_select_own  (SELECT, to authenticated)
    USING (auth.uid() = id)

  profiles_update_own  (UPDATE, to authenticated)
    USING (auth.uid() = id) WITH CHECK (auth.uid() = id)

No INSERT policy, no DELETE policy — deny-by-default extends to
capabilities nobody asked for yet, not just to other users' rows.

Grants (independent of, and necessary alongside, the policies above —
Postgres RLS restricts which rows, GRANT restricts which operations at
all):
  REVOKE ALL on public.profiles FROM anon, authenticated  (explicit,
    defense in depth — supabase/config.toml's auto_expose_new_tables
    default already means nothing is auto-granted, but this doesn't rely
    on that default)
  GRANT SELECT on public.profiles TO authenticated
  GRANT UPDATE (first_name, preferred_name, preferred_currency, timezone)
    on public.profiles TO authenticated  — column-level, deliberately
    excluding id, created_at, and onboarding_completed. A payload that
    includes id (an ownership-reassignment attempt) or created_at fails
    with "permission denied for column" before RLS's WITH CHECK is even
    evaluated. updated_at is excluded too; it's trigger-maintained.
  No INSERT or DELETE grant to anyone except via the SECURITY DEFINER
    trigger (section 10), which doesn't go through GRANT/RLS at all.

12. ISOLATION TEST ARCHITECTURE
------------------------------------
supabase/tests/rls/ — a small dependency-free harness (no test framework
added; not justified at this phase's scope), run via plain `node`
(Node 24's native TypeScript execution, no build step, no ts-node/tsx
dependency):
  env.ts       — loads required env vars; HARD REFUSES to run unless
                 NEXT_PUBLIC_SUPABASE_URL looks like 127.0.0.1/localhost.
                 This suite creates and deletes real auth.users rows with
                 a service-role key, so this guard is a safety-critical
                 line, not a formality — it is what stands between this
                 harness and accidentally running fixture create/delete
                 against a real linked project (e.g. "Nemryn").
  fixtures.ts  — creates two independent users via the Auth admin API
                 (service-role client), signs each in through the normal
                 anon-key + password flow to get a session-bound client
                 (the actual path the browser SDK uses — this is what
                 makes the suite prove database enforcement, not just
                 call the admin API and assume RLS applies), plus a
                 no-session anonymous client. Purges any leftover
                 @monatriq.test fixture users from a previous crashed run
                 before creating new ones (idempotent/repeatable), and
                 deletes its own fixtures in a `finally` block.
  assert.ts    — expectSuccess / expectFilteredToEmpty (RLS silently
                 excluded a row — no error, zero rows, the actual Postgres
                 RLS behavior for USING-clause exclusion) / expectDenied
                 (a hard database rejection — missing grant, WITH CHECK
                 violation, or a raised constraint).
  run.ts       — the suite itself, 20 assertions (section 13/14).

Everything user-facing goes through the real anon-key + PostgREST path
(supabase-js against the local REST API), which is the same mechanism a
browser client uses and the same mechanism a "direct REST request" attack
would use — this is database enforcement being tested, not application
code hiding rows.

13. ADVERSARIAL TESTS EXECUTED
------------------------------------
Mapped to the phase brief's required list 1-10, all present:
 1. User A can read User A's profile.
 2. User A cannot read User B's profile.
 3. User B cannot read User A's profile.
 4. User A can update User A's profile.
 5. User A cannot update User B's profile (targeting B's id in a filter).
 6. User A cannot insert a profile owned by User B (forged id).
 7. User A cannot reassign their own profile's ownership to User B
    (attempted `UPDATE ... SET id = <B's id>`).
 8. Anonymous access cannot read authenticated-user profiles.
 9. Anonymous access cannot mutate profiles (tested INSERT, UPDATE, AND
    DELETE separately).
10. Direct request for another user's UUID (`.eq("id", userB.id)`, both
    as a list query and as `.maybeSingle()`) returns nothing, not an
    error — no existence leak either.

Additional adversarial/structural cases beyond the required 10:
 - User A cannot insert a second row for themselves either (no INSERT
   grant exists at all, not even for your own id).
 - User A cannot delete their own profile, or User B's (no DELETE grant
   or policy exists for anyone).
 - Signup creates exactly one profile row with the correct id and
   onboarding_completed = false (proves the SECURITY DEFINER trigger's
   privilege boundary — it does exactly one fixed thing, nothing more).
 - After every attack above, User B's row is confirmed unmutated
   (first_name still null) — a final integrity check that nothing leaked
   through silently.
 - Domain-correctness (not adversarial, but validates the real
   integration): completing onboarding via the actual updateProfile()
   repository function flips onboarding_completed to true and persists
   all fields; an invalid IANA timezone is rejected; a malformed currency
   code is rejected.

20. ASSUMPTIONS
--------------------
- profiles.id = auth.users.id (no separate surrogate key) — the brief
  explicitly invited this: "using the profile primary key itself as the
  auth user ID may be preferable... choose deliberately and document
  why." Documented in the migration header and
  docs/security/SECURITY_AND_RLS_PRINCIPLES.md §10.
- preferred_currency/timezone nullable with no default, diverging from
  the brief's illustrative NOT NULL — resolved in favor of the brief's
  own, more specific "Default Profile Values" section, which explicitly
  forbids a fabricated default.
- onboarding_completed implemented as a stored generated column rather
  than a hand-set boolean — not explicitly requested, chosen because it
  cannot drift from the fields it summarizes and makes "required currency
  once onboarding is complete" (a constraint the brief names as an
  example) true by construction.
- update-password, forgot-password, and the rest of the P0-E1-S2 auth
  shell were left untouched; only the boundary between "authenticated"
  and "authenticated + onboarded" was added.
- Docker Desktop was started (a reversible, non-destructive local action)
  specifically to obtain real local validation rather than leaving RLS
  testing unexecuted — judged to serve the phase's explicit preference for
  local testability over relying on remote/dashboard validation.
- The curated ~25-entry currency list is a starting set, not a product
  decision about which currencies V1 ultimately supports.
