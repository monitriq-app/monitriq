9. FINANCIAL-RULE ARCHITECTURE
------------------------------------------------------------------------
`financial_rules` (id, user_id, rule_type, currency_code, status,
created_at, updated_at) is the identity/slot for one (user, rule_type,
currency) configuration. `rule_type` is a CHECK-constrained, extensible
list — only `'minimum_cash_floor'` this phase — so future rule types
(maximum_capital_per_asset, maximum_debt_payment_ratio,
maximum_active_ventures, ...) can be added without restructuring the
table. A unique index on (user_id, rule_type, currency_code) means each
currency has at most one identity row per rule type ever; deactivating
(status='inactive') preserves it rather than deleting it, and
reactivating (`create_financial_rule()`) reuses the same identity row.

10. RULE-HISTORY/VERSION STRATEGY
------------------------------------------------------------------------
`financial_rule_versions` is append-only: a new row is a new version of
the threshold — old thresholds are never overwritten. The current
threshold for a rule is always its latest version (by effective_at). This
is the exact same "identity + append-only versioned value" pattern
P0-E2-S5's `goals`/`goal_target_history` established, reused rather than
reinvented — proving the pattern generalizes. Verified explicitly:
recording three successive threshold changes (2000 -> 2500 -> 3000, the
middle one via reactivation) preserves all three as separately-readable
history rows.

11. MINIMUM-CASH-FLOOR MODEL
------------------------------------------------------------------------
A minimum cash floor is an absolute, per-currency retained-cash
threshold — never a single cross-currency figure. It is purely a
calculation constraint: `create_financial_rule()`/
`record_financial_rule_version()` never move or lock cash, never touch
`financial_events`/`cash_movements`. An explicit zero floor
(`threshold_value = 0`) is structurally distinct from "no rule
configured" — a currency with no active rule row (with at least one
version) reports `not_configured`; a currency with an active rule whose
latest version is exactly 0 reports `calculated` with a real zero
requirement. Verified explicitly with a dedicated NZD scenario: cash
existed with no rule (not_configured), then an explicit zero floor was
set (calculated, safe_to_deploy = full liquid cash).

12. OBLIGATION MODEL
------------------------------------------------------------------------
`obligations` (id, user_id, name, description, currency_code, amount,
due_date, status, is_protected, funding_goal_id, created_at, updated_at)
— a plain user-owned record, never inferred or scraped from Money
activity. Status is restrained to active/paid/cancelled/archived; there
is no stored urgency label. "Overdue" is always derived
(`obligation_summary()`: status='active' and due_date < today in the
caller's profile timezone) — no `is_overdue` column exists anywhere to
drift out of sync. Marking an obligation "paid" is organizational
metadata only: `updateObligation()` never creates a
`financial_events`/`cash_movements` row (verified explicitly); a future
phase may add an optional link to a real Money event, but none is
fabricated this phase. `is_protected` defaults to `false` at the database
level on every insert path — an explicit, visible, user-editable choice,
never auto-true.

13. GOAL-LINKED OBLIGATION MODEL
------------------------------------------------------------------------
An obligation may optionally set `funding_goal_id`. `prepare_obligation()`
(a BEFORE INSERT OR UPDATE trigger) validates three things on every
write, not just at creation: the goal belongs to the same user, the
obligation's currency exactly equals the goal's currency, and the goal's
`measurement_type` is one that actually accepts monetary funding
(`cash_target`/`debt_balance_target` — the same two types Goals itself
allows allocation into). The `obligations_insert_own`/
`obligations_update_own` RLS policies independently re-check the
cross-tenant EXISTS condition, so even a raw insert bypassing
`create_obligation()` cannot link to another user's goal. Verified
explicitly: currency mismatch rejected, cross-tenant goal link rejected.

14. OBLIGATION COVERAGE / DOUBLE-COUNT PREVENTION
------------------------------------------------------------------------
`rules_uncovered_protected_obligations()` aggregates ALL protected,
active, linked obligations PER GOAL first (grouping by
(currency_code, funding_goal_id)) before comparing the combined total
against that goal's backed protected allocation
(`goal_backed_protected_allocation()`) — only the amount by which the
AGGREGATE exceeds the backing becomes an additional retained-cash
requirement. This specifically prevents two obligations sharing one goal
from each independently claiming the goal's full backing. Verified with
a worked CHF scenario: a Tuition Goal backed at 8,000, first a 6,000
linked obligation (fully covered, uncovered=0, no double-count against
the goal's own 8,000 protected_goal_cash), then a second 5,000 linked
obligation added (combined 11,000 vs backing 8,000 -> uncovered
correctly reports 3,000, not 0 or 5,000). An obligation with no
`funding_goal_id` has no goal backing to draw on at all — its full
amount is always uncovered.

15. BACKED-PROTECTED-CASH MODEL
------------------------------------------------------------------------
A goal allocation can nominally exceed the real cash left in its bucket
after later spending (the allocation-shortfall concept established in
P0-E2-S5). `protected_goal_cash` (the currency-level Safe-to-Deploy term)
never uses the nominal allocation: per bucket, backed = LEAST(protected
allocation total in that bucket, bucket's actual balance), summed across
the user's buckets in that currency. Protected allocations have first
claim on real cash ahead of non-protected allocations in the same
bucket — a deliberate, documented precedence choice (protection signals
the higher-priority claim). When splitting a bucket's backed total back
down to INDIVIDUAL competing protected goals (needed only for
per-goal obligation-coverage math, not the currency-level formula),
`goal_backed_protected_allocation()` uses a pro-rata split by each goal's
share of the bucket's total protected allocation — a deterministic,
priority-free rule chosen specifically per the brief's "avoid inventing
priority where possible" instruction, rather than an arbitrary ordering.
Verified against the phase brief's own worked example exactly: two
protected goals (4,000 + 3,000 = 7,000 nominal) sharing one bucket funded
to 7,000, then spent down to 5,000 real balance via ordinary Money
activity -> backed protected cash for the currency correctly reports
5,000, never the imaginary 7,000.

16. ALLOCATION-SHORTFALL INTEGRATION
------------------------------------------------------------------------
The Goals domain's `goal_bucket_shortfalls()` (P0-E2-S5) is reused
directly on `/rules` via the existing `ShortfallBanner` component —
unmodified, confirming it was genuinely domain-agnostic. Within the
Safe-to-Deploy formula itself, shortfall integration is implicit in the
backed-protected-cash calculation (§15): a bucket's shortfall is exactly
why its contribution to `protected_goal_cash` is capped at its real
balance rather than the nominal allocation.

17. SAFE-TO-DEPLOY FORMULA
------------------------------------------------------------------------
`safe_to_deploy_by_currency()` computes, per currency, exactly the
specified formula:
  protected_commitments   = protected_goal_cash + uncovered_protected_obligations
  required_retained_cash  = MAX(minimum_cash_floor, protected_commitments)
  safe_to_deploy           = MAX(liquid_cash - required_retained_cash, 0)
  retained_deficit         = MAX(required_retained_cash - liquid_cash, 0)
MAX, never SUM — verified explicitly with the brief's own worked example
(cash 10,000, protected goal cash 4,000, uncovered obligations 1,000,
floor 3,000 -> protected_commitments 5,000, required_retained MAX(3000,
5000)=5000, safe_to_deploy 5,000 — not 8,000, which a SUM would
incorrectly produce) and its floor-dominant variant (floor 7,000 ->
required_retained 7,000, safe_to_deploy 3,000). `safe_to_deploy` always
clamps at zero; `retained_deficit` is exposed separately and is never
hidden by the clamp (verified: cash 3,000 against required 5,000 reports
both `safe_to_deploy=0` and `retained_deficit=2,000` simultaneously).

18. NOT-CONFIGURED BEHAVIOR
------------------------------------------------------------------------
A currency with cash but no active minimum_cash_floor rule reports
`status='not_configured'`; every floor-dependent field
(minimumCashFloor, requiredRetainedCash, safeToDeploy, retainedDeficit)
is null — never a fabricated zero floor. `liquidCash`/`protectedGoalCash`/
`uncoveredProtectedObligations` remain populated regardless (they don't
depend on a floor existing), so the UI can still show honest partial
information. Verified explicitly across the whole suite: multiple
currencies coexist in one `safe_to_deploy_by_currency()` result set with
some `calculated` and others `not_configured` simultaneously.

19. RETAINED-DEFICIT MODEL
------------------------------------------------------------------------
Computed inline as part of `safe_to_deploy_by_currency()`'s single query
(§17) — `MAX(required_retained_cash - liquid_cash, 0)` — rather than a
separate function, since it shares every input the main formula already
computes. Present as its own column, always populated when a currency is
`calculated` (0 when there is no deficit), so the UI can surface it
distinctly from the deployable figure without re-deriving it.

20. MULTI-CURRENCY BEHAVIOR
------------------------------------------------------------------------
Every rule, obligation, and Safe-to-Deploy row is scoped to one explicit
currency — never a blended cross-currency figure. A user may configure
entirely independent floors across as many currencies as they hold cash
in (verified: separate USD/NGN/EUR/GBP/NZD/CAD/JPY/SGD/CHF/SEK/HKD/DKK/
KWD/CZK/PLN configurations coexist independently across this suite's own
test data, each with correct, uncontaminated figures). A reporting-
currency consolidated figure
(`aggregateSafeToDeployToReportingCurrency()` in
`lib/domain/rules/aggregate.ts`) is available only when every relevant
currency's Safe to Deploy is itself `calculated` AND every required FX
rate is supplied, reusing `convertToReportingCurrency()` — no second FX
implementation. Verified explicitly: an unconfigured currency present in
the input set forces `not_calculated` even when a rate would have been
available for it; a missing rate alone (all currencies calculated) also
forces `not_calculated`; a complete rate set produces an exact converted
total.

21. PROPOSED-CASH-USE EVALUATOR
------------------------------------------------------------------------
`evaluate_proposed_cash_use(bucket_id, amount)` returns factual before/
after figures (current/post-use balance, current/post-use protected
allocation shortfall, currency Safe to Deploy before/after, retained
deficit after) plus three neutral relationship labels — never
approve/reject/recommend semantics (verified by an explicit test against
an advisory-vocabulary blocklist). It is a pure read: calling it writes
nothing. Documented scope limitation: the "after" recomputation reflects
the proposed bucket's own contribution to protected backing and currency
liquid cash, but does not recursively re-derive obligation coverage that
depends on OTHER buckets funding the same goal — a genuine second-order
effect deliberately left out per the brief's explicit "do not turn this
into a reservation system" instruction. Any bucket ID is explicitly
verified to belong to `auth.uid()` before any figure is computed or
returned (verified: cross-tenant bucket evaluation rejected; anonymous
invocation rejected via missing EXECUTE grant).

22. RULE CONFLICT SEMANTICS
------------------------------------------------------------------------
Five statuses used across the domain: `aligned`, `attention`, `conflict`,
`not_configured`, `insufficient_information` — describing a relationship,
never deciding for the user. `minimum_cash_floor_status`: `conflict` when
the post-use liquid cash would fall below the configured floor,
`attention` when Safe to Deploy would decrease without an outright floor
breach, `aligned` otherwise. `protected_goal_status`: `conflict` when the
proposed use would newly impair or worsen this bucket's own protected
allocation shortfall. `protected_obligation_status`: `attention` when the
proposed use reduces this bucket's protected backing AND the bucket funds
a goal with a linked protected obligation (the coarse, honest signal
described in §21's scope limitation). All three report
`not_configured`/`insufficient_information` when the currency has no
active floor rule, since a full evaluation isn't meaningfully possible
without it.

23. OVERRIDE AUDIT MODEL
------------------------------------------------------------------------
`cash_use_overrides` (id, user_id, bucket_id, currency_code,
proposed_amount, conflicts_snapshot jsonb, safe_to_deploy_before,
safe_to_deploy_after, context_type, note, created_at). Recording one
(`record_cash_use_override()`) calls `evaluate_proposed_cash_use()` for a
fresh snapshot at that moment, freezes its conflict labels/figures into
the immutable `conflicts_snapshot` JSONB column, and stores the before/
after Safe-to-Deploy figures as real NUMERIC columns (not parsed from the
JSON for any further arithmetic — the JSONB is a frozen record, never an
authoritative amount store). No `UPDATE`/`DELETE` grant exists on this
table at all — append-only and immutable under every normal user flow,
verified by a direct-update rejection test (denied by grant absence, not
merely a policy). Recording an override never creates a
`financial_events`/`cash_movements` row, never alters a goal, never
alters an obligation — verified explicitly for all three. Cross-tenant
override recording against another user's bucket is rejected.

24. EXACT-DECIMAL STRATEGY
------------------------------------------------------------------------
All threshold/amount/snapshot columns are `numeric(20,6)`. No
`real`/`double precision` anywhere. `financial_rule_versions.threshold_
value` and `obligations.amount` both enforce their currency's
`decimal_exponent` via BEFORE INSERT (and, for obligations, BEFORE
UPDATE too) triggers — a fractional JPY threshold and a 4-decimal KWD
obligation amount were both tested explicitly and rejected; a 3-decimal
KWD amount was tested and accepted. All read functions cast monetary
amounts to `::text`. A real bug was found and fixed this phase (see §35):
bare-integer `0` fallbacks in `coalesce`/`greatest`/`least` lose NUMERIC's
display scale once cast to text (`"0"` instead of `"0.000000"`) — every
such fallback across the new migration is now explicitly cast
`0::numeric(20, 6)`.

25. RLS POLICIES
------------------------------------------------------------------------
Every new table (`financial_rules`, `financial_rule_versions`,
`obligations`, `cash_use_overrides`) has RLS enabled immediately,
deny-by-default, no policy granting anonymous access. All use
`auth.uid() = user_id` ownership policies plus EXISTS-based cross-tenant
checks wherever a row references another table.

26. CROSS-DOMAIN REFERENCE PROTECTIONS
------------------------------------------------------------------------
`financial_rule_versions` -> `financial_rules` (EXISTS check). `obligations`
-> `goals` via `funding_goal_id` (EXISTS check on both INSERT and UPDATE
policies, plus trigger-level currency/measurement-type validation —
tested with three angles: currency mismatch, cross-tenant goal, and via

RPC accepting a bucket ID explicitly re-verifies ownership via
`auth.uid()` inside the function body before computing or returning
anything — never trusting RLS alone as the only check, consistent with
every prior domain's discipline.
