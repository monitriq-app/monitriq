Real-device testing after this phase's approval found iPhone Chrome not offered install guidance, while iPhone Safari was. The user's own real-device retest after S1R1 still did not see the guidance, confirming the simulated test was insufficient proof. See P0-E6-S1R2 immediately below.

P0-E6-S1R3 — CROSS-PLATFORM INSTALL PROMPT
-------------------------------------------
Previous discoverability problem: the only install entry point was the profile menu's "Install Monitriq" (InstallSection) — correct but easy to never find, since nothing on the app's main surface hinted it existed. This phase adds a primary, top-of-shell install invitation while keeping the profile entry as a secondary fallback, and removes the P0-E6-S1R2 temporary diagnostics.

ANDROID BEHAVIOUR: unchanged capture of the real `beforeinstallprompt` (still only in lib/pwa/install-store.ts / PwaRuntime.tsx — no second listener was added). The new top banner (components/pwa/InstallBanner.tsx) shows once that event has been seen; its Install button calls the SAME deferred prompt's real `prompt()`, inspects `userChoice`, and always clears the deferred state afterwards (`setDeferredInstallPrompt(null)`) — identical to the existing profile-menu flow, not a second implementation. Accepted -> hidden for the rest of the session via `markInstallPromptInstalled()` (also called from PwaRuntime's existing `appinstalled` handler, so an install completed through the browser's own UI hides the banner too). Declined -> `dismissInstallPromptForSession()`, the exact same function "Not now" calls, so a decline gets the normal 7-day reminder delay, not silence forever or an immediate re-offer. No Android UI is ever shown without a real captured prompt.

IPHONE/IPAD BEHAVIOUR: the SAME banner (not a separate Android-only vs iOS-only component) renders on any iOS device via the existing device-based detectPlatform()/installOffer() (lib/pwa/install.ts, untouched — reused exactly, not reimplemented; verified again this phase for Safari, Chrome/CriOS, Firefox/FxiOS and Edge/EdgiOS on iPhone, plus Chrome on iPad). Its Install button opens InstallInstructionsSheet.tsx — an accessible modal (role="dialog", aria-modal, labelled title, focus-on-open, Escape-to-close, backdrop-click-to-close) with the three approved numbered steps and a "Got it" button. iOS has no programmatic install API, so this is guidance only — nothing claims to install anything. Closing the sheet does not dismiss the banner (the user may not have finished the steps yet); only "Not now", a real install, or reaching standalone hides it.

DISMISSAL POLICY: lib/pwa/install-prompt-store.ts holds two layers — an in-memory "dismissed this tab session" flag (so navigating between pages, which does not remount the banner since AppShell is a persistent Next.js layout, never re-shows something just closed) and a `localStorage` timestamp under the key `monitriq_install_prompt_dismissed_at` (the ONLY value ever written there — a bare epoch millisecond number) for a 7-day reminder across visits. The delay is one centralized, easy-to-change constant, `INSTALL_PROMPT_REMINDER_MS` in lib/pwa/install-prompt.ts (`INSTALL_PROMPT_REMINDER_DAYS = 7`). "Not now" and a declined native prompt both call the identical dismissal function.

ELIGIBILITY: `shouldShowInstallPrompt()` (lib/pwa/install-prompt.ts, pure and unit-tested) combines `installOffer()`'s result (which already encodes standalone, in-app-webview and platform eligibility — no second detector was built) with the session/persisted dismissal state and a `ready` flag that only becomes true ~1.5s after mount (`INSTALL_PROMPT_SHOW_DELAY_MS`), so the banner never flashes in before the shell has settled.

ONBOARDING SUPPRESSION: InstallBanner is mounted exactly once, inside AppShell (components/layout/AppShell.tsx) — the shared layout for every `(app)` route. `/onboarding`, `/login`, `/signup`, `/link-invalid` and the auth confirmation route do not render AppShell at all, so the banner cannot structurally appear before onboarding is complete; a brand-new user's first sight of it is on Home, after signup -> confirm -> onboarding -> Home, exactly as specified. Verified: an eligible user landing on `/onboarding` (with a captured `beforeinstallprompt`) sees no banner.

PROFILE FALLBACK: components/pwa/InstallSection.tsx is unchanged in behaviour (same copy, same offer logic) and, critically, never reads the banner's dismissal state at all — dismissing the top banner never hides the profile entry, and the profile entry has no "Not now" of its own; it is the stable, always-available fallback the phase asked for. Both InstallSection and InstallBanner now read platform/standalone/in-app-browser from one shared function, `snapshotInstallEnv()` (lib/pwa/install-env.ts), so they can never drift into disagreeing with each other.

UPDATE VS INSTALL PRECEDENCE: PwaRuntime.tsx now also calls the shared `useInstallPromptVisible()` hook (components/pwa/useInstallPromptVisible.ts) that InstallBanner renders from, and folds its `visible` result into the existing update-banner condition: `showUpdate = waiting !== null && !dismissed && !installPromptVisible`. This is the only change to PwaRuntime — registration, update detection, `SKIP_WAITING`, and the offline notice are all untouched. The two banners can now never stack; installation takes precedence for a browser user who hasn't installed yet.

INSTRUCTION SHEET: see IPHONE/IPAD BEHAVIOUR above; copy matches the brief exactly (three steps, footer, "Got it").

STANDALONE HANDLING: no new detector — `isStandalone()` (lib/pwa/install.ts) is reused exactly as before via `installOffer()`; both the banner and the profile entry disappear together once standalone, verified in browser with a `navigator.standalone` override.

PRIVACY: the only storage write anywhere in this phase's code is the one `localStorage.setItem(INSTALL_PROMPT_DISMISS_KEY, String(Date.now()))` call in lib/pwa/install-prompt-store.ts. A dedicated test scans every file under lib/pwa and components/pwa and fails if `localStorage`/`sessionStorage` appears anywhere else, and fails if anything resembling a balance, account, budget figure, session, token, email or `user_id` appears near the dismissal code. No IndexedDB anywhere (unchanged from P0-E6-S1).

9. SERVICE-WORKER ARCHITECTURE
------------------------------
  - Source: lib/pwa/service-worker.ts builds the worker string; app/sw.js/route.ts serves it (force-static) at /sw.js with Cache-Control "no-cache, no-store, must-revalidate", Service-Worker-Allowed "/", nosniff, application/javascript.
  - Registered by components/pwa/PwaRuntime.tsx, PRODUCTION ONLY, scope "/", updateViaCache "none". Loaded through next/dynamic (ssr:false) so it is out of the initial bundle and adds no dependency.

  - install: precache /offline only. NO skipWaiting.
  - activate: delete every older "monitriq-" cache, clients.claim().
  - message SKIP_WAITING: skipWaiting (sent only when the user presses Refresh).

10. EXACT CACHE POLICY
----------------------
  Request                                        Handling
  ---------------------------------------------  ------------------------------------------------
  Navigations (all pages, incl. /home, /money,   NETWORK ONLY. Never stored. On failure serve the
    /budget, /goals, ... and public pages)         precached /offline page (or a 503 text fallback)
  /_next/static/*  (immutable hashed assets)     Cache-first, only ok + same-origin "basic" responses
  /brand/*         (public logos/icons)          Stale-while-revalidate, only ok + basic responses
  /offline                                       Precached at install
  Cross-origin (Supabase, fonts, anything)       NOT intercepted
  Non-GET (POST/PUT/DELETE, auth, server actions) NOT intercepted
  RSC / data fetches (?_rsc, non-navigate)       NOT intercepted
  /api/*, /auth/callback                         NOT intercepted
  Cookies, tokens, Authorization headers         Never read, stored or forwarded by the worker
Browser QA after logging in and visiting /money /budget /goals /home: Cache Storage held exactly {/offline, /brand/*, /_next/static/*}; no HTML, no RSC, no API. localStorage, sessionStorage and IndexedDB were empty.

11. FINANCIAL-DATA CACHING CONFIRMATION
---------------------------------------
Question: is any authenticated financial data cached broadly? ANSWER: NO.
  - Not cached: Supabase authenticated API responses, profile, Money, Budget, Goals, Debts, Money Owed, Assets, Spending Check results, auth/session endpoints, cookies, tokens, any personalised server response, any page HTML.
  - Cached: only the public offline page, content-hashed build assets, and public brand images — none contain user data.
  - No IndexedDB / localStorage / sessionStorage / Cache writes of user data anywhere in lib/pwa, components/pwa, app/offline, app/sw.js (tested by scanning code with comments stripped).
  - PWA code imports no financial-domain or Supabase code (tested).
  - The worker source contains no env, secrets, storage APIs (tested).
Automated proof is behavioural, not textual: the real worker is executed in a node:vm sandbox with a fake network and Cache Storage; authenticated navigations to eleven routes return fresh network content and leave the cache holding only /offline; nine categories of private traffic are asserted to be un-intercepted with zero worker network calls.
Caveat (public only): statically prerendered public pages (/login, /offline, /) carry Next's "s-maxage=31536000" header. That is a shared/CDN directive on public, non-personalised HTML that Vercel purges on each deploy; it is not a browser cache and no authenticated route carries it. Documented for awareness.

13. UPDATE STRATEGY
-------------------
  - New Vercel deployment -> new worker bytes -> browser installs it in the background and it WAITS (no skipWaiting on install).
  - The app shows a status banner: "An update is available." with Later / Refresh (48px buttons), positioned above the bottom nav (safe-area aware).
  - Refresh posts SKIP_WAITING, the new worker activates, the page reloads on controllerchange (3s fallback). Old caches are deleted on activate.
  - Never reloads automatically, so a form is never interrupted. Later dismisses for the session.
  - Update checks run on register, when the tab becomes visible, and hourly.
  - No cache-forever: the worker file is no-store; static assets are content-hashed and version-scoped.
Browser-verified with two real builds (aaa111-dpl_A then bbb222-dpl_B) under one open, signed-in page with the account menu open: banner appeared, page instance and open menu untouched, Later dismissed it, after reload + Refresh the served/active version became bbb222-dpl_B, old caches were removed, user stayed signed in.

26. RISKS
---------
  - A future edit that widens the worker's allowlist (e.g. caching pages) would put private data on device. Mitigation: behavioural tests fail if anything outside /offline, /_next/static, /brand is cached or if navigations/private requests are touched.
  - Update prompt relies on browser update checks (visibility + hourly); users on a stale tab see the banner on next check. The old worker keeps serving only public assets meanwhile; an old worker never serves stale data.
  - iOS PWA storage/cookie behaviour is Apple-controlled; a session may need re-login after long inactivity (Supabase behaviour, not changed).
  - Icon appearance in circle/squircle masks should be eyeballed on device.
