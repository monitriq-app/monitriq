3. EXISTING PWA AUDIT
---------------------
Found before starting:
  - app/manifest.ts existed but was minimal (name, colours, icons); it was extended, not duplicated.
  - Approved logo/icon set already in public/brand (192, 512, 1024, favicons). Only two derivatives were missing.
  - No service worker, no offline page, no install UI, no viewport-fit=cover, no Apple web-app metadata.
  - App shell (header, drawer, bottom nav, profile menu), theme tokens, dvh/safe-area padding and the mobile "no permanent scrollbar" CSS already existed and were reused.
  - proxy.ts ran a Supabase session refresh on every non-asset path (needed a narrow exclusion for the worker and offline page).
No PWA library was present. A maintained library (e.g. Serwist) was considered and rejected: the requirement is deliberately narrow (three public path families, no runtime caching of pages), and a ~100-line hand-written worker is easier to audit for "does this ever cache private data" than a generic precache/runtime-caching framework. It is fully covered by executable tests.

9. SERVICE-WORKER ARCHITECTURE
------------------------------
  - Source: lib/pwa/service-worker.ts builds the worker string; app/sw.js/route.ts serves it (force-static) at /sw.js with Cache-Control "no-cache, no-store, must-revalidate", Service-Worker-Allowed "/", nosniff, application/javascript.
  - Registered by components/pwa/PwaRuntime.tsx, PRODUCTION ONLY, scope "/", updateViaCache "none". Loaded through next/dynamic (ssr:false) so it is out of the initial bundle and adds no dependency.
  - Version = VERCEL_GIT_COMMIT_SHA + VERCEL_DEPLOYMENT_ID (else "dev"): every deployment yields different worker bytes, hence a browser update, and new cache names.
  - install: precache /offline only. NO skipWaiting.
  - activate: delete every older "monitriq-" cache, clients.claim().
  - message SKIP_WAITING: skipWaiting (sent only when the user presses Refresh).
  - proxy.ts matcher now also excludes /sw.js and /offline (no Supabase session refresh / Set-Cookie on those two public resources). Nothing else in proxy.ts changed.

10. EXACT CACHE POLICY
----------------------
  Request                                        Handling
  ---------------------------------------------  ------------------------------------------------
  Navigations (all pages, incl. /home, /money,   NETWORK ONLY. Never stored. On failure serve the
    /budget, /goals, ... and public pages)         precached /offline page (or a 503 text fallback)
  /_next/static/*  (immutable hashed assets)     Cache-first, only ok + same-origin "basic" responses
  /brand/*         (public logos/icons)          Stale-while-revalidate, only ok + basic responses
  /offline                                       Precached at install
  Cross-origin (Supabase, fonts, anything)       NOT intercepted
  Non-GET (POST/PUT/DELETE, auth, server actions) NOT intercepted
  RSC / data fetches (?_rsc, non-navigate)       NOT intercepted
  /api/*, /auth/callback                         NOT intercepted
  Cookies, tokens, Authorization headers         Never read, stored or forwarded by the worker
Browser QA after logging in and visiting /money /budget /goals /home: Cache Storage held exactly {/offline, /brand/*, /_next/static/*}; no HTML, no RSC, no API. localStorage, sessionStorage and IndexedDB were empty.

11. FINANCIAL-DATA CACHING CONFIRMATION
---------------------------------------
Question: is any authenticated financial data cached broadly? ANSWER: NO.
  - Not cached: Supabase authenticated API responses, profile, Money, Budget, Goals, Debts, Money Owed, Assets, Spending Check results, auth/session endpoints, cookies, tokens, any personalised server response, any page HTML.
  - Cached: only the public offline page, content-hashed build assets, and public brand images — none contain user data.
  - No IndexedDB / localStorage / sessionStorage / Cache writes of user data anywhere in lib/pwa, components/pwa, app/offline, app/sw.js (tested by scanning code with comments stripped).
  - PWA code imports no financial-domain or Supabase code (tested).
  - The worker source contains no env, secrets, storage APIs (tested).
Automated proof is behavioural, not textual: the real worker is executed in a node:vm sandbox with a fake network and Cache Storage; authenticated navigations to eleven routes return fresh network content and leave the cache holding only /offline; nine categories of private traffic are asserted to be un-intercepted with zero worker network calls.
Caveat (public only): statically prerendered public pages (/login, /offline, /) carry Next's "s-maxage=31536000" header. That is a shared/CDN directive on public, non-personalised HTML that Vercel purges on each deploy; it is not a browser cache and no authenticated route carries it. Documented for awareness.

12. OFFLINE BEHAVIOUR
---------------------
  - Navigating offline shows the branded /offline page at the requested URL: "You're offline. Reconnect to refresh your financial information." plus "Monitriq doesn't store your financial information on this device, so nothing is shown while you're offline." No balances are ever shown from a cache (browser-verified: page contains no amounts).
  - While already on a page, going offline shows a polite live-region banner with the same message; it clears when back online.
  - "Try again" is a plain link to the current URL, so it works even though the offline page's JS chunks may not have loaded offline. (Found and fixed during QA: the first version was a JS button that did nothing until hydration. After the fix, reconnect + Try again returned to /money with live data.)
  - If even the offline page is missing from cache, the worker returns a 503 with the same honest sentence.

13. UPDATE STRATEGY
-------------------
  - New Vercel deployment -> new worker bytes -> browser installs it in the background and it WAITS (no skipWaiting on install).
  - The app shows a status banner: "An update is available." with Later / Refresh (48px buttons), positioned above the bottom nav (safe-area aware).
  - Refresh posts SKIP_WAITING, the new worker activates, the page reloads on controllerchange (3s fallback). Old caches are deleted on activate.
  - Never reloads automatically, so a form is never interrupted. Later dismisses for the session.
  - Update checks run on register, when the tab becomes visible, and hourly.
  - No cache-forever: the worker file is no-store; static assets are content-hashed and version-scoped.
Browser-verified with two real builds (aaa111-dpl_A then bbb222-dpl_B) under one open, signed-in page with the account menu open: banner appeared, page instance and open menu untouched, Later dismissed it, after reload + Refresh the served/active version became bbb222-dpl_B, old caches were removed, user stayed signed in.

26. RISKS
---------
  - A future edit that widens the worker's allowlist (e.g. caching pages) would put private data on device. Mitigation: behavioural tests fail if anything outside /offline, /_next/static, /brand is cached or if navigations/private requests are touched.
  - Update prompt relies on browser update checks (visibility + hourly); users on a stale tab see the banner on next check. The old worker keeps serving only public assets meanwhile; an old worker never serves stale data.
  - iOS PWA storage/cookie behaviour is Apple-controlled; a session may need re-login after long inactivity (Supabase behaviour, not changed).
  - Icon appearance in circle/squircle masks should be eyeballed on device.
