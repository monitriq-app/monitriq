transfer note, the Asset-Sale deferral message) — while its most
valuable, directly reproducible element, the 5-second Undo, IS

8. EXISTING MONEY CAPABILITY AUDIT
--------------------------------------------------------------------------------
Confirmed by reading the domain layer directly, not inferred from the
UI mockups:
- `cash_buckets`: user-owned, one row per bucket, fixed currency once it
  has movements. `createBucket`/`updateBucket`/`listBuckets` — plain
  table access (no amount columns, so no RPC needed).
- `financial_events`/`cash_movements`: the one ledger. `event_type` is
  now a 10-value CHECK constraint (`opening_balance`, `money_received`,
  `money_spent`, `transfer`, `fx_transfer`, `receivable_recovery`,
  `debt_principal_payment`, `debt_interest`, `debt_fee`,
  `loan_proceeds`) — the last five added by the Receivables/Liabilities
  migration, each with its own real, DB-trigger-derived
  `cash_flow_class` (never client-settable).
- Five mutation RPCs: `record_opening_balance`, `record_money_received`,
  `record_money_spent`, `record_transfer` (same-currency only, rejects
  otherwise), `record_fx_transfer` (different-currency only, requires
  BOTH a real source and destination amount from the caller — computes
  and stores an implied `fx_rates` row for record-keeping, source
  `transaction_actual`, but never fetches or applies a market rate
  itself).
- Correction: `voidFinancialEvent` — a plain RLS/column-grant-protected
  UPDATE of `voided_at` (append-only, never a delete). This is Money's
  only supported correction mechanism and is what Quick Add's real Undo
  calls.
- Reads: `money_bucket_balances`, `money_currency_totals`,
  `money_period_summary`/`resolve_period_bounds` (P0-E3-S1A, arbitrary
  explicit `[start, end]` or defaults to the current calendar month in
  the caller's profile timezone), `money_recent_activity`.
- `money_received_categories` (9 seeded: business_income, salary,
  freelance_contract, investment_income, gift, receivable_recovery,
  asset_sale, refund, other) and `money_spending_categories` (14
  seeded, including `debt_payment`) — critically, the `receivable_
  recovery`/`asset_sale`/`debt_payment` ROWS in these lookup tables
  still exist (their `cash_flow_class` is correctly seeded), but the
  REAL, linked workflows for the first and third bypass them entirely
  via their own dedicated `event_type`s — see §25/§27.
- Receivables: `recordRecovery({receivableId, bucketId, amount, ...})`
  — a real, dedicated function; currency is fixed to the receivable's
  own, destination bucket must match.
- Liabilities: `recordDebtPayment({liabilityId, bucketId,
  principalAmount?, interestAmount?, feeAmount?, ...})` — a real,
  dedicated function with the genuine 3-way split the phase brief
  requires.
- Assets: no sale/disposal mutation exists anywhere in
  `lib/domain/assets/repository.ts` — confirmed by reading every
  exported function.
- No existing UI anywhere in the codebase called `recordOpeningBalance`
  before this phase — a genuine gap this phase fills (§19).

12. MONEY PAGE IMPLEMENTATION
--------------------------------------------------------------------------------
`app/(app)/money/page.tsx` is a server component. It resolves the
active period from `?period=` (defaulting to `month`), computes
`[start, end]` via the new `resolveMoneyPeriodRange()` utility (pure
calendar-date arithmetic anchored to the user's real profile timezone —
never a financial calculation), then fetches — in parallel — buckets,
currencies, both category lists, bucket balances, currency totals,
recent activity, the period summary, the weekly buckets, and the
category breakdown, all from Money's own canonical functions. Zero
arithmetic happens in this file or in any component it renders. A
brand-new user (zero active buckets) sees a dedicated setup state
instead of the full dashboard (§18).

--------------------------------------------------------------------------------
13. CASH BUCKETS
--------------------------------------------------------------------------------
`AvailableCashSection` shows every real bucket's name, currency, and
balance (from `money_bucket_balances()`), grouped/totaled per currency
using `money_currency_totals()` — the canonical pre-summed total, never
re-derived client-side (an earlier draft of this component briefly
summed bucket balances with native JS `Number()` arithmetic; caught and
replaced with the real RPC total before this report was written — see
§54). A single currency shows one headline total; multiple currencies
show one line per currency, never combined. The bucket list itself is a
collapsible drawer (client-side `useState` toggle only — no data
re-fetch), matching the reference's own "View N cash buckets" pattern.

--------------------------------------------------------------------------------
14. MONEY SUMMARY
--------------------------------------------------------------------------------
`MoneySummaryCard` shows Money In / Money Out / Net Change per native
currency for the resolved period, read verbatim from
`money_period_summary()`. The reference's "+44.7% surplus" badge — a
NEW ratio (net ÷ cashIn) the domain layer doesn't return — was
deliberately NOT reproduced: computing it in JSX would be exactly the
"arbitrary financial calculation" the phase brief prohibits. Net
Change's own real sign/color already communicates surplus vs. deficit.
Earned Income/Expense are available on the same summary object
(`MoneyPeriodCurrencySummary`) but are not surfaced as their own
headline row on Money (the reference doesn't show them here either);
they remain visible in Home's own "This Month" panel unchanged.

--------------------------------------------------------------------------------
15. CASH-FLOW VISUALIZATION
--------------------------------------------------------------------------------
A NEW canonical read capability, `money_weekly_summary(p_start, p_end)`
— see §46 for the full justification and §9/§10 of the migration file
itself. `CashFlowChart` renders one In/Out bar pair per real week
returned, bar heights scaled (Decimal.js, never a native float) against
the real max value present for that currency — a presentational scaling
transform over already-real numbers, not invented data. Multiple
currencies render as separate chart blocks. An empty period shows an
honest "No cash flow activity" message, never a fabricated flat chart.

--------------------------------------------------------------------------------
16. ACTIVITY
--------------------------------------------------------------------------------
`MoneyActivityList` reads `money_recent_activity()` (fetched with a
higher limit, 30, than the prior foundation screen's 25, to keep the
filtered views meaningfully populated) and renders one contained,
`divide-y`-divided list (correct here — the reference itself divides
this specific list, unlike Home's Capital Distribution rows, which
don't). Each row's title prefers the event's own real `description`,
falling back to an event-type label; the subline shows the real date
plus the real category/event-type context. Transfers get an "Internal
transfer · excluded from In/Out" tag rendered directly on the row —
real, not inferred.

--------------------------------------------------------------------------------
17. FILTERS
--------------------------------------------------------------------------------
All / Received / Spent / Transfers, implemented as a client-side filter
over the already-fetched activity array (no re-fetch, no mutation) using
each item's own real `cashFlowClass`: Received = `income` ∪
`other_inflow` (covers plain Money Received AND real linked Receivable
Recovery/Loan Proceeds); Spent = `expense` ∪ `other_outflow` (covers
plain Money Spent AND real linked Debt Principal/Interest/Fee);
Transfers = `transfer`. `opening_balance` matches neither Received nor
Spent (its own distinct `cash_flow_class`) — it only ever appears under
All, always labeled "Opening Balance," never folded into "Money
Received."

--------------------------------------------------------------------------------
18. EMPTY STATE
--------------------------------------------------------------------------------
Zero active buckets → the full dashboard (summary/chart/breakdown/
activity) is replaced with a short orientation block and the real Add
Cash Balance form directly inline — no fake chart, no fake summary
figure, no seeded bucket name.

19. ADD CASH BALANCE
--------------------------------------------------------------------------------
`AddCashBalanceForm` — the canonical opening-balance entry point this
phase adds (no UI called `recordOpeningBalance` before this phase, per
§8). Lets the user pick an existing (as-yet-unfunded) bucket or create a
brand-new one inline, then records the opening amount via
`recordOpeningBalance`. Never implemented as Money Received. A separate
"Create Cash Bucket" section (the existing, unchanged
`CreateBucketForm`) remains available for creating an empty bucket to
fund later.

--------------------------------------------------------------------------------
20. QUICK ADD ARCHITECTURE
--------------------------------------------------------------------------------
`QuickAddProvider` is mounted once in `AppShell` (server component,
fetches buckets/balances/categories) and wraps `{children}` + the
bottom nav in a React context (`QuickAddContext`: `isOpen`, `view`,
`open`/`close`/`goTo`/`backToHub`). `MobileBottomNav`'s central `+`
(mobile) and a new equivalent button in `DesktopNav` (tablet/desktop,
since the mobile nav is `md:hidden`) both call `open()` — never a
`<Link>` to a generic page. The sheet itself: a `fixed inset-0`
backdrop + a `rounded-t-2xl` bottom sheet (drag-handle bar, safe-area
padding, `max-h-[92vh]` with internal scroll), hosting either the 4-
option hub or the active flow form. Every mutating action goes through
the exact same repository functions used elsewhere in the app — no
client-side table insert, no bypass of any RPC.

--------------------------------------------------------------------------------
21. MONEY RECEIVED
--------------------------------------------------------------------------------
`MoneyReceivedForm`: 7 generic source chips (Business Income, Salary,
Freelance/Contract, Investment Income, Gift, Refund, Other) call
`recordMoneyReceived` directly with the real `categoryCode`. Two
additional chips switch the form's MODE instead of setting a category —
see §25/§26. Fields: amount, source, destination bucket, optional note;
date defaults to now (server-side `occurred_at` default), matching
"manual-first" (no separate date/time picker was added beyond what the
canonical RPC's own default already provides, since the reference's own
date field just reads "Today" — a real default, not an editable value
this phase needed to add UI for; this is disclosed as a scoped-down
simplification, not a rejected reference feature).

--------------------------------------------------------------------------------
22. MONEY SPENT
--------------------------------------------------------------------------------
`MoneySpentForm`: 12 generic category chips (Housing, Food, Transport/
Fuel, Vehicle Repair, Business Expense, Education, Healthcare,
Subscriptions, Family, Entertainment, Travel, Professional Services,
Other) call `recordMoneySpent` directly. "Vehicle Repair" is a plain
expense category like any other — no asset-linking/capitalization logic
was added, because `RecordMoneySpentInput` has no such parameter; adding
cross-domain capitalization behavior here would have been exactly the
kind of architecture work this phase is explicitly forbidden from doing
mid-UI-pass. One additional chip, "Debt Payment," switches mode — see
§27.

--------------------------------------------------------------------------------
23. MOVE MONEY
--------------------------------------------------------------------------------
`MoveMoneyForm`: From/To bucket selects (destination list excludes the
selected source, structurally preventing same-bucket selection before
submit; the RPC itself also rejects it server-side), amount, and — only
when source/destination currencies differ — a second real "amount
received" field, routing to `recordFxTransfer` with both real user-
entered amounts (never an auto-computed conversion). A real inline note
states transfers don't count as income or spending. Fewer than 2 active
buckets → an honest unavailable message, no fabricated destination.

--------------------------------------------------------------------------------
24. ASSET / INVESTMENT BEHAVIOR
--------------------------------------------------------------------------------
Routes directly to `/assets#add-asset` (a one-line anchor `id` added to
the existing, unmodified Assets page section wrapping `AddAssetForm` —
the "very small existing workflow" hook the phase boundary explicitly
permits) and closes the sheet. No second Asset domain, no parallel form,
no fake cash-to-asset transaction was built — cash-purchase linkage
isn't canonically supported yet, so this phase doesn't invent it.

--------------------------------------------------------------------------------
25. RECEIVABLE RECOVERY HANDLING
--------------------------------------------------------------------------------
Selecting the "Receivable Recovery" chip in Money Received switches the
form to a dedicated mode: a live-fetched (client-side, on-demand —
never pre-loaded into `AppShell`'s global fetch) list of the user's own
outstanding receivables, a bucket selector constrained to the
receivable's own currency, amount, and note — submitting via the real
`recordRecovery()` (Receivables domain), which atomically links the cash
increase to that specific receivable's outstanding decrease. The
generic `record_money_received` path (with `categoryCode:
"receivable_recovery"`) is never called from this mode. A user with zero
outstanding receivables sees an honest message + a link to
`/receivables`, never a fabricated entry.

--------------------------------------------------------------------------------
26. ASSET SALE HANDLING
--------------------------------------------------------------------------------
Selecting "Asset Sale" shows an inline, honest deferral message (capital
returned vs. realized gain/loss are distinct concepts Assets doesn't yet
have a dedicated workflow for) with a link to `/assets` — no submit
button, no generic category fallback, no fake accounting semantics.

--------------------------------------------------------------------------------
27. DEBT PAYMENT HANDLING
--------------------------------------------------------------------------------
Selecting the "Debt Payment" chip in Money Spent switches to a dedicated
mode: a live-fetched list of the user's own outstanding debts, a bucket
selector constrained to the debt's currency, and three real separate
fields — Principal / Interest / Fees — submitted via the real
`recordDebtPayment()` (Liabilities domain), preserving the genuine
principal-vs-interest-vs-fee split (principal is cash-out but
net-worth-neutral; interest/fees are a real expense). The generic
`record_money_spent` path is never used for this mode.

--------------------------------------------------------------------------------
28. OPENING BALANCE HANDLING
--------------------------------------------------------------------------------
See §19. `record_opening_balance` only, never `record_money_received`.
Opening-balance events keep their own `cash_flow_class`
(`opening_balance`) throughout — excluded from Money In/Out, from
Earned Income, and from every Quick-Add-filter's Received bucket (§17).

--------------------------------------------------------------------------------
29. UNDO / REVERSAL HANDLING
--------------------------------------------------------------------------------
`SuccessPanel` shows a real 5-second Undo (matching the reference's own
countdown pattern) that calls the exact same `voidFinancialEvent()` used
everywhere else in the app — a genuine, canonically-backed correction
(append-only `voided_at`, never a row delete), not a client-side "undo"
that merely hides the row. After the countdown, the Undo control
disappears — it never continues to imply an action it can no longer
safely offer through this exact one-tap path (the underlying
`voidFinancialEvent` function itself has no time restriction; the 5s
window is a UI restraint matching the reference's own pacing, not a
domain-layer limitation).

--------------------------------------------------------------------------------
30. MULTI-CURRENCY BEHAVIOR
--------------------------------------------------------------------------------
No screen or form in this phase sums two different currencies into one
figure. `AvailableCashSection`/`MoneySummaryCard`/`CashFlowChart`/
`WhereMoneyWentSection`/`CashInBySourceSection` all render one block per
native currency present. `MoveMoneyForm` restricts same-currency
transfers to `recordTransfer` and cross-currency ones to
`recordFxTransfer` with two real user-entered amounts — never a client-
computed conversion. `MoneyReceivedForm`/`MoneySpentForm`'s
receivable/liability-linked modes constrain the bucket selector to the
receivable's/liability's own currency, structurally preventing a
currency-mismatched linked payment.

--------------------------------------------------------------------------------
31. REPORTING-CURRENCY BEHAVIOR
--------------------------------------------------------------------------------
Not touched by this phase. Profile `preferred_currency` is used only as
a display DEFAULT (the pre-selected currency when creating a brand-new
bucket in `AddCashBalanceForm`) — never as an assumed currency for any
existing bucket, and never used to silently convert or blend Money
figures. Reporting-currency conversion (Financial Position's own
mechanism, P0-E3-S1A) is unchanged and untouched.

--------------------------------------------------------------------------------
32. DATE/TIMEZONE BEHAVIOR
--------------------------------------------------------------------------------
`resolveMoneyPeriodRange()` (new, `lib/utils/period-range.ts`) resolves
"today" via `Intl.DateTimeFormat` against the user's real profile
timezone (never the server's or browser's local date), then computes
Week/Month/3M/Year boundaries as plain calendar-date arithmetic — no
financial value is touched. The resolved `[start, end]` is passed
verbatim to `money_period_summary()`/`money_weekly_summary()`/
`money_category_breakdown()`, which perform the real, authoritative,
timezone-aware period-bounded aggregation server-side exactly as
`resolve_period_bounds()` already established in P0-E3-S1A. Quick Add's
own date fields rely on each RPC's own `occurred_at default now()`
rather than a separately-built date/time picker (§21).

--------------------------------------------------------------------------------
33. AUTHENTICATED-USER DYNAMICS
--------------------------------------------------------------------------------
Every read/mutation in this phase resolves ownership from `auth.uid()`
server-side (RLS + the RPCs' own `where user_id = auth.uid()` clauses) —
no client-provided user id or ownership relation is ever trusted. No
component branches on a specific email, name, or UUID. Every list,
total, and label is derived from the currently authenticated user's own
real rows.

--------------------------------------------------------------------------------
34. USER ISOLATION
--------------------------------------------------------------------------------
Verified with real fixtures in `supabase/tests/money/run.ts` (existing
tests, unchanged, plus new ones for the two new RPCs): User A's weekly
buckets/category-breakdown totals never include User B's real amounts;
a dedicated new test funds User B with a deliberately huge gift
(999,999) and asserts User A's own "gift" category total stays below it.
Every pre-existing cross-user adversarial test (bucket UUID guessing,
event/movement ownership reassignment attempts, anonymous access) still
passes unchanged.

--------------------------------------------------------------------------------
35. RLS/SECURITY
--------------------------------------------------------------------------------
Not weakened anywhere. The two new SQL functions are `security invoker`
(RLS applies through them exactly as it does through every table they
touch), `revoke all ... from public, anon` / `grant execute ... to
authenticated` — the identical pattern every other Money RPC uses. No
client-provided `user_id` is accepted anywhere in this phase's new code
(`createClient()`'s own session cookie is the only identity source,
per the established `@supabase/ssr` pattern). A runtime grep for
`service_role`/`SUPABASE_SERVICE` across every file this phase touched
returned zero matches (§52).

--------------------------------------------------------------------------------
36. MOBILE BEHAVIOR
--------------------------------------------------------------------------------
Priority viewport ~390–393px, per the phase brief. Quick Add's sheet:
`max-w-md`, `max-h-[92vh]` with internal `overflow-y-auto`, safe-area
bottom padding, a `rounded-t-2xl` shape matching the reference. Every
form control reuses the established `Input`/`Select` primitives (48px
minimum height, `text-base` on mobile to avoid iOS zoom). The
backdrop's own click handler closes the sheet (`stopPropagation` on the
sheet itself prevents accidental closes while interacting with a form
field).

--------------------------------------------------------------------------------
37. NARROW/FOLD BEHAVIOR
--------------------------------------------------------------------------------
Reasoned, not browser-verified (§53). At 320px, every card/section in
this phase inherits the exact 16px page gutter + 16px card padding
scale P0-E3-S2's gap-audit pass established and verified structurally
for Home; no new fixed-pixel-width element was introduced anywhere in

54. ASSUMPTIONS
--------------------------------------------------------------------------------
1. Category-share percentages in `WhereMoneyWentSection`/
   `CashInBySourceSection` (e.g. "44%") are computed client-side via
   Decimal.js from two already-fetched real totals (a category's own
   amount ÷ the real sum of every category shown). This is a judgment
   call: `money_category_breakdown()` returns raw amounts only, not
   pre-computed percentages, so this is a new derived ratio rather than
   a sum of already-computed percentages (the precedent Home's Capital
   Distribution used). Treated as acceptable because it's fully
   decimal-exact, transparent, reproducible, and never used for
   anything beyond display — but flagged explicitly here as a boundary
   judgment rather than a clean precedent match.
2. `AvailableCashSection` originally summed bucket balances with native
   JS `Number()` arithmetic to produce a per-currency total — caught
   during this same implementation pass (not by an external review) and
   replaced with `money_currency_totals()`'s own real, pre-summed
   total before any test or build was run against it.
3. The two `useEffect`-based on-demand fetches (receivable/liability
   pickers) initially called `setLoading(true)` synchronously inside
   the effect body, which ESLint's `react-hooks/set-state-in-effect`
   rule correctly flagged (the same rule encountered and resolved in
   P0-E3-S2's onboarding-hook fix). Fixed by deriving the loading flag
   from existing state (`mode === X && data === null`) instead of a
   separate `useState`, eliminating the synchronous setState entirely.
4. Quick Add's data (buckets/balances/categories) is fetched once at
   `AppShell` level and does not automatically refresh while the sheet
   is open across multiple submissions in one session without a page
   navigation; `router.refresh()` after each successful mutation (used
   throughout every form) re-runs the server fetch, including
   `AppShell`'s own, so this self-corrects on every submit.

ADDENDUM — THEME PROVIDER REACT 19 / NEXT 16 COMPATIBILITY FIX
================================================================================

DEFECT. `npm run dev` reported: "Encountered a script tag while
rendering React component. Scripts inside React components are never
executed when rendering on the client," originating from
`components/theme/ThemeProvider.tsx`. Confirmed by inspection: `next-
themes@0.4.6` (the installed, and current latest stable, version) with
React `19.2.8` / Next.js `16.3.6`. `next-themes` has no fixed stable
release for this — its only newer published version tag, `1.0.0-beta.0`,
was checked directly against the npm registry's per-version publish
timestamps and dates to 2022-05-17, years before React 19 existed;
irrelevant, not a fix.

FIX. Migrated from `next-themes` to `@teispace/next-themes@^3.0.2` — an
actively maintained fork whose own README explicitly documents this
exact upstream bug (its issue #397: "React 19.2 'Encountered a script
tag while rendering React component' when the provider client-remounts,"
and #387/#385, the same inline-`<script>`-in-React-19 class of issue)
and its fix mechanism: the anti-FOUC bootstrap script is injected via
Next.js's own `useServerInsertedHTML` (raw HTML written directly into
the stream), never returned as `<script>` JSX from a component, so
React's client reconciler never encounters a script element as part of
a component's own render output — structurally eliminating the warning
rather than suppressing it. Peer deps (`next >=13`, `react/react-dom
>=18`) confirmed compatible before migrating, per this task's own
explicit "verify API compatibility first" instruction.

`components/theme/ThemeProvider.tsx`: import swapped;
`storage="local"` added explicitly — this fork defaults to a hybrid
cookie+localStorage mode, and `storage="local"` is required to preserve
the exact prior device-local-only, no-cookie persistence behavior the
original P0-E3-S2 phase brief mandated (confirmed via the fork's own
migration guide: "Default storage is 'hybrid' ... To preserve exact old
behavior, set storage='local'"). `attribute="data-theme"`,
`defaultTheme="system"`, `enableSystem` are unchanged — all three are
source-compatible props on the new library. `components/theme/
ThemeToggle.tsx`: import swapped; its doc comment updated to describe
the new library's actual pre-hydration behavior (`theme` starts at
`defaultTheme` via `useSyncExternalStore`, never `undefined`, unlike
upstream) rather than leaving a now-inaccurate comment in place.

INCIDENTAL FIX (discovered while verifying this one, not scope creep):
`components/layout/AppShell.tsx` had a real, pre-existing crash —
`QuickAddProvider` (added in the P0-E3-S3 work this addendum follows)
only wrapped `<main>`/`MobileBottomNav`, not the `<header>`, so
