10. CASH BUCKET MODEL
--------------------------
Minimal: id, user_id, name, currency_code, bucket_type (CHECK-constrained
to bank_account/cash_wallet/savings_account/mobile_wallet/business_cash/
other), is_archived, timestamps. No manually-editable balance field — see
section 18. Currency is immutable once the bucket has any cash_movements,
enforced by a BEFORE UPDATE trigger
(enforce_bucket_currency_immutable()), not just documented convention;
tested explicitly. No DELETE grant/policy exists for any bucket, ever —
archive (is_archived) is the only supported removal-from-view mechanism,
per the brief's "prefer archive over delete."

11. FINANCIAL-EVENT MODEL
------------------------------
event_type in (opening_balance, money_received, money_spent, transfer,
fx_transfer) — deliberately not extended to asset_purchase/asset_sale/
receivable_recovery/debt_payment/goal_allocation this phase; the CHECK
constraint is a simple future ALTER once those domains exist.
cash_flow_class (income, other_inflow, expense, other_outflow, transfer,
opening_balance) is computed by a BEFORE INSERT trigger
(set_financial_event_classification()) from event_type + category — never
trusted from client input, and excluded from every INSERT/UPDATE column
grant. Correction is voiding only: enforce_financial_event_void_only()
makes voided_at a one-way transition and blocks every other column from
changing on an existing event. No event content is ever editable in
place; no automatic reversal-event generation exists this phase — both
are documented as deferred, not silently absent.

12. CASH-MOVEMENT MODEL
----------------------------
One signed-amount convention throughout: positive = credit to the bucket,
negative = debit. No separate direction column that could contradict the
sign. user_id is denormalized from the parent event for a simple,
join-free RLS policy, but is never taken from client input —
prepare_cash_movement() (a BEFORE INSERT trigger) overwrites it from the
event every time, and separately validates that the movement's
currency_code matches its bucket's currency_code and that the amount's
fractional precision doesn't exceed the currency's decimal_exponent.
Movements are immutable once inserted (no UPDATE grant or policy exists
for anyone) — a correction means voiding the owning event.

13. MULTI-CURRENCY ARCHITECTURE
------------------------------------
Full detail in docs/architecture/MULTI_CURRENCY_MODEL.md. Summary: bucket
currency, movement currency, and reporting currency (profiles.
preferred_currency, P0-E2-S1) are three distinct concepts, never
conflated. A user's buckets do not have to share a currency or match
their reporting currency. Nothing in the schema assumes NGN or any single
currency; the currency registry (section 14) is the canonical identifier
source everywhere.

14. CURRENCY REGISTRY STRATEGY
------------------------------------
public.currencies is a real reference table (not a hardcoded enum),
RLS-enabled with a permissive USING (true) SELECT policy — deliberately
so, because this is public non-sensitive lookup data, not user data; the
phase's own "avoid USING (true) as a shortcut" guidance is about
user-owned tables. code (ISO-4217-shaped, format-checked) is the
canonical identifier everywhere; symbol is presentation metadata only,
never used for comparison or identity. decimal_exponent records each
currency's actual decimal convention. Seeded with 26 codes including
0-decimal (JPY) and 3-decimal (KWD) examples specifically to exercise the
"not every currency has 2 decimal places" requirement, not just the
common 2-decimal case. Extending the registry is a migration that inserts
a row, not a schema change.

Known, documented duplication: lib/domain/profile/currencies.ts (P0-E2-S1's
onboarding picker) is a separate hand-maintained list that overlaps with
this registry. Not reconciled this phase — see Open Questions.

15. FX-RATE MODEL
----------------------
Fixed convention, stated once: rate = units of quote_currency received
for 1 unit of base_currency. For an executed fx_transfer, base_currency
is always the source bucket's currency, quote_currency the destination
bucket's currency, rate = destination_amount / source_amount — the
actual, permanent, historical rate. fx_rates.source is manual or
transaction_actual (provider/bank/broker are anticipated future values,
not implemented — no live FX integration this phase, no "live rate"
language anywhere). A validate_transaction_actual_fx_rate() trigger
ensures a transaction_actual row can only reference the same user's own
fx_transfer event (an RLS/FK check alone would not catch a rate pointing
at the right owner but the wrong event). numeric(24,12) precision —
deliberately more than cash amounts need, since FX rates can require more
decimal places than any display value would.

16. CROSS-CURRENCY TRANSFER MODEL
----------------------------------------
record_fx_transfer() creates two cash_movements (source debit in source
currency, destination credit in destination currency) with both original
amounts stored exactly — neither derived from nor discarding the other —
plus one fx_rates row (source=transaction_actual) computed from those
exact amounts. cash_flow_class is always 'transfer', never income or
expense. FX fees are not automatically bundled into the transfer call:
a fee is recorded as its own money_spent event (a fee genuinely is
spending, not part of a neutral transfer) using the existing
record_money_spent() primitive — no schema change needed to support this
later as a combined operation if wanted; deliberately kept as two calls
this phase (documented as an assumption, section 33).

17. MONEY CLASSIFICATION MODEL
------------------------------------
cash_flow_class is the single controlled-vocabulary field answering "does
this event contribute to income/expense/inflow/outflow/transfer" —
computed by set_financial_event_classification() from event_type +
category, never guessed from an amount's sign and never a
client-settable value (excluded from every column grant). money_received
categories map to income or other_inflow (receivable_recovery, asset_sale,
refund, and the catch-all "other" -> other_inflow; business_income,
salary, freelance_contract, investment_income, gift -> income).
money_spending categories map to expense or other_outflow (debt_payment
-> other_outflow; everything else, including the catch-all "other" ->
expense). This directly implements FINANCIAL_DOMAIN_MODEL.md's "cash
received is not automatically income" / "cash out is not automatically
spending" principles as an enforced database invariant, not just
documented intent.

18. BALANCE CALCULATION MODEL
------------------------------------
cash_buckets has no stored balance. money_bucket_balances() (per bucket +
currency) and money_currency_totals() (per currency, across buckets) are
the sole authoritative calculations — both SECURITY INVOKER SQL
functions, both excluding voided events, neither ever summing across
currencies (return shape is always {currency_code, amount}[], never one
blended number). money_recent_activity() joins events+movements for a
single "what happened" read. Every amount in all three is cast to text
(section 19). Home, Money, and any future consumer are expected to call
these rather than re-deriving balance independently
(docs/architecture/SYSTEM_ARCHITECTURE.md §4).

19. DECIMAL/PRECISION STRATEGY
------------------------------------
No REAL/DOUBLE PRECISION anywhere. Storage: numeric(20,6) for amounts,
numeric(24,12) for FX rates. Currency-specific precision
(decimal_exponent) is enforced by a trigger, not just documented, and
tested explicitly for 0-decimal (JPY) and 3-decimal (KWD) currencies.
JSON-transport risk: PostgREST serializes numeric as a JSON number by
default, which risks float64 precision loss for large/precise values once
a JS client's JSON.parse touches it — the three read functions cast every
amount to text in their RETURNS TABLE shape specifically to close this,
so the value arrives in TypeScript as an exact decimal string. On the
write side, PostgREST extracts JSON body values as text before casting to
the SQL parameter type, so a JSON string amount is parsed into numeric
exactly with no float round-trip — every repository function in
lib/domain/money/repository.ts accepts amount as string, never number,
and documents (via asNumericParam()) exactly why passing a string against
a TypeScript-generated number parameter type is correct rather than
unsafe. decimal.js is the one arbitrary-precision library used anywhere
in the codebase (chosen for being small, mature, and the most widely used
option; no second numeric library was introduced) — used for
lib/domain/money/format.ts's display formatting (per-currency
decimal_exponent, thousands-grouping via string manipulation, never a
number round-trip) and conversion.ts's rate multiplication.

20. ATOMIC TRANSACTION STRATEGY
--------------------------------------
Every record_* function is a single PL/pgSQL function body — Postgres
executes the whole body as one transaction, so a raised exception at any
point rolls back everything the function did (e.g. a transfer's source
debit is never left without its destination credit). This is why
sequential client-side inserts, explicitly disallowed by the brief, are
not equivalent: a dropped request between two separate REST calls cannot
leave a half-created transfer here, because there is only ever one call.
All five functions are SECURITY INVOKER (the default, stated explicitly
throughout the migration for clarity) — no elevated privilege exists
anywhere in the Money domain. None trusts a caller-supplied owner id:
every referenced bucket is checked against auth.uid() explicitly, in
addition to (not instead of) the RLS policies the inserts still go
through as the invoking user.

21. IDEMPOTENCY STRATEGY
-----------------------------
Every record_* function accepts an optional client-generated
idempotency_key (uuid). A partial unique index on financial_events
(user_id, idempotency_key) where idempotency_key is not null enforces
uniqueness. Each function first checks for an existing event with that
key and returns it directly if found (no new insert); an EXCEPTION WHEN
unique_violation block also catches the race window between that check
and the insert, re-querying and returning the existing row instead of
propagating the error. Tested explicitly: two record_money_received()
calls with the same idempotency_key produce the same event id and exactly
one movement, not two. lib/domain/money's RecordMoneyForm/TransferForm
generate a key once per in-progress submission (React state, rotated only
after a successful submit) rather than per keystroke, so retries of the
same click collapse correctly.

22. CORRECTION/VOIDING STRATEGY
--------------------------------------
Voiding only, this phase — see FINANCIAL_DOMAIN_MODEL.md §18 and section
11 above. enforce_financial_event_void_only() makes voided_at a one-way
transition (cannot be set to null again once set) and rejects any UPDATE
that changes any other column. cash_movements rows are never editable at
all — not even by the voiding mechanism, since voiding only touches the
parent event; a voided event's movements are excluded from balance
calculations (section 18) but never deleted, preserving the audit trail.
Editing event contents in place and automatic reversal-event generation
are both explicitly deferred, not silently absent.

23. RLS POLICIES
---------------------
Every Money table has RLS enabled. currencies/money_received_categories/
money_spending_categories: SELECT-only, permissive (public reference
data — see section 14). cash_buckets: SELECT/INSERT/UPDATE all scoped to
auth.uid() = user_id, column-level UPDATE grant excludes user_id itself;
no DELETE. financial_events: SELECT/INSERT scoped to auth.uid() =
user_id, UPDATE grant restricted to the voided_at column only (enforced
further by the trigger in section 11/22); no DELETE. cash_movements:
SELECT/INSERT both require auth.uid() = user_id, and INSERT additionally
requires EXISTS checks proving the referenced bucket and event both
belong to auth.uid() (section 24); no UPDATE, no DELETE, for anyone.
fx_rates: SELECT allows the caller's own rows or global rows
(user_id is null — none seeded this phase); INSERT requires auth.uid() =
user_id, plus a trigger validating transaction_actual rows reference the
caller's own fx_transfer event; no UPDATE, no DELETE.

24. CROSS-TENANT REFERENCE PROTECTIONS
--------------------------------------------
The pattern that differs from Profile (a single-table domain): any table
that references another user-owned table validates ownership of BOTH the
row itself and everything it points to. cash_movements' INSERT policy:
auth.uid() = user_id AND EXISTS(bucket owned by auth.uid()) AND
EXISTS(event owned by auth.uid()). Without the EXISTS checks, a user
could satisfy auth.uid() = user_id while still pointing bucket_id/
event_id at someone else's row. Every record_* function additionally
re-validates bucket ownership explicitly in PL/pgSQL (independent of, not
instead of, the RLS the insert still goes through as the invoking user) —
tested by attempting a transfer/fx_transfer/money_received into or
referencing another user's bucket or event, and by attempting a raw
cash_movements insert against another user's real bucket+event pair
(section 25).

25. ADVERSARIAL TESTS
--------------------------
All required scenarios from the phase brief's 35-item matrix are present
in supabase/tests/money/run.ts, plus several beyond it:
- Bucket creation/isolation (items 1-10): create own NGN/USD/other
  buckets, read-only-own, cannot read/update B's bucket by UUID, cannot
  reassign own bucket's ownership, cannot create a bucket owned by B,
  anonymous cannot read/mutate buckets.
- Money received/spent + balance (11-13).
- Same-currency transfer (14-19): moves both bucket balances without
  changing the currency total, not income, not expense, fails into B's
  bucket, fails when referencing B's bucket for a plain money_received
  event, and a direct cash_movements insert naming B's real bucket+event
  (with the attacker's own user_id, the realistic attack shape) is denied.
- Event/movement read isolation (20-21): cannot read B's financial_events,
  a raw unfiltered SELECT on cash_movements returns only the caller's own
  rows (not B's — see section 27 for why this test's expectation changed
  mid-phase), money_recent_activity() never leaks a B-owned row.
- FX transfer (22-27): both original amounts persist exactly, the applied
  rate persists exactly, not income, not expense, fails into B's bucket.
- Validation failures (28-29): currency mismatch in record_transfer
  fails; a currency code not in the registry fails via FK.
- Bucket currency immutability (30): fails once movements exist.
- Missing-rate aggregation (31): convertToReportingCurrency() returns
  not_calculated with the correct missing-currency list; converts
  correctly once a rate is supplied.
- Idempotency (32): a retried call with the same key produces one event,
  not two.
- Ownership reassignment (33-34): cannot reassign a financial_event's
  user_id (raw update, column not grantable); cannot update a
  cash_movements row at all, for any reason (no UPDATE grant exists).
- Direct UUID-targeted reads (35): across cash_buckets, financial_events,
  and fx_rates simultaneously, no User B data is ever returned.
- Beyond the matrix: anonymous isolation across financial_events,
  fx_rates, and every Money RPC (not just cash_buckets); an opening
  balance is its own event, not income; a JPY (0-decimal) bucket rejects
  a fractional amount and accepts a whole number; a KWD (3-decimal)
  bucket accepts 3 decimal places and rejects 4.

Two real defects were found by actually running these suites against a
live database, not by design review alone:
1. An early cash_movements grant design (no SELECT for anyone, intending
   to force all reads through the text-casting functions) broke the
   functions themselves, since they are SECURITY INVOKER and therefore
   need the same grants a direct query would. Every balance/activity read
   failed with "permission denied for table cash_movements" — including
   for the legitimate owner. Root-caused via the improved error messages
   in assert.ts (previously "[object Object]" for non-Error thrown
   values — Supabase/Postgrest errors are plain objects, not Error
   instances; describeError() was added to surface the real Postgrest
   message). Fixed by granting SELECT (see section 9/23) rather than
   making the functions SECURITY DEFINER, which the security doc
   explicitly warns against using merely to route around a missing grant.
2. /money/page.tsx fetched Money data unconditionally. Even though
   app/(app)/layout.tsx correctly redirects an unauthenticated visitor
   away (documented P0-E1-S2 lesson: Next.js can render a layout and the
   page it wraps concurrently), the page's own data fetching still ran
   during that race and threw an uncaught "permission denied for function
   money_bucket_balances" when called with no session — caught by
   route-level `next dev` smoke testing (curling /money unauthenticated
   and reading the server log), not by the build. Fixed the same way
   /home already handled it: check getCurrentUser() first, return null if
   absent, before touching the Money repository at all.
Both are recorded here per instruction not to describe the phase as
complete without fixing or flagging issues found during its own
validation.

33. ASSUMPTIONS
--------------------
- FX fees are recorded as a separate money_spent event rather than a
  parameter on record_fx_transfer() — a fee is spending, not a neutral
  part of the transfer, and this needed no schema change; documented as a
  deliberate scope decision, not an oversight.
- Opening balance amounts are required to be positive (a cash reserve, not
  a starting liability) — the brief's worked example is positive; no
  requirement was stated either way for a negative opening balance, and
  cash buckets are modeled as assets, not debt instruments, this phase.
- The currencies table's 26-code seed list is a starting set (matching
  the existing onboarding picker plus JPY/KWD for decimal-exponent
  coverage), not a product decision about which currencies V1 ultimately
  supports.
- Bucket type codes (bank_account/cash_wallet/savings_account/
  mobile_wallet/business_cash/other) match the brief's example list
  exactly; "Other cash reserve" was shortened to the code `other` with
  "Other cash reserve" as its UI label.
- Docker was already running from the P0-E2-S1 session; no new
  environment-startup action was needed this phase.

   function level, not driven end-to-end through a real browser.

   if one list is updated and the other isn't.
