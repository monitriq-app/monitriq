9. AGGREGATION ARCHITECTURE
--------------------------------------------------------------------------------
Hybrid query strategy, chosen deliberately and documented in the
migration's own header comment:

  (a) ONE composed SQL function (`financial_position_by_currency()`) for
      every per-currency NUMERIC aggregate — cash, assets, receivables,
      liabilities, Net Worth, Safe-to-Deploy fields, potential liquidity,
      allocation shortfall. Implemented as CTEs, each selecting from one
      existing canonical function, joined on `currency_code`. Avoids N+1
      round trips for tabular, currency-keyed data.

  (b) PARALLEL TypeScript-layer reads (`Promise.all` in
      `getFinancialPositionSummary()`) for the list-shaped domain
      summaries that don't fit a currency-keyed row: Goals
      (`getGoalSummaries()`), Decisions (`getDecisionSummaries()`),
      Obligations (`getUpcomingObligations()`), plus the user's Profile
      for `reportingCurrency`. Filtering (`activeGoals`, `focusGoal`,
      `activeDecisions`) happens in TypeScript over already-fetched data,
      not via additional queries.

No table is read directly by the new function or the new repository
layer except through the eight canonical functions/repositories listed
in §10 — this is "aggregation, not ownership" enforced by construction:
the new SQL function's body contains no independent balance/valuation/
outstanding-amount arithmetic anywhere except the one Net Worth sum.

10. CANONICAL SOURCE MAP
--------------------------------------------------------------------------------
Liquid Cash              -> money_currency_totals()
Non-Cash Asset Value      -> asset_native_currency_totals()  (estimated_current_value only)
Receivables Outstanding   -> receivable_native_currency_totals()
Liabilities Outstanding   -> liability_native_currency_totals()
Safe to Deploy / Protected
  Cash / Retained Deficit -> safe_to_deploy_by_currency()
Asset Quick-Sale Potential -> asset_summary()  (filtered, summed by currency)
Receivable Estimated
  Recoverable              -> receivable_summary()  (filtered, summed by currency)
Allocation Shortfall       -> goal_bucket_shortfalls()  (summed by currency)
Active Goals / Focus Goal  -> getGoalSummaries() (TypeScript layer)
Active Decisions           -> getDecisionSummaries() (TypeScript layer)
Upcoming Obligations       -> getUpcomingObligations() / upcoming_obligations()
Reporting Currency         -> getProfile().preferred_currency
Reporting Conversion       -> convertToReportingCurrency() (lib/domain/currency)

No formula from any of these was re-derived, forked, or duplicated.

11. NATIVE FINANCIAL-POSITION MODEL
--------------------------------------------------------------------------------
`NativeFinancialPosition` (lib/domain/financial-position/types.ts): one
row per native currency — currencyCode, liquidCash, nonCashAssetValue,
receivablesOutstanding, liabilitiesOutstanding, netWorth,
protectedGoalCash, protectedCommitments, minimumCashFloor,
requiredRetainedCash, safeToDeploy, safeToDeployStatus, retainedDeficit,
assetQuickSalePotential, receivablesEstimatedRecoverable,
receivablesRecoverabilityDifference, allocationShortfall. All monetary
fields are exact-decimal strings (never parsed to JS number). Computed
independently per currency; currencies are never blended.

12. NET-WORTH MODEL
--------------------------------------------------------------------------------
netWorth = liquidCash + nonCashAssetValue + receivablesOutstanding
           − liabilitiesOutstanding

The ONLY new calculation this phase introduces. Never clamped — a
currency with more debt than assets legitimately produces a negative
netWorth (verified explicitly: NGN liability-only setup with no
offsetting cash produces exactly "-50000.000000", not "0.000000" or an
error). Goals, Rules, Obligations, and Decisions are all verified to
leave netWorth completely unchanged (see §30).

13. RECEIVABLE TREATMENT
--------------------------------------------------------------------------------
Net Worth uses current outstanding receivable amount
(receivable_native_currency_totals()) — never the estimated recoverable
value. receivablesEstimatedRecoverable is exposed as a fully separate
field, null ("Not set") when no estimate was ever recorded — never
silently assumed equal to outstanding. receivablesRecoverabilityDifference
= receivablesEstimatedRecoverable − receivablesOutstanding, null exactly
when the estimate is null. Receivable recovery (cash in, receivable down)
was verified to leave netWorth completely unchanged (value moves between
two Net Worth components, doesn't create or destroy it) both when applied
and after voiding.

14. ASSET VALUATION TREATMENT
--------------------------------------------------------------------------------
Net Worth uses the latest estimated_current_value only
(asset_native_currency_totals()). target_value never enters Net Worth
(verified: a EUR asset with target_value=9000 and
estimated_current_value=4000/later 4500 produces netWorth matching the
current value, never 9000). quick_sale_estimate never enters Net Worth
either — it is exposed separately as assetQuickSalePotential, null when
not recorded.

15. LIABILITY TREATMENT
--------------------------------------------------------------------------------
Net Worth subtracts current outstanding principal only
(liability_native_currency_totals()) — never opening principal, never
already-paid interest, never future interest assumptions, never
hypothetical Decision debt. Verified explicitly: a principal-only debt
payment moves cash and liability down by the same amount (netWorth
unchanged); an interest+fee payment moves cash down with liability
unchanged (netWorth reduced by exactly the interest+fee total); voiding
the principal-only payment restores both sides symmetrically (netWorth
unchanged again, both before/after values matching).

16. GOAL / OBLIGATION / DECISION TREATMENT
--------------------------------------------------------------------------------
Verified structurally, not just observed: goal allocation, release, and
protected-vs-unprotected distinctions all leave netWorth unchanged (goals
claim already-existing cash, they don't move it between tables). Rule
creation/change, obligation creation, and marking an obligation
paid/cancelled all leave netWorth unchanged (configuration and
commitments, not transactions). Decision scenario evaluation and every
choice including 'proceed' leave netWorth unchanged (Decisions write only
to decision_* tables, never to financial_events/cash_movements/assets/
liabilities). All four are surfaced as separate, factual information
(activeGoals, focusGoal, activeDecisions, upcomingObligations) — never
folded into Net Worth.

17. LIQUID-POSITION MODEL
--------------------------------------------------------------------------------
protectedGoalCash, protectedCommitments, minimumCashFloor,
requiredRetainedCash, safeToDeploy, safeToDeployStatus, retainedDeficit
are read verbatim, per currency, from safe_to_deploy_by_currency() — no
second liquidity formula exists anywhere in this phase's code.

18. PROTECTED-CASH MODEL
--------------------------------------------------------------------------------
protectedGoalCash is Rules' own actual-backed protected cash (capped at
real bucket balance, never the nominal allocation) — inherited directly,
not recomputed. Verified with the same underfunded-bucket worked case
established in P0-E2-S6A: SGD bucket funded to 7000, two protected goals
allocated 4000+3000 (nominal 7000), a real spend of 2000 leaves only 5000
actually backed — protectedGoalCash reads exactly "5000.000000", matching
safe_to_deploy_by_currency() exactly (asserted field-by-field, not just
value-by-value).

19. SAFE-TO-DEPLOY INTEGRATION
--------------------------------------------------------------------------------
Verified with a direct, same-request comparison: `getSafeToDeployByCurrency()`
and `getFinancialPositionByCurrency()` are called in parallel against
identical fixture state, and protectedGoalCash/safeToDeploy/retainedDeficit
are asserted equal between the two results field-by-field. Currencies with
no configured minimum cash floor report safeToDeployStatus="not_configured"
in Financial Position exactly as they do in Rules — never a silently
assumed floor.

20. POTENTIAL LIQUIDITY
--------------------------------------------------------------------------------
assetQuickSalePotential (sum of recorded quick_sale_estimate, filtered to
non-archived assets) and receivablesEstimatedRecoverable (sum of recorded
estimated_recoverable_value, filtered to non-archived receivables) are
exposed as fully distinct fields — never combined with cash or receivable
outstanding into one "liquid total." Both are null (not 0) when nothing
was ever recorded, via Postgres's natural SUM()-over-empty-filtered-set
NULL propagation. Verified: receivables never appear in liquidCash; an
asset's quick-sale estimate never feeds safeToDeploy (a currency with a
quick-sale estimate but no configured floor still reports
safeToDeployStatus="not_configured", proving no back-door contribution).

21. ALLOCATION-SHORTFALL MODEL
--------------------------------------------------------------------------------
allocationShortfall sums goal_bucket_shortfalls() per currency and is
always a real number (0 when nothing is short — a genuine computable
zero, not a missing value). Exposed as its own field, never hidden inside
safeToDeploy. Verified with the same SGD underfunded-bucket case: nominal
7000 allocated, 5000 actually backed -> allocationShortfall =
"2000.000000".

22. REPORTING-CURRENCY MODEL
--------------------------------------------------------------------------------
`convertFinancialPositionToReportingCurrency()`
(lib/domain/financial-position/aggregate.ts) converts each of the four
Net Worth components independently via convertToReportingCurrency()
(never pre-summing mixed currencies), then combines the four converted
totals via decimal.js into one reporting netWorth. Verified with a
non-round rate (1 EUR = 1.10 USD): USD position (netWorth 5000, already
reporting currency) + EUR position (netWorth 4500 * 1.10 = 4950) produces
an exact reporting netWorth of "9950" — no binary-float drift.

23. FX TRANSPARENCY
--------------------------------------------------------------------------------
The calculated result exposes reportingCurrency, currenciesRequiringConversion,
ratesUsed (exact rate strings, scoped only to currencies actually
requiring conversion), and asOf (calculation timestamp) — never implying
live FX. No live FX integration exists or was added this phase; every
rate must be supplied explicitly by the caller.

24. PARTIAL / NOT-CALCULATED STATES
--------------------------------------------------------------------------------
Verified explicitly: with a EUR position present and no EUR->USD rate
supplied, convertFinancialPositionToReportingCurrency() returns
{status: "not_calculated", missingRates: ["EUR"], currenciesRequiringConversion:
["EUR"]} — never omitting the unsupported currency, never assuming
rate=1, never showing a partial Net Worth. Native-currency Financial
Position remains fully available regardless (it does not depend on this
function at all). Other honest-nullable states verified throughout: no
quick-sale estimate -> null, not 0 (§20); no minimum cash floor ->
safeToDeployStatus="not_configured" (§19); no goals -> protectedGoalCash
naturally reflects Rules' own not_configured/zero semantics; no focus
goal explicitly selected -> focusGoal is null, never invented (§16 of the
FINANCIAL_DOMAIN_MODEL.md addendum).

25. EXACT-DECIMAL STRATEGY
--------------------------------------------------------------------------------
Unchanged discipline, reused not reinvented: Postgres numeric(20,6)
throughout every composed source function, every monetary column in
financial_position_by_currency()'s return type cast to ::text, decimal.js
as the only arbitrary-precision library at the TypeScript combination
step in aggregate.ts. Verified with JPY (0-decimal currency, exact
"100000.000000"), KWD (3-decimal currency, exact "50.123000"), and the
non-round EUR->USD reporting conversion (§22) — no binary-float drift
anywhere in the chain.

26. QUERY / PERFORMANCE STRATEGY
--------------------------------------------------------------------------------
Documented explicitly in the migration's header comment and in
FINANCIAL_DOMAIN_MODEL.md §41 / SYSTEM_ARCHITECTURE.md §4: one SQL round
trip for the per-currency numeric core (avoiding N+1 across up to eight
source functions), plus a small, fixed number (5) of parallel
(Promise.all) reads at the TypeScript layer for list-shaped data that
doesn't belong in a currency-keyed SQL row. No sequential/serial fetch
loop exists anywhere in the new code.

27. RLS / SECURITY POSTURE
--------------------------------------------------------------------------------
financial_position_by_currency() is SECURITY INVOKER, never DEFINER —
consistent with every prior domain's read function. It requires no
service-role client; every underlying domain continues enforcing its own
RLS through auth.uid()-scoped policies, and composing SECURITY INVOKER
functions inside another SECURITY INVOKER function never changes whose
privileges apply at any point in the chain. This is documented as an
explicit, reusable pattern for future cross-domain aggregation:
docs/security/SECURITY_AND_RLS_PRINCIPLES.md §20.

37. ASSUMPTIONS
--------------------------------------------------------------------------------
- "Active" Decisions for the summary means status = 'active' (excludes
  'closed' and 'archived'), matching DecisionStatus's own vocabulary and
  the brief's "archived Decisions excluded from active view" requirement.
- "Active" Goals for the summary means status = 'active', matching
  GoalStatus's own vocabulary.
- Financial Position's own read model exposes GoalSummary/DecisionSummary/
  UpcomingObligation objects verbatim (not a narrowed/reshaped subset) —
  the brief explicitly permits diverging from its own suggested shape "if
  a cleaner typed model exists," and reusing each domain's own summary
  type in full keeps domain boundaries intact with zero remapping risk.
- upcomingObligations uses upcoming_obligations()'s own default horizon
  (no explicit start/end passed) rather than Financial Position inventing
  its own default — consistent with "reuse Obligations' own date-range
  logic."
