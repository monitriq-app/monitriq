3. OBJECTIVE
------------------------------------------------------------------------
Build Monatriq's Goals domain so it can answer "what am I working
toward," "what money have I deliberately assigned to it," "how much
remains," and "what pace would mathematically be required" — without
creating fake money, double-counting cash, telling the user what they
should do, or treating all goal types as identical. Core architectural
constraint: GOALS DO NOT OWN CASH. A goal allocation assigns purpose to
cash that already exists in a Money bucket; it never creates a second
version of the user's money.

9. GOAL SCHEMA
------------------------------------------------------------------------
`goals` (id, user_id, goal_type_code, measurement_type, name,
description, currency_code, liability_id, starting_liability_balance,
status, is_protected, is_focus, priority, created_at, updated_at). No
`target_value`/`current_saved` column — those are derived (see §11/§13).
Three CHECK constraints enforce measurement-type-consistent shape:
currency required unless `milestone`; `liability_id` required iff
`debt_balance_target`; `starting_liability_balance` required iff
`debt_balance_target`. A partial unique index
(`goals_one_focus_per_user`) enforces at most one focus goal per user,
regardless of write path. RLS enabled, deny-by-default,
`auth.uid() = user_id` ownership policies; the INSERT policy additionally
requires an EXISTS check on `liability_id` against the caller's own
liabilities when set.

10. GOAL-TYPE STRATEGY
------------------------------------------------------------------------
`goal_types` is a separate, extensible, public-reference registry (13
seeded codes: home_property, emergency_reserve, savings_target,
relocation, recurring_income, debt_payoff, business_capital, education,
vehicle, event, retirement, travel, custom) — purely descriptive, with a
`default_measurement_type` column that only pre-fills the creation form.
It never drives progress math. This deliberately decouples "what kind of
goal is this, descriptively" from "what mathematics apply to it," so a
future goal type needs no schema change to the measurement axis.

11. MEASUREMENT MODEL
------------------------------------------------------------------------
`goals.measurement_type` is a CHECK-constrained axis with exactly four
values: `cash_target`, `debt_balance_target`, `monthly_income_target`,
`milestone`. Every progress calculation (allocated total, remaining,
percentage, required pace, allocation eligibility) branches on this
single column, never on `goal_type_code`. The four types are not four
independent systems — they share the same `goal_target_history` and
`goal_allocation_events` infrastructure, differing only in which fields
are populated/permitted for each (enforced by triggers and RPC checks,
not merely UI convention).

12. TARGET-HISTORY MODEL
------------------------------------------------------------------------
`goal_target_history` is append-only: a new row is a new "version" of the
target (target_value, currency_code, target_date, effective_at, note) —
old targets are never overwritten. The current target for a goal is
always the latest row (`goal_current_target()`). `target_value` is
structurally null for `debt_balance_target` (target is implicitly
"outstanding principal = 0") and `milestone` (no numeric target at all) —
enforced by `prepare_goal_target()`'s trigger, not just documented
convention.

13. CASH-ALLOCATION MODEL
------------------------------------------------------------------------
`goal_allocation_events` is append-only: `allocate` rows are positive,
`release` rows are negative, current allocation = `sum(amount)`. No
`goal.current_saved`-style mutable column exists. Unlike Receivables/
Liabilities' ledgers, this table has NO `financial_event_id` column at
all — it structurally cannot represent a cash effect, which is the
architectural enforcement of "Goals do not own cash," not merely a
convention. `record_goal_allocation()`/`record_goal_release()`/
`record_goal_reallocation()` never write to `financial_events`/
`cash_movements`, verified explicitly by asserting byte-identical bucket
balances and financial_events row counts before/after every operation.

14. ONE-UNIT-ONE-PURPOSE ENFORCEMENT
------------------------------------------------------------------------
Enforced by construction via allocation capacity (§15), not by convention
or client-side validation. The same cash can never simultaneously fund
two goals beyond the bucket's actual balance: `available_to_allocate =
bucket_balance − sum(existing allocations from that bucket, across ALL
goals)`, checked before every allocate, and the bucket row is locked for
the duration of that check (see §15). Verified explicitly: a bucket fully
allocated across two different goals rejects even a 1-unit further
allocation to a third goal.

15. ALLOCATION-CAPACITY / CONCURRENCY MODEL
------------------------------------------------------------------------
Every allocate/release/reallocate RPC issues `select ... for update` on
the target `cash_buckets` row before computing available-to-allocate
capacity. This makes two concurrent allocation attempts against the same
bucket serialize (the second transaction blocks until the first commits,
then re-reads the now-current available balance) rather than both reading
a stale figure and both succeeding. Proven by a dedicated test that fires
two concurrent 700-unit allocation attempts against a 1000-unit bucket via
`Promise.allSettled`: exactly one succeeds, and the bucket's allocated
total is exactly 700 afterward, never 1400.

16. RELEASE/REALLOCATION MODEL
------------------------------------------------------------------------
Release inserts a negative `goal_allocation_events` row, reducing a
goal's allocation from a specific bucket by exactly the released amount;
rejected if it would exceed the current (goal, bucket) allocation.
Reallocation (`record_goal_reallocation()`) is one atomic operation: a
release row on the source goal and an allocate row on the destination
goal, sharing one bucket, written in a single transaction — the same
money is never observably assigned to both goals at once. Only the
release-side row carries the idempotency key (the allocate-side row's key
stays null); since the pair always commits together, a retry is safely
detected by the release row's key alone. Neither operation ever touches
cash.

17. PROTECTION MODEL
------------------------------------------------------------------------
`is_protected` is a plain user-controlled boolean, freely toggleable via
the UPDATE grant — Monatriq never sets it automatically. This phase only
makes the flag exist and be queryable
(`goal_protected_allocation_totals()`, grouped by currency); it does not
itself block or warn about anything. The five-step override workflow
(show impact, show conflict, allow cancellation, allow override, record
the override) described in the original conceptual spec is explicitly
deferred to P0-E2-S6's Financial Rules engine.

18. ALLOCATION-SHORTFALL MODEL
------------------------------------------------------------------------
If cash later leaves a bucket that has allocations attached (an ordinary
Money spend/transfer that Goals has no say over and does not intercept),
`goal_bucket_shortfalls()` reports `balance`, `allocated_total`, and
`shortfall = greatest(allocated_total − balance, 0)` per bucket, honestly.
Allocation history is never rewritten to hide a shortfall — verified
explicitly: after allocating 1000 from a bucket and then spending 400 via
Money, the bucket's reported `allocated_total` stays exactly 1000 while
`shortfall` reports exactly 400.

19. DEBT-PAYOFF GOAL MODEL
------------------------------------------------------------------------
A `debt_balance_target` goal's `liability_id` is set once at creation
(cross-tenant-checked, immutable afterward) and its currency is derived
from the liability, never independently chosen. Progress is always read
live from `liability_outstanding_principal()` — the exact function
Liabilities' own read models use, never a duplicated balance.
`starting_liability_balance` is a one-time frozen snapshot taken at
creation (never updated, never in the UPDATE grant) purely to answer "how
much did I owe when I started this goal." Verified explicitly: a real
debt payment made after goal creation changes the live
`current_outstanding_principal` in `goal_summary()` while
`starting_liability_balance` stays frozen at its original value. Cash
allocated toward a debt goal (earmarked future repayment) is kept
conceptually distinct from an actual payment — only
`record_debt_payment()`/`record_loan_proceeds()` in Liabilities ever
change outstanding principal.

20. RECURRING-INCOME GOAL MODEL
------------------------------------------------------------------------
`monthly_income_target` goals reject cash allocation outright
(`record_goal_allocation()`/`record_goal_reallocation()` both check this).
No heuristic reads business-income/salary/asset-sale/receivable-recovery/
refund/transfer events to infer a "current recurring income" figure —
`goal_summary()` has no "current" concept for this measurement type at
all; `allocatedTotal`/`remaining` are always null and
`requiredPaceStatus` is always `not_applicable`, regardless of how much
unrelated Money activity exists for the user. Verified explicitly in the
test suite even after the user has recorded substantial unrelated income
elsewhere.

21. MILESTONE MODEL
------------------------------------------------------------------------
`goal_milestones` (title, due_date, completed_at, sort_order) attach to
any goal — not restricted to the `milestone` measurement type, since a
cash_target goal can usefully have sub-steps too. Completion is a plain
`completed_at` column update with zero code path to
`financial_events`/`cash_movements`/`goal_allocation_events` — verified
explicitly (byte-identical bucket balances and financial_events counts
before/after). Creation goes through `record_goal_milestone()`, a narrow
SECURITY INVOKER RPC, for the same reason established in Assets §14:
`user_id` is trigger-derived and grant-excluded, so a direct insert would
need to supply a column the database will never accept.

22. REQUIRED-PACE CALCULATION
------------------------------------------------------------------------
`goal_required_pace()` computes remaining / periods for `cash_target` and
`debt_balance_target` goals only (`monthly_income_target`/`milestone`
return `not_applicable`). Status values: `calculated`, `target_reached`,
`no_target_date`, `no_target_amount`, `date_passed`, `not_applicable` —
never a fabricated number when an input is missing. Monthly cadence is
approximated via average days-per-month (365.25/12 = 30.4375); a partial
final period rounds UP (ceil), so pace is never understated. "Today" is
computed from the caller's `profiles.timezone` (falls back to UTC).
Explicitly labeled a calculation, not a recommendation — no "At Current
Pace" predictive forecasting exists this phase (deferred pending real
contribution-history data). Verified with an exact worked example: target
12000, allocated 3000, target_date 91 days out → periods = ceil(91 /
30.4375) = 3, required pace = (12000-3000)/3 = 3000.000000 — matched the
SQL function's actual output exactly on the first run.

23. MULTI-CURRENCY BEHAVIOR
------------------------------------------------------------------------
Both `currency_code` and `liability_id` are immutable after creation
(currency via trigger once allocation history exists; liability_id via
grant exclusion). A debt-payoff goal's currency is derived from its
liability, never independently chosen. Allocation/release/reallocation
are same-currency-only (bucket currency must equal goal currency;
reallocation additionally requires both goals and the bucket to share one
currency) — cross-currency allocation is rejected outright, mirroring
Receivables/Liabilities' same-currency-only rule. `goal_native_currency_
totals()` (scoped to `cash_target` goals only) reuses the shared
`{currencyCode, amount}[]` shape every other domain's native-totals
function returns; a missing reporting-currency rate returns
`not_calculated` via the shared `convertToReportingCurrency()`, verified
by feeding the function's own output through it with an empty rate map.

24. EXACT-DECIMAL STRATEGY
------------------------------------------------------------------------
All amount columns are `numeric(20,6)`. No `real`/`double precision`
anywhere. Every currency's `decimal_exponent` is enforced via BEFORE
INSERT triggers on both `goal_target_history` (target_value) and
`goal_allocation_events` (amount) — a fractional JPY target and a
3-decimal KWD allocation were both tested explicitly (JPY rejected, KWD
accepted). All read functions cast monetary amounts to `::text`;
percentages (a UI ratio, not a transportable monetary amount) are plain
numeric, matching the precedent set for `interest_rate`. `decimal.js`
remains the only arbitrary-precision library; the
`asNumericParam()`/`asOptionalNumericParam()` helper pattern is reused
unchanged.

25. RLS POLICIES
------------------------------------------------------------------------
Every new table (`goal_types`, `goals`, `goal_target_history`,
`goal_milestones`, `goal_allocation_events`) has RLS enabled immediately,
deny-by-default, no policy granting anonymous access. `goal_types` is
public reference data (like `currencies`/`liability_types`) — a
permissive `USING (true)` SELECT policy, no user-owned rows. All other
tables use `auth.uid() = user_id` ownership policies plus EXISTS-based
cross-tenant checks wherever a row references another table.

26. CROSS-DOMAIN REFERENCE PROTECTIONS
------------------------------------------------------------------------
`goals` → `liabilities` (INSERT policy EXISTS check when `liability_id`
is set). `goal_target_history`/`goal_milestones` → `goals` (EXISTS
check). `goal_allocation_events` → BOTH `goals` and `cash_buckets`
simultaneously — the critical two-reference policy this domain's brief
called out explicitly, proven by three dedicated raw-insert tests
(goal=own/bucket=other's; goal=other's/bucket=own; both other's with a
forged user_id). All `record_*` RPCs additionally re-verify ownership of
every referenced row inside the function body (never trusting RLS alone,
never trusting a caller-supplied `user_id`).

35. ASSUMPTIONS

- The remote "Monatriq Dev" project identity (confirmed in P0-E2-S3)
  remains valid and did not need re-confirmation this phase.

  partial periods round up) is a deliberate, documented choice among
  several defensible options for "choose a clear initial cadence."
