P0-E3-S4R2 — ADD ASSET: TYPE-AWARE CREATION FLOW
================================================================

STATUS: COMPLETE.

1. ROOT ISSUE
P0-E3-S4R fixed subtype leakage in the post-creation Manage flow
(`AssetActionSheet` no longer shows vehicle status/repair controls for
non-vehicle assets). Manual QA then found the same underlying problem
one step earlier: `AddAssetSheet`'s Step 2 showed essentially identical
fields for every asset type — "Cost Basis," "Current Value Estimate,"
"Conservative Quick-Sale Value," "Target Value" — with only two labels
(`business_interest`/`financial_investment`'s basis+current-value)
varying via a small local `BASIS_LABEL`/`CURRENT_VALUE_LABEL` map.
Quick-sale and target labels were 100% hardcoded, generic, identical
across all 8 types. A Vehicle and a Financial Investment therefore
looked like the same product with a different type tag at creation
time, even though the post-creation Manage experience had already been
made properly type-aware.

2. GENERIC FIELDS RETAINED
Confirmed by re-reading `create_asset()` (the atomic RPC every type
still calls unchanged): it accepts `p_asset_type`, `p_name`,
`p_currency_code`, `p_description`, `p_acquired_at`,
`p_initial_basis_amount`, `p_estimated_current_value`,
`p_quick_sale_estimate`, `p_target_value`, `p_valued_at` — one INSERT
into `assets` plus up to one `asset_basis_events` row and up to three
`asset_valuations` rows, all type-agnostic at the database level. These
remain the ONLY fields creation ever writes, for every type, with no
change to that function's signature or body. What changed is purely
which LABEL is shown for each of those same four numeric inputs, plus
(for Vehicle only) one additional real capability — see §4.

3. CREATION CONFIG INTRODUCED
`lib/domain/assets/capabilities.ts` gained a second export,
`assetCreationConfig(assetType): AssetCreationConfig`, alongside the
existing `assetCapabilities()` — the same centralized-model pattern,
extended to creation-time presentation rather than a third set of
scattered `assetType === "vehicle"` conditionals in JSX. Shape:
`valuesHeading` (Step 2's heading), `helperCopy?` (Step 1's clarifying
line under the selected type), `basisLabel`, `currentValueLabel`,
`quickSaleLabel`, `targetValueLabel`. Deliberately does NOT duplicate
`supportsVehicleStatus` — `AddAssetSheet` calls `assetCapabilities()`
directly for that, so the flag lives in exactly one place. `AddAssetSheet`
now calls both functions once per render and reads every Step 1/Step 2
label from their results; the old local `BASIS_LABEL`/`CURRENT_VALUE_LABEL`
maps were removed entirely.

4. VEHICLE CREATION BEHAVIOR
`valuesHeading`: "Vehicle values". Labels: Cost Basis / "Current /
As-Is Value" / "Conservative Quick-Sale Value" / "Target Sale Value" —
matching the brief's suggested wording. No make/model/year/VIN field was
added (none exist canonically). One real addition, evaluated per the
brief's own "Vehicle Status on Create" section: an OPTIONAL "Vehicle
Status" select in Step 2, gated by `assetCapabilities("vehicle").
supportsVehicleStatus`, defaulting to "Status not set", using the exact
same `ASSET_STATUS_OPTIONS` vocabulary Manage uses — no inferred
default, no second status system. Because `create_asset()` has no status
parameter and adding one would mean changing that atomic RPC's
signature (a schema change), this was deliberately implemented WITHOUT
touching the database: `handleSubmit` calls the existing `createAsset()`
first, and only if a status was chosen does it make a second, already-
existing `updateAsset(supabase, asset.id, "vehicle", {statusCode})`
call. If that second call fails, the sheet does not silently discard the
failure or pretend nothing happened — it shows an honest message ("...
was added, but its status could not be saved — set it from Manage
instead") and keeps the sheet open, while still refreshing so the
successfully-created asset is visible.

5. FINANCIAL INVESTMENT BEHAVIOR

bonds and similar investments" (shown under the selected type in Step
1, per the brief's "Type Label Clarity" section, distinguishing it from
Inventory/Stock). Labels: "Amount Invested / Cost Basis" / "Current
Estimated Value" / "Estimated Liquidation Value" / "Target Value" — no
vehicle/repair/listing language anywhere (verified by a regex assertion

Shares-count, Dividend, Market Price, ROI, or Performance field was
invented — none of those are canonically modeled, and this remediation
is about removing false behavior, not building a brokerage system.

12. TYPE-SWITCH STATE HANDLING
`AddAssetSheet`'s `handleAssetTypeChange(next)` — the function passed to
`AssetTypeSelector`'s `onChange` — sets the new `assetType` AND, in the
same handler, clears the `vehicleStatus` draft state whenever
`assetCapabilities(next).supportsVehicleStatus` is false. This runs
immediately on selection in Step 1, not deferred to submit time, so
switching Vehicle -> Financial Investment (or any other type) cannot
carry a stale vehicle-only status value forward — there is no code path
by which an incompatible status could reach `handleSubmit`, since
`handleSubmit` itself only attempts the second `updateAsset()` call when
`capabilities?.supportsVehicleStatus` is true for the CURRENTLY selected
type at submit time, a second independent check.

status-ineligible), and a dedicated test proving the type-switch

infrastructure exists in this environment (same disclosed limitation as
every prior phase's report), so the component's own state-clearing
behavior is not directly exercised by a browser test; these assertions
instead prove the underlying decision function is correct for every
possible switch destination, which is what that behavior is entirely
driven by.
