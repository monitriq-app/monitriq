5. EXISTING PROFILE AUDIT
public.profiles (20260922201924): id = auth.users id, first_name, preferred_name, preferred_currency, timezone, generated onboarding_completed, created_at/updated_at; CHECKs on name lengths and currency shape; BEFORE UPDATE/INSERT trigger validates the timezone and sets updated_at; RLS on with profiles_select_own and profiles_update_own (auth.uid() = id); `revoke all` from anon/authenticated, `grant select`, and a COLUMN-LEVEL `grant update (first_name, preferred_name, preferred_currency, timezone)`. handle_new_user() inserts a row at signup without naming any preference column. The app reads it through getProfile()/getCurrentProfile() (per-request cached) and writes through updateProfile().

6. PREFERENCE MODEL
profiles.financial_language_mode text, stable codes simple | balanced | financial (never display labels). Display labels: Keep it simple / Balanced / Financial terms. Default and fallback: simple. resolveLanguageMode() maps missing, null or invalid input to simple; terminology() never throws.

7. MIGRATION (one, local only)
supabase/migrations/20261003090000_add_financial_language_mode.sql: `alter table profiles add column financial_language_mode text not null default 'simple'`, a named CHECK constraint (simple|balanced|financial), a column comment, and the column-level UPDATE grant. NOT NULL DEFAULT backfills every existing row to 'simple' and gives new signups 'simple' without touching handle_new_user(), so no existing user is blocked. No new table. `supabase db reset --local` applied all 19 migrations cleanly (LOCAL Docker only; the remote was never touched).

8. RLS / GRANTS
Ownership is unchanged (profiles_update_own). Only the column-level grant was extended so the established profile boundary can write the field; anon still has no grants on profiles; no service role in application code. Tested against the real database: A reads own mode; A updates own mode; A's update of B's row affects zero rows and B is unchanged; A cannot read B's preference; anonymous read and update are denied; an invalid value ('expert') and NULL are rejected by the constraint.

9. ONBOARDING

Simple is preselected; it is not a test and has no levels or badges. It saves in the same updateProfile() call. Verified in Chrome: Keep it simple preselected, choosing Balanced saved 'balanced', no overflow at 320, 360, 393 and 430 px in dark and light, cards 63-79px tall.

10. SETTINGS
Profile menu > "Language & explanations" > "How Monitriq explains money" with the same three options (the same LanguageModeSelector component). Saving calls updateProfile() then router.refresh(); the server re-renders in the new mode with no sign-out (verified: switching through all three modes in the UI, the session stayed signed in). The menu now scrolls within the viewport height on short phones.

11. TERMINOLOGY ARCHITECTURE
lib/domain/language: types.ts (modes, default, resolve, selector copy), terms.ts (a typed vocabulary of about 35 semantic keys, each with a label per mode and an optional balanced-only hint; terminology(mode).t(key)/.hint(key)), explain.ts (explanation depth by mode), assets.ts (asset-card wording). The server resolves the mode once per request from the already-cached profile (getLanguageMode, no extra query); server components receive a `terms` object, and client components read it from a LanguageProvider mounted once in AppShell (useTerms(); outside a provider it is Simple). Components ask for semantic keys and never branch on the mode (tested: no mode comparisons in any component or page). One page tree, one set of components and domain reads; there is no SimpleHome/BalancedHome/FinancialHome.

12. SIMPLE VOCABULARY (default)

No primary Simple label contains Safe to Deploy, Minimum Cash Floor, Required Retained Cash, Illiquid, Receivables, Liabilities, Liquidity, Capital Allocation or Disposition (tested).

13. BALANCED VOCABULARY
