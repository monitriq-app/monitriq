9. RECEIVABLE SCHEMA
------------------------------------------------------------------------
`receivables` (id, user_id, name, description, counterparty, currency_code,
expected_payment_date, last_follow_up_at, is_archived, created_at,
updated_at). No `face_amount` column — face is derived (see §10). Currency
immutable once the receivable has any ledger history
(`enforce_receivable_currency_immutable()` BEFORE UPDATE trigger). RLS
enabled, deny-by-default, `auth.uid() = user_id` ownership policies,
column-level grants (identity/audit columns excluded from UPDATE grant).

10. RECEIVABLE BALANCE MODEL
------------------------------------------------------------------------
`receivable_ledger_events` (append-only: opening_face / adjustment /
recovery, signed amounts, currency must match parent). `face_total` =
sum(opening_face + adjustment); `recovered_total` = sum(recovery,
excluding voided); `outstanding_amount = face_total − recovered_total`.
Computed by shared helper `receivable_outstanding_amount()`, used both
for the read model and as the validation boundary for recovery amounts.
No mutable balance column anywhere.

11. RECOVERY MODEL
------------------------------------------------------------------------
`record_receivable_recovery()`: validates receivable ownership, bucket
ownership, not-archived, same-currency, outstanding-not-exceeded,
idempotency key; then atomically creates one `financial_events` row
(`event_type = 'receivable_recovery'`, `cash_flow_class = 'other_inflow'`
— never `income`), one positive `cash_movements` row into the destination
bucket, and one `recovery` ledger row carrying that event's id. Partial
recoveries accumulate correctly (verified with exact cumulative math
across two recoveries). Recovery cannot exceed outstanding. Creating a
receivable never moves cash — only `create_receivable()`'s
`opening_face` ledger row is written, no financial_events row.

12. RECOVERABILITY MODEL
------------------------------------------------------------------------
`receivable_recoverable_estimates` — append-only, latest-row-wins,
optional. `record_recoverable_estimate()` inserts a new estimate row;
`receivable_summary()` surfaces only the latest. Absent, it reads as
`null` ("Not set") — never defaulted to Outstanding Amount, never
fabricated. Verified structurally distinct from both Face and Outstanding
in the test suite.

13. LIABILITY SCHEMA
------------------------------------------------------------------------
`liability_types` (generic registry, seeded: loan, credit_facility,
mortgage, personal_debt, business_debt, other). `liabilities` (id,
user_id, liability_type_code, name, description, counterparty,
currency_code, interest_rate numeric(7,4) optional, is_archived,
created_at, updated_at). Currency immutable once the liability has any
principal-ledger history (`enforce_liability_currency_immutable()`). RLS
+ grants follow the identical pattern to Receivables.

14. LIABILITY PRINCIPAL MODEL
------------------------------------------------------------------------
`liability_principal_events` (append-only: opening_principal / draw /
repayment / adjustment). `liability_outstanding_principal()` =
sum(amount) excluding rows whose linked `financial_event_id` is voided.
Principal cannot go negative — enforced inside `record_debt_payment()`
before the repayment row is inserted.

15. DEBT-PAYMENT MODEL
------------------------------------------------------------------------
`record_debt_payment()` is the compound operation at the center of this
phase. It validates liability ownership, bucket ownership, same-currency,
idempotency, and principal-not-exceeding-outstanding, then in one
transaction: creates a `financial_operations` row (`operation_type =
'debt_payment'`); creates up to three `financial_events` rows — one each
for principal, interest, and fee, but only for the components actually
submitted with a positive amount — all sharing that operation's id; a
matching `cash_movements` row per component; and one `liability_
principal_events` `repayment` row for the principal component only,
linked to its financial_event. Idempotency is checked at the operation
level (one retried call cannot double any component), verified by
counting events per `operation_id` after a retried call.

16. PRINCIPAL/INTEREST/FEE CLASSIFICATION
------------------------------------------------------------------------
`set_financial_event_classification()` extended:
  event_type = 'debt_principal_payment'  → cash_flow_class = 'other_outflow'
  event_type = 'debt_interest'           → cash_flow_class = 'expense'
  event_type = 'debt_fee'                → cash_flow_class = 'expense'
  event_type in ('receivable_recovery','loan_proceeds') → 'other_inflow'
Principal is explicitly never an expense (it is debt-balance movement,
not consumption); interest and fees explicitly are. Verified per-
component in the compound-payment test by querying `financial_events`
filtered by `operation_id` and asserting each row's `cash_flow_class`
individually.

17. COMPOUND FINANCIAL-OPERATION STRATEGY
------------------------------------------------------------------------
The existing `financial_events` table (one `cash_flow_class` per row)
could not correctly represent a single debt payment with three
differently-classified components as one row without misclassifying at
least two of the three. The smallest durable fix: a new
`financial_operations` grouping table (id, user_id, operation_type,
occurred_at, description, idempotency_key) plus a nullable
`financial_events.operation_id` FK. Single-component events (money
received/spent, transfers, receivable recovery, loan proceeds) are
entirely unaffected — `operation_id` stays null. `operation_type` is a
CHECK-constrained, extensible list (currently just `'debt_payment'`),
designed for reuse by a future compound action (asset sale, asset
purchase, receivable settlement) without any further schema change.

18. FINANCIAL-EVENT CHANGES
------------------------------------------------------------------------
`financial_events.event_type` CHECK extended to add:
'receivable_recovery', 'debt_principal_payment', 'debt_interest',
'debt_fee', 'loan_proceeds'. `financial_events_category_matches_type`
constraint extended accordingly. New nullable `operation_id` column +
FK (`ON DELETE RESTRICT`) to `financial_operations`. A new additive
column-level grant, `grant insert (operation_id) ... to authenticated`,
was required (see §33 for why).

19. IDEMPOTENCY
------------------------------------------------------------------------
Receivable recovery: idempotent via the existing per-user
`idempotency_key` partial unique index on `financial_events`, exactly as
Money's primitives already work — a retried recovery with the same key
does not create a second event, cash movement, or ledger row.
Debt payment: idempotency is checked at the `financial_operations` level
(one key covers the whole compound operation, not each sub-event
individually) — a retried debt payment does not double any of principal,
interest, or fee. Both verified explicitly in their respective suites.

20. CORRECTION/VOIDING STRATEGY
------------------------------------------------------------------------
Ledger rows with a real cash effect (`receivable_ledger_events.recovery`,
`liability_principal_events.draw`/`repayment`) carry a nullable
`financial_event_id`. Every balance-computing read function
(`receivable_outstanding_amount()`, `liability_outstanding_principal()`,
and the summary functions) joins to `financial_events` and excludes rows
whose `voided_at is not null`. There is no separate void/active flag on
either ledger table — a single source of truth, derived, never
independently toggled. Voiding a recovery or a debt principal-payment
event through the existing, unmodified `voidFinancialEvent()` mechanism
therefore reverts both cash and the domain-specific outstanding balance
consistently, by construction. Both suites contain a dedicated test that
voids an event and asserts both figures move by the exact originating
amount in the correct direction.

21. MULTI-CURRENCY BEHAVIOR
------------------------------------------------------------------------
Both domains are natively multi-currency; NGN is never assumed. Currency
is fixed once a receivable/liability has ledger history. Recovery and
debt payments are same-currency-only this phase (destination/source
bucket currency must equal the receivable's/liability's currency) —
mismatches are rejected outright at the database layer, mirroring
Assets' no-cross-currency-appraisal stance rather than Money's
`fx_transfer` path. Native-currency totals
(`receivable_native_currency_totals()`, `liability_native_currency_
totals()`) never sum across currencies and reuse the shared
`convertToReportingCurrency()` — a missing rate returns `not_calculated`,
never a guessed blended figure.

22. EXACT-DECIMAL STRATEGY
------------------------------------------------------------------------
All amount columns are `numeric(20,6)` (interest_rate is `numeric(7,4)`,
treated as a plain recorded metadata field, not cash-transport). No
`real`/`double precision` anywhere. Every currency's `decimal_exponent`
is enforced via BEFORE INSERT triggers on both new ledger tables (a
JPY 0-decimal receivable/liability rejects a fractional amount; a KWD
3-decimal liability accepts one — both tested explicitly). All read
functions cast amounts to `::text` to avoid PostgREST's JSON-number
float64 risk. `decimal.js` remains the only arbitrary-precision library;
the `asNumericParam()`/`asOptionalNumericParam()` helper pattern from
Money/Assets is reused unchanged in both new repositories.

23. RLS POLICIES
------------------------------------------------------------------------
Every new table (`receivables`, `receivable_ledger_events`,
`receivable_recoverable_estimates`, `liability_types`, `liabilities`,
`liability_principal_events`, `financial_operations`) has RLS enabled
immediately, deny-by-default, no policy granting anonymous access.
`liability_types` is public reference data (like `currencies`) — a
permissive `USING (true)` SELECT policy, no user-owned rows. All other
tables use `auth.uid() = user_id` ownership policies plus EXISTS-based
cross-tenant checks wherever a row references another domain (below).

24. CROSS-DOMAIN REFERENCE PROTECTIONS
------------------------------------------------------------------------
Every INSERT policy on a row that references another user-owned table
checks EXISTS on that reference, scoped to `auth.uid()`:
  - receivable_ledger_events → receivables
  - liability_principal_events → liabilities
  - financial_events.operation_id → financial_operations (new this phase)
  - financial_events.bucket-adjacent references → cash_buckets (existing,
    reused unchanged for receivable_recovery/debt_payment/loan_proceeds
    cash_movements)
All `record_*` RPCs additionally re-verify ownership of every referenced
row inside the function body (never trusting RLS alone as the only
check, never trusting a caller-supplied `user_id`).

25. ADVERSARIAL TESTS
------------------------------------------------------------------------

update/archive rejection, forged ownership on create (attempting to set

recovery/payment directed at another user's bucket, recovery/payment
directed at another user's receivable/liability, and loan-proceeds
cross-tenant rejection. All pass.

26. FINANCIAL-CORRECTNESS TESTS
------------------------------------------------------------------------

exceeds-outstanding rejection; recovery classified as `other_inflow`
never `income`; receivable creation has zero cash effect; principal-only
debt payment moves cash and principal by the exact same amount and is
