7. PRODUCT DECISIONS ESTABLISHED
----------------------------------
- Production name is Monatriq; "Capital Compass" is retired as a working
  name only, with no in-repo references requiring migration.
- Monatriq is defined as a personal financial position, asset, goal and
  decision-management application — explicitly not just an expense
  tracker, budgeting app, net-worth calculator, investment app, or
  autonomous AI adviser. The user remains the decision-maker.
- Primary product areas confirmed: Home, Money, Quick Add, Assets,
  Decisions, Goals, with supporting domains: Profile, Cash Buckets,
  Liabilities, Financial Rules, Obligations, Businesses, Receivables,
  Valuation History, Decision Assumptions, Goal Allocations, Audit/
  Financial Events.
- Home is confirmed as an aggregation/command-center layer only, never an
  independent source of financial truth.
- V1 is manual-first: no live bank connection required.
- Multi-user from day one; no shared family wallet, no social feed, no
  leaderboards in V1.
- Currency and timezone are per-user profile settings, not global
  hardcoded defaults.

8. ARCHITECTURE DECISIONS ESTABLISHED
----------------------------------------
- One shared financial domain calculation layer is mandatory; Money,
  Assets, Goals, Decisions and Home must all consume it rather than
  independently computing cash, net worth, or deployable capital.
- Proposed stack confirmed: Next.js + TypeScript + Supabase (Postgres +
  Auth) + PWA.
- Proposed repository layout documented (app/, lib/domain, lib/supabase,
  supabase/migrations, supabase/tests, docs/, public/) as a target for
  future phases — not created in this phase.
- A lightweight, append-only financial event log is the chosen audit
  mechanism — explicitly not full event sourcing and not a blockchain-style
  design, per instruction to use the simplest architecture that preserves
  integrity and traceability.
- Brand asset production placement (public/ icons, PWA manifest, app shell
  usage) is planned but deferred to the implementation phase that builds
  the app shell.

9. FINANCIAL-DOMAIN DECISIONS ESTABLISHED
---------------------------------------------
- Asset value concepts kept distinct: Cost Basis, Estimated Current Value,
  Conservative/Quick-Sale Estimate, Target Value, Potential Liquidity,
  Actual Sale Price.
- Worked compound-event examples formalized: receivable recovery, asset
  purchase, capitalizable resale-vehicle repair vs. non-capitalizable
  personal maintenance, asset sale (gross proceeds vs. selling costs vs.
  capital returned vs. realised profit/loss vs. cash received), and debt
  payment (principal vs. interest/fees).
- Receivables model defined: Face Amount, Recovered Amount, Outstanding
  Amount, optional Estimated Recoverable Value, optional Expected Payment
  Date, optional Last Follow-Up. Full collectibility is never assumed.
- Goals defined as typed and extensible (Savings/Reserve, Purchase/
  Property, Debt Payoff, Recurring Income, Business Capital, Relocation/
  Milestones, Education, Vehicle, Event, Travel, Custom), with a "one
  naira, one purpose" allocation rule to prevent double counting.
- Protected goals: protection is user-configured; overriding it always
  shows impact/conflict, allows cancellation, and records the override —
  the system never decides autonomously.
- Decisions are explicitly non-transactional: saving "Proceed" never moves
  money; decision figures are tagged as Tracked Fact / User Estimate /
  User Assumption / Derived Calculation, with missing assumptions staying
  missing.
- Financial Rules and Safe to Deploy are both defined as "Not configured"/
  "Not calculated" by default until the user supplies real configuration —
  no invented thresholds or guessed formulas.
- Recurring income is restricted to explicitly recurring sources, excluding
  asset sales, receivable recovery, refunds, transfers, one-off jobs and
  windfalls by default.
- Internal transfers between the user's own cash buckets are never counted
  as income, spending, or net-worth change.

10. SECURITY / RLS DECISIONS ESTABLISHED
--------------------------------------------
- Row Level Security is non-negotiable on every user-owned table, default
  posture deny-by-default, policies keyed on auth.uid() = user_id.
- Isolation must never rely solely on client-side filtering, frontend route
  protection, hidden IDs, or application-only checks.
- No normal UI/admin path may allow one user to view or act on another
  user's financial records.
- Supabase service-role credentials must never reach browser/client code;
  any service-role use must be server-side and explicitly justified.
- Every future data-layer phase must include RLS review, cross-user
  isolation tests, adversarial direct-query tests, and mutation isolation
  tests before being considered complete.
- The git-repository-root risk (home directory as repo root) was recorded
  as a source-control hygiene risk relevant to future secrets handling,
  though it is not itself an application security defect and was not
  altered without instruction.
