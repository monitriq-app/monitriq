OBJECTIVE
------------------------------------------------------------------------
Remove the documented second-order limitation in
`evaluate_proposed_cash_use()`: the evaluator must produce an internally
consistent hypothetical post-use Safe-to-Deploy state using the SAME
economic logic as the authoritative current-state Safe-to-Deploy engine
(`safe_to_deploy_by_currency()`), correctly accounting for a protected
goal funded from multiple cash buckets and the protected obligations
linked to it — before Decisions is ever built to consume the evaluator.

PREVIOUS LIMITATION
------------------------------------------------------------------------
`evaluate_proposed_cash_use()` computed the "before" state by calling
`safe_to_deploy_by_currency()`, but computed the "after" state by locally
patching only the ONE proposed bucket's own contribution to
`protected_goal_cash` (via a scalar delta), while leaving
`uncovered_protected_obligations` completely UNCHANGED from the "before"
value. This was correct only when the affected protected goal happened
to be funded from a single bucket. Whenever a goal was funded from
several buckets — a supported, tested pattern since P0-E2-S5 — a proposed
spend from one of those buckets could silently under-report (or fail to
report at all) a resulting protected-obligation coverage shortfall,
because the OTHER buckets' real, unaffected contribution to that goal's
backing was never re-examined and the obligation-coverage comparison was
never re-run against the new total.

ROOT ARCHITECTURE
------------------------------------------------------------------------
The fix threads an optional hypothetical bucket-balance override
(`p_hypothetical_bucket_id`, `p_hypothetical_delta`, both defaulting to
null/0) through the entire existing dependency chain rather than writing
a second formula:
  goal_backed_protected_allocation(goal_id, [hyp_bucket, hyp_delta])
    -> rules_uncovered_protected_obligations([hyp_bucket, hyp_delta])
      -> safe_to_deploy_by_currency([hyp_bucket, hyp_delta])
With no arguments, every function computes exactly the real current
state — byte-identical to P0-E2-S6's behavior, proven by the complete,
unmodified P0-E2-S6 test suite (69 assertions) still passing against the
refactored functions. `evaluate_proposed_cash_use()` now calls
`safe_to_deploy_by_currency()` exactly twice (real, then hypothetical)
and contains no independent Safe-to-Deploy arithmetic of its own.

MIGRATION CHANGES
------------------------------------------------------------------------
One new migration, no table added/altered/dropped — every change is to
function bodies and signatures:
  - `goal_backed_protected_allocation(uuid)` DROPped and recreated as
    `(uuid, uuid, numeric)` — hypothetical delta applied to exactly the
    matching bucket inside the pro-rata backing calculation; a genuine,
    unrelated NUMERIC-division precision bug was also fixed here (see
    Validation section).
  - `rules_uncovered_protected_obligations()` DROPped and recreated as
    `(uuid, numeric)` — threads the override through to the backing
    calculation; the per-goal obligation-aggregation logic itself is
    completely unchanged from P0-E2-S6.
  - `safe_to_deploy_by_currency()` DROPped and recreated as
    `(uuid, numeric)` — the hypothetical delta is folded into both the
    currency's liquid-cash total (via a synthetic adjustment row, scoped
    to the caller's own bucket) and the affected bucket's own protected-
    backing contribution; every other CTE (obligations, floors) is
    unchanged.
  - `evaluate_proposed_cash_use(uuid, numeric)` DROPped and recreated
    with the same public signature but an entirely rewritten body (see
    Shared calculation strategy) and three new output columns.
Each function is DROPped by its exact prior signature before being
recreated — required because Postgres identifies a function by
name+signature; a bare `CREATE OR REPLACE` with a different parameter
list creates a second, ambiguously-overloaded function rather than
replacing the first (documented as a standing rule in
`docs/security/SECURITY_AND_RLS_PRINCIPLES.md §18`).

SHARED CALCULATION STRATEGY
------------------------------------------------------------------------
Exactly the brief's "one calculation model" instruction: no
Safe-to-Deploy-Formula-B exists anywhere. `evaluate_proposed_cash_use()`
calls the real `safe_to_deploy_by_currency()` for "before" and the same
function with a hypothetical override for "after," then derives every
returned figure from a straightforward comparison of those two records
(or from simple, unchanged bucket-local balance arithmetic for the
current/post-use-balance and this-bucket's-own-shortfall fields, which
were never part of the documented limitation). There is no second SQL
expression anywhere in the codebase that reimplements
`protected_commitments`, `required_retained_cash`, `safe_to_deploy`, or
`retained_deficit`.

HYPOTHETICAL-STATE STRATEGY
------------------------------------------------------------------------
The override is applied at exactly one point in each function: the
balance of the one named bucket, inside that function's innermost
balance-computing subquery (a `case when <this bucket> then real_balance
+ delta else real_balance end`). Every downstream computation —
per-bucket protected backing (`LEAST(protected_total, balance)`),
per-goal pro-rata backed allocation, per-goal obligation-coverage
aggregation, and the final currency-level MAX-based formula — flows from
that one adjusted number through otherwise completely unmodified logic.
A hypothetical-bucket lookup is independently scoped to
`user_id = auth.uid ()` everywhere it's resolved (the
`hypothetical_adjustment` CTE in `safe_to_deploy_by_currency()`; the
`case when n.bucket_id = p_hypothetical_bucket_id` branch in
`goal_backed_protected_allocation()`) — pointing the override at a
bucket that is not the caller's own silently contributes nothing, never
an error, never another tenant's data, defense-in-depth alongside
`evaluate_proposed_cash_use()`'s own mandatory ownership check at the
entrypoint.

MULTI-BUCKET GOAL BEHAVIOR
------------------------------------------------------------------------
Verified against Worked Case 1 exactly: a protected goal funded 4,000
from Bucket A (balance 5,000) and 4,000 from Bucket B (balance 5,000),
backed 8,000 total, with a linked 7,000 protected obligation (uncovered
0). Evaluating a hypothetical 3,000 spend from Bucket A alone: Bucket A
can now back only 2,000 of its own allocation (pro-rata:
4,000 × LEAST(2,000, 4,000) / 4,000 = 2,000); Bucket B, untouched,
still backs its full 4,000. Total backing 6,000, exactly matching the
brief. Worked Case 2 verified with a smaller 1,500 spend: backing
reduces to 7,500 (still above the 7,000 obligation), uncovered correctly
stays 0. Worked Case 5 verified with one bucket funding two separate
protected goals, each also funded from its own additional bucket:
combined backing correctly drops from 14,000 to 10,000 after a
hypothetical spend from the shared bucket, both goals' individual
pro-rata reductions correctly summed.

OBLIGATION-COVERAGE BEHAVIOR
------------------------------------------------------------------------
Verified against Worked Case 4 exactly: a second protected obligation
(2,000) added to the same multi-bucket goal already carrying a 7,000
obligation. Combined linked total 9,000 is aggregated PER GOAL before
comparing against backing (unchanged aggregation logic from P0-E2-S6,
now correctly fed a hypothetically-recomputed backing figure) — a
hypothetical spend from Bucket B reducing total backing to 7,000
correctly reports uncovered = 2,000 (9,000 − 7,000), not 0 (which an
incorrect independent-per-obligation-claim model would have produced,
since 2,000 alone is less than 7,000).

CONFLICT SEMANTICS
------------------------------------------------------------------------
`protected_obligation_status` is upgraded from P0-E2-S6's coarse "does
this bucket fund some linked obligation" heuristic to a direct
comparison of the fully recomputed hypothetical result:
`conflict` when the proposed use creates or worsens uncovered protected
obligations (`uncovered_after > uncovered_before`) — a direct coverage
failure; `attention` when protected liquidity for the currency decreases
without an outright coverage failure (`protected_goal_cash_after <
protected_goal_cash_before`) — a factual, evidence-based signal, never an
invented percentage threshold; `aligned` otherwise. All five labels
remain within the established neutral vocabulary
(aligned/attention/conflict/not_configured/insufficient_information) —
verified by the existing P0-E2-S6 advisory-vocabulary-blocklist test,
still passing unmodified.

OVERRIDE INTEGRATION
------------------------------------------------------------------------
`record_cash_use_override()` was not modified at all this phase — it
already called `evaluate_proposed_cash_use()` for its snapshot, so
fixing the evaluator automatically corrects every override recorded from
this point forward with zero additional code. Verified explicitly:
recording an override for Worked Case 1's exact scenario (which the
pre-S6A evaluator would have shown as `'aligned'`, since
uncovered_protected_obligations was never recomputed) now correctly
captures `'conflict'` in the immutable `conflicts_snapshot` JSONB.
